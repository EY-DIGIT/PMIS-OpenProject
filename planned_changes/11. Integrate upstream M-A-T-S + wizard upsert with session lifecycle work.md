## Merge strategy

1. `git stash push -u` — preserved both tracked and untracked session-10 work. Partial-reset left `pmis.db` locked by a stale process; released the lock and restored a clean working tree.
2. `git pull --ff-only` — fast-forwarded to `af67d12`.
3. `git checkout stash@{0} -- <file>` selectively — restored the 10 files session-10 touched where upstream did not, bypassing the stash-pop conflict path entirely.
4. Hand-merged 8 files where both sides edited.
5. Adapted three call sites in session-10 code to match upstream's contracts.
6. Dropped the stash; ran the full suite.

Rationale for not using `git stash pop`: six of the stashed files conflicted with upstream and the three cross-team stubs had the "already exists, no checkout" problem. A targeted checkout + hand-merge gives a more legible diff than resolving nine conflict markers.

## Notable contract boundaries to keep in mind

- **`ProjectRepository.upsert_by_identifier` commits internally.** Every other write on `ProjectRepository` (`create`, `update`, `soft_delete`, `hard_delete`) is flush-only and commits at the service edge. Upstream's `upsert_project` service is aware of this; session-10 services are aware of their half. Do not wrap `upsert_by_identifier` in a service-edge transaction or commit a second time around it.
- **Upsert does not clear `deleted_at`.** `upsert_by_identifier` updates content fields but leaves `deleted_at` untouched. A soft-deleted row that is re-upserted stays soft-deleted. This has not been exercised and is a latent issue if the wizard ever re-uses a soft-deleted identifier; flagged for the M/A/T/S contributor.
- **New vocabulary is shared.** `ProjectUpsertRequest`, `ProjectCreateRequest`, and `ProjectUpdateRequest` now all validate against the session-10 status set. Existing upstream tests and the wizard's Step 1 default (`status="new"`) remain valid; `in_progress`/`completed`/`on_hold` are gone.
