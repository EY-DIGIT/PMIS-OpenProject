# Feature additions — vendors, category-others, milestone/activity metadata, level restrictions, and baseline-to-version propagation

## Context

Document 11 closed out the merge of the upstream M/A/T/S + wizard-upsert work with the session-10 lifecycle modules. This document captures the changes made on top of that integrated base. These are **application-level feature additions and contract tightening**, not merge reconciliation — no overlap with document 11.

Work recorded here falls into three groups:

- **A.** Nine feature additions requested by the product team (vendors, category-others, milestone metadata, activity resource metadata, cascade-delete to versions, explicit `Save Project` button).
- **B.** Endpoint renaming to unambiguous `/create` suffix at every resource level.
- **C.** Baseline/version write-level restrictions + allow post-publish baseline edits + propagate baseline M/A changes to active versions with per-version audit rows.

## A. Feature additions

### A.1 Free-text `categoryOther` on project

`Project.category` now accepts `others` alongside `MSIP`/`MSAP`/`BSP`. When `category='others'`, the request MUST supply a non-empty `categoryOther` (max 255 chars); for any other category the field MUST be omitted.

- DB: `projects.category_other VARCHAR(255) NULL`.
- Request schemas: `ProjectCreateRequest`, `ProjectUpdateRequest`, `ProjectUpsertRequest`.
- Service validation: `app/api/v3/projects/services/create.py`, `upsert.py`, `update.py`.
- Response: emitted as `categoryOther` via `format_project_response`.
- Carried forward by `create_version` when a project is versioned.
- Transitions constant added: `CATEGORY_OTHERS = "others"` in `services/transitions.py`.

### A.2 Vendor catalog + project/milestone vendors

Two new tables:

- `vendors` — catalog (id UUID, name unique, description, active). Five demo vendors seeded on boot: Infosys, TCS, Wipro, Accenture, Capgemini.
- `project_vendors` — association (project_id, vendor_id) composite PK.
- `milestone_vendors` — association (milestone_id, vendor_id) composite PK.

Endpoints: `GET /vendors` (any authenticated user), `POST /vendors/create` (admin), `PATCH /vendors/{id}` (admin). RBAC: `VENDORS_READ` granted to ADMIN/MEMBER/VIEWER; `VENDORS_MANAGE` to ADMIN only.

Validation:
- On project create/update: each supplied vendor_id must exist and be active.
- On milestone create/update: vendor_ids must be a **subset of the parent project's vendors** (you cannot attach a vendor to a milestone unless the project itself has signed off on that vendor).
- `vendorIds: []` on update clears the current vendor list; omitting the field leaves it unchanged.

### A.3 Milestone `status`, `depends`, `vendors`

- `milestones.status VARCHAR(32) NOT NULL DEFAULT 'not_completed'` indexed. Choices: `not_completed`, `completed` (extensible via `MILESTONE_STATUS_CHOICES` in `domain/milestones/milestone.py`).
- `milestones.depends JSON NULL` — pass-through list of milestone ids. No referential integrity enforced; the wizard owns the dependency graph.
- Vendors via `milestone_vendors` association; response format includes the full vendor list on every milestone read.

### A.4 Standard-activity `status` + `dependency`

Standard-type activities only (rejected on `resource` / `transactional` types):
- `activities.status VARCHAR(32) NULL` indexed. Defaults to `not_completed` when type is `standard`. Choices in `ACTIVITY_STATUS_CHOICES`.
- `activities.dependency JSON NULL` — pass-through list of activity ids.
- Type transitions into `standard` (via PATCH) auto-apply the default `status`; transitions out of `standard` clear both `status` and `dependency`.

### A.5 Resource-activity classification columns

On `activity_resources`:
- `type_of_resource_id VARCHAR(36) FK resource_types(id)` — required when an activity is `type='resource'` + `resourceMode='details'`. Must reference an active row.
- `division VARCHAR(32)` — one of `tmd1`, `tmd2`, `others` (constants in `domain/resource_types/resource_type.py`).
- `division_other VARCHAR(255)` — required when division='others'; rejected otherwise.

New `resource_types` catalog table, seeded with `rfp` / `asg` / `ccm`. Endpoints `GET /resource_types` (authenticated) and `POST /resource_types/create` (admin).

Clone carries forward `type_of_resource_id`, `division`, `division_other` when a version is spawned.

### A.6 `POST /projects/{uuid}/save` — explicit Save Project

Step-1 wizard button. Flips `status` from `new` → `draft` when ≥ 1 live milestone exists on the project. Returns 422 when called with zero milestones (with a milestone-mentioning error message). Idempotent after draft. 404 on unknown project. Audit action: `project.draft`.

Added: `services/save.py`, route on `POST /projects/{uuid}/save`. Adding a milestone no longer implicitly flips `status` — only the explicit Save button does.

### A.7 Soft-delete a baseline cascades to its versions

`DELETE /projects/{uuid}` on a baseline now discovers every live version (via `ProjectRepository.list_live_version_ids`) and soft-deletes each version's M/A/T/S subtree in the same transaction. Per version, a `project.soft_delete` audit row is written with `cascaded_from_baseline_id` in the `before` payload so lineage is traceable. Deleting a version alone leaves the baseline and siblings live (unchanged behavior).

### A.8 `status_explanation` audit

Whenever `status_explanation` is modified on a PATCH, the audit before/after payload already captures it via `project_snapshot`. (No schema change; flagged here for completeness.)

### A.9 Postman collection rewrite

`PMIS_API_Collection.postman_collection.json` grew from 1,303 → 1,802 lines to cover the nine additions plus the M/A/T/S surface. Now: 18 folders, 90 requests, 14 collection variables, all request paths using `{{projectUuid}}` / `{{milestoneId}}` / etc. The file is tracked but the updated version is currently uncommitted.

## C. Level-write restrictions + baseline editable after publish + baseline→version propagation

### C.1 Level-write guards

`assert_project_editable` was superseded in two directions inside `app/core/project_lock.py`:

- `assert_project_editable(db, project_id)` — project exists + not soft-deleted. **No longer blocks published baselines.** Still used by project PATCH and restore.
- `assert_milestone_activity_writable(db, project_id)` — project is a live **baseline** (`is_version=False`). Used by milestone/activity create/update/delete services. Versions get **403** with "Milestones and activities can only be added or modified on the baseline project... changes propagate to active versions automatically."
- `assert_task_subtask_writable(db, project_id)` — project is a live **version** (`is_version=True`). Used by task/subtask create/update/delete. Baselines get **403** with "Tasks and subtasks can only be added or modified within a version. Create a version of this baseline first."

Restore services (M/A/T/S) keep the permissive `assert_project_editable` — restoring a soft-deleted row is an admin-only repair action and isn't meant to create new tree shapes.

### C.2 Published baselines remain editable

`EDITABLE_FIELDS_BASELINE_PUBLISHED` in `services/transitions.py` now aliases `EDITABLE_FIELDS_BASELINE_UNPUBLISHED` (was the empty set). Published baselines accept the same PATCH fields as unpublished baselines: `name`, `description`, `owner`, `start_date`, `end_date`, `public`, `active`, `status_explanation`.

### C.3 Propagate baseline M/A changes to active versions

New lineage column on both milestones and activities:

- `milestones.cloned_from_id VARCHAR(36) FK milestones(id) NULL` indexed.
- `activities.cloned_from_id VARCHAR(36) FK activities(id) NULL` indexed.

Baseline rows have `cloned_from_id = NULL`. When `clone_tree_for_version` mints a version's M/A rows it stamps `cloned_from_id = source.id`. Drift migrations cover SQLite upgrades; columns are on `Base.metadata` so `create_all()` covers fresh DBs.

New module `app/api/v3/projects/services/baseline_version_sync.py` exposes:

- `propagate_milestone_create(db, baseline_milestone_id, actor_id)` — on each active version, mint a twin milestone with `cloned_from_id` set.
- `propagate_milestone_update(db, baseline_milestone_id, updates, actor_id)` — apply matching `name`/`description`/`start_date`/`end_date`/`position` patch to every version twin.
- `propagate_milestone_soft_delete(db, baseline_milestone_id, actor_id)` — soft-delete version twins + their subtree.
- `propagate_activity_create`, `propagate_activity_update`, `propagate_activity_soft_delete` — same pattern; activity propagation resolves the version's parent milestone via the milestone's own lineage.

**Active version** = `is_version=True AND deleted_at IS NULL AND status NOT IN ('suspended', 'closed')`. Suspended or closed versions are dormant and do NOT receive propagation.

**Field scope.** Propagated: `name`, `description`, `start_date`, `end_date`, `position` on milestones; those plus `type`, `resource_mode`, `resource_count` on activities. Deliberately **not** propagated: `status`, `depends`, `dependency` — those are version-local (each version tracks its own progress, and dependency id lists reference sibling rows that differ between versions). Vendor associations are also not propagated.

**Audit.** Every baseline M/A write records a `milestone.*` / `activity.*` audit row on the baseline project. Each cascaded version twin gets a corresponding `*.cascade_from_baseline` audit row on the **version's** project_audit_logs, with the source baseline entity id in the `before` payload.

### C.4 Test coverage

New test file `tests/test_baseline_version_propagation.py` (14 tests):

- Legacy bare POST paths return 404/405.
- Versions cannot add milestones or activities.
- Baselines cannot add tasks.
- Patching a published baseline succeeds.
- Version clone stamps `cloned_from_id` on both milestones and activities.
- Baseline milestone/activity update propagates name changes to version twins.
- `status` updates on baseline milestones do **not** propagate (version-local).
- New baseline milestones after versioning mint twins on active versions.
- Deleting a baseline milestone cascades (soft) to version twins.
- Suspended versions are NOT touched by propagation.
- Each cascade writes its own audit row on the version project.

## Known limitations (scope-out)

- Baseline date changes that push a milestone's window outside its existing version tasks will produce logically inconsistent T/S dates on the version. The cascade does not re-validate T/S against the new M dates — that stays a version-local concern.
- Baseline **vendor** replacements are not propagated (out of scope; versions may tighten their own vendor subset).
- Activity **resource sub-entity** changes (classification columns on `activity_resources`) do not propagate.
- Restore of a M/A on a project whose is_version flag would reject a fresh create is not blocked by the new guards. Restore is admin-only and stays permissive.
