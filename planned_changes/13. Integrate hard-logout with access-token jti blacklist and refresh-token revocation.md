# Integrate hard-logout: access-token jti blacklist + refresh-token revocation

## Context

Pulled commit `728433a` "Add hard logout: access-token jti blacklist + refresh-token revocation" by kamal21. 12 files, +498 / -18 on top of the post-rebase HEAD.

The motivation: previously, the only way to end a session was to wait for the access token to expire. That left revoked sessions live for the remainder of the token's exp window. Hard-logout now actively invalidates both halves of the session server-side.

## What the commit changes

### New model — `RevokedTokenModel`

[`app/infrastructure/db/models/revoked_token.py`](app/infrastructure/db/models/revoked_token.py) — the access-token blacklist.

- `jti VARCHAR(64) PK` — the token's `jti` claim (uuid4 hex).
- `user_id INTEGER FK users.id` — for per-user introspection/cleanup.
- `revoked_at DATETIME` — when the row was inserted.
- `expires_at DATETIME` — the token's natural `exp`. Rows past this are harmless and can be cleaned up.
- Indexes on `user_id` and `expires_at`.

### New repository — `RevokedTokenRepository`

[`app/infrastructure/db/repositories/revoked_token_repository.py`](app/infrastructure/db/repositories/revoked_token_repository.py):

- `is_revoked(jti)` — `True` iff the jti is blacklisted AND `expires_at > now()`. Past-expiry rows return `False`.
- `revoke(jti, expires_at, user_id)` — idempotent insert (silent no-op if jti already revoked). Flushes, no commit.
- `cleanup_expired()` — optional disk-space helper (not wired to a cron).

### New service — `logout_user`

[`app/api/v3/users/services/logout.py`](app/api/v3/users/services/logout.py):

1. Clears `users.refresh_token_jti` + `refresh_token_expires_at` (via `user_repo.update_refresh_token_metadata(user_id, None, None)`). Any stored refresh token can no longer mint new access tokens.
2. If the incoming request's access-token jti + exp are available, inserts a blacklist row. If exp is already in the past, skips (pointless row).
3. Commits. Returns `ServiceResult.ok({"message": "Logged out successfully."})`.

Tokens without a `jti` claim (pre-blacklist era) are handled gracefully — only the refresh-token clearing runs.

### New route — `POST /api/v3/users/logout`

[`app/api/v3/users/routes.py:61-78`](app/api/v3/users/routes.py#L61-L78) — requires authentication (via `require_authenticated()`), no specific permission. Idempotent.

### Token-mint change — `security.create_access_token`

[`app/core/security.py`](app/core/security.py) — every new access token now carries a `jti: uuid4().hex` claim. Needed so the blacklist has something to key off. Tokens minted before this change have no jti; they're grandfathered (never revoked, expire naturally).

### Auth middleware change

[`app/core/middleware/auth.py`](app/core/middleware/auth.py) — now:

1. Decodes the token (signature + exp) as before.
2. If the token has a `jti`, checks `RevokedTokenRepository.is_revoked(jti)`. If revoked, treats the request as anonymous (skips attaching user to request state). Downstream RBAC then rejects protected routes with 401.
3. Attaches `token_jti` and `token_exp` to `request.state` so the logout endpoint can revoke the current token without re-decoding.

The blacklist lookup opens a short-lived DB session per request — one indexed PK probe, microseconds on SQLite. Fine for this workload.

### Tests

[`tests/test_users.py`](tests/test_users.py) adds 10 tests under `TestLogout`:

- `test_logout_success` — happy path 200.
- `test_logout_blacklists_access_token` — same token is rejected (401) on the next protected call.
- `test_logout_clears_refresh_token` — `users.refresh_token_jti` becomes NULL.
- `test_logout_inserts_blacklist_row` — a `RevokedTokenModel` row exists with correct `jti` / `expires_at`.
- `test_logout_idempotent` — two consecutive logouts both return 200; only one blacklist row exists.
- `test_logout_without_auth_rejected` — 401 when no Authorization header.

- Plus three supporting tests verifying the round-trip (login → protected call → logout → protected call → 401).

## Operational notes

- **Cleanup.** `revoked_tokens` grows 1 row per logout, capped by token lifetime. For a 1-hour access token and an active user base of N, at most N rows accumulate per hour. Call `RevokedTokenRepository.cleanup_expired()` from a cron if you want to recover the disk, but it isn't required for correctness.
- **"Logout everywhere".** Out of scope. Each access token carries its own jti, so logging out on one device only revokes that device's token. A future `POST /users/logout-all` would need to enumerate every unexpired jti for the user (which we don't currently track — the blacklist is keyed by revoked tokens, not minted ones). Two implementation paths: (a) stamp every minted jti in a new `issued_tokens` table and blacklist them en masse on logout-all, or (b) bump a user-level `token_epoch` column that the middleware compares against every access token's iat. Path (b) is simpler but requires a claim change.
- **Refresh-token flow.** Clearing `refresh_token_jti` is a single-device revocation for refresh tokens too. If the same user has a second browser with a different refresh token, it's unaffected — but in practice there's only one refresh token per user row right now, so there's only ever one refresh to clear.
