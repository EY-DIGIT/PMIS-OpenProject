# Split activity-create into one endpoint per (type, mode)

## Context

The original activity-create surface was a single catch-all:

```
POST /milestones/{milestone_id}/activities/create
  body: { type, resourceMode?, resourceCount?, resource?, status?, dependsOn?, ... }
```

The `type` + `resourceMode` discriminators pushed a lot of complexity into the body: Swagger rendered one schema with 12+ mostly-optional fields; a post-parse `model_validator` rejected every invalid combination with a message the caller could only discover experimentally. Team feedback: "the activity endpoints are too cluttered when calling using activity type".

This change splits the single endpoint into four focused endpoints, one per (type, mode) pair. The URL encodes the discriminator; the body only carries the fields that type actually uses.

## New endpoint surface

| Endpoint | Body |
|---|---|
| `POST /milestones/{id}/activities/standard/create` | `name`, `description`, `startDate`, `endDate`, `actualStartDate`, `actualEndDate`, `position`, `status`, `dependsOn` |
| `POST /milestones/{id}/activities/resource/count/create` | `name`, `description`, `startDate`, `endDate`, `actualStartDate`, `actualEndDate`, `position`, **`resourceCount` (required, ≥ 1)**, `dependsOn` |
| `POST /milestones/{id}/activities/resource/details/create` | `name`, `description`, `startDate`, `endDate`, `actualStartDate`, `actualEndDate`, `position`, **`resource` (required, with `typeOfResourceId` + `division` both required)**, `dependsOn` |
| `POST /milestones/{id}/activities/transactional/create` | `name`, `description`, `startDate`, `endDate`, `actualStartDate`, `actualEndDate`, `position`, `dependsOn` |

No body carries a `type` discriminator. No body carries fields that belong to a different type — the schemas literally don't define them.

## Implementation

### Schemas — [`app/api/v3/activities/schemas.py`](app/api/v3/activities/schemas.py)

Added a shared `_ActivityCommonFields` base with `name`, `description`, `startDate`, `endDate`, `actualStartDate`, `actualEndDate`, `position`, `dependsOn`, and the `endDate ≥ startDate` cross-field validator. Then four leaves:

- **`StandardActivityCreateRequest`** — adds `status` (optional; schema validator enforces `ACTIVITY_STATUS_CHOICES`).
- **`ResourceCountActivityCreateRequest`** — adds required `resourceCount: int ≥ 1`.
- **`ResourceDetailsActivityCreateRequest`** — adds required `resource: ResourcePayload` and a `model_validator` that enforces `typeOfResourceId` and `division` are both non-null (the inner `ResourcePayload` already handles the `division='others' ↔ divisionOther` idiom).
- **`TransactionalActivityCreateRequest`** — no extra fields (body is just the common ones).

The old `ActivityCreateRequest` class is kept in the module for now so external callers (the Postman collection, any UI) don't fail to import — but it's no longer referenced by any route. `ActivityUpdateRequest` stays unchanged: update handles full type transitions and still needs the superset schema.

### Controller — [`app/api/v3/activities/controller.py`](app/api/v3/activities/controller.py)

Added four handler methods: `create_standard`, `create_resource_count`, `create_resource_details`, `create_transactional`. Each one translates its per-type body into a call to the single existing `create_activity(...)` service with fixed arguments:

| Handler | `type=` | `resource_mode=` | `resource_count=` | `resource=` | `status=` |
|---|---|---|---|---|---|
| `create_standard` | `"standard"` | `None` | `None` | `None` | from body (default `not_completed`) |
| `create_resource_count` | `"resource"` | `"count"` | from body | `None` | `None` |
| `create_resource_details` | `"resource"` | `"details"` | `None` | from body | `None` |
| `create_transactional` | `"transactional"` | `None` | `None` | `None` | `None` |

Keeping the service signature single-entry was deliberate: every downstream concern — the service's existing type × mode validator, the dependency-graph hierarchy check, the baseline→version propagation cascade, the audit trail (action `activity.create`) — still fires exactly once regardless of which split endpoint was hit.

### Routes — [`app/api/v3/activities/routes.py`](app/api/v3/activities/routes.py)

Removed the legacy `POST /{milestone_id}/activities/create`. Added four new routes with the same `ACTIVITIES_CREATE` permission guard.

Read / update / delete / restore endpoints are unchanged:
- `GET /milestones/{id}/activities` (list)
- `GET /activities/{id}` (read)
- `PATCH /activities/{id}` (update — full type-transition matrix still lives here)
- `DELETE /activities/{id}` (soft-delete + cascade)
- `POST /activities/{id}/restore` (admin restore)

Update is deliberately not split: editing an existing activity includes transitions (standard ↔ resource ↔ transactional, count ↔ details) and the current-state merge logic needs all fields available. Splitting would double the endpoint count without simplifying the caller's job.

## Test updates

**Updated call-sites (12)** in `tests/test_baseline_version_propagation.py`, `tests/test_dependencies.py`, and `tests/test_new_features.py` to use `.../activities/standard/create` or `.../activities/resource/details/create` as appropriate. Bodies dropped the `type` and `resourceMode` fields.

**Behavioral shift noted in `test_new_features.py::TestStandardActivityFields::test_transactional_has_no_status_field`** (was `test_transactional_rejects_status`): with the split, sending `status` to the transactional endpoint no longer returns 422 — Pydantic's default `extras='ignore'` silently discards the field, and the activity is created with `status=None`. The test now asserts the ignore-and-create-with-null behavior because the split makes the old rejection path structurally unreachable. Could be tightened to 422 by adding `extra="forbid"` to the schemas, but that's more invasive than the team asked for; deferred.

**New file — [`tests/test_activity_split.py`](tests/test_activity_split.py) (18 tests):**

- `TestStandardSplitEndpoint` (4): default status, accepts status, rejects invalid status, accepts dependsOn.
- `TestResourceCountSplitEndpoint` (3): happy path, resourceCount required, rejects zero.
- `TestResourceDetailsSplitEndpoint` (5): happy path, typeOfResourceId required, division required, resource block required, division='others' requires label.
- `TestTransactionalSplitEndpoint` (2): happy path, extra fields silently ignored.
- `TestLegacyCatchAllGone` (1): old `POST .../activities/create` returns 404/405.
- `TestSharedValidationsStillApply` (3): date floor vs project, end-before-start, baseline-only guard still fires on a version.

## Known follow-ups (scope-out)

- **Postman collection.** `PMIS_API_Collection.postman_collection.json` still contains 5 requests pointing at the old `.../activities/create`. Not updated here; one update pass can refresh those to the four new routes with focused payloads per type.
- **`extra="forbid"` on split schemas.** Would turn the "send status to transactional endpoint" case from 201-with-null to 422. Minor usability difference; skipped to keep this change narrowly scoped.
- **Dead `ActivityCreateRequest` class.** The old superset schema is no longer referenced by any route but is kept in `schemas.py` to avoid breaking any importer in external tooling. Safe to delete later.
- **Activity update endpoint.** Could also be split by type for consistency, but update has transition semantics that make a per-type surface awkward (you'd need a "change type" endpoint for state transitions). Left as single PATCH.
