## Item 1 — Status transitions catalog (table + GET endpoint + validator)

**Why.** The frontend needed a way to discover legal next-statuses for a project at any state without duplicating the rules in JavaScript. The transition graph also lived only in code (`_LEGAL_TRANSITIONS` / `ADMIN_ONLY_TRANSITIONS` / `VERSION_ONLY_TRANSITIONS` in `app/api/v3/projects/services/transitions.py`), so ops couldn't adjust a rule without a code release.

**What landed.**

- New table `project_status_transitions` ([model](app/infrastructure/db/models/project_status_transition.py)): `(id, from_status, to_status, requires_admin, version_only, active, description, created_at, updated_at)`. `from_status` is nullable — a NULL row marks the seed for the initial status (the only value allowed on a fresh create is `new`).
- Unique constraint on `(from_status, to_status)`; partial index for fast `(to_status, active)` lookup.
- New repository [`ProjectStatusTransitionRepository`](app/infrastructure/db/repositories/project_status_transition_repository.py) with `list_active`, `find_edge`, `known_to_statuses`.
- New endpoint `GET /api/v3/project_status_transitions` ([routes](app/api/v3/catalogs/routes.py)) — auth required, lists every active row.
- Seed in [`init_db`](app/infrastructure/db/session.py) that mirrors the in-code constants on every boot. Idempotent: skips edges that already exist.
- Validator wired into `app/api/v3/projects/services/create.py`: now queries the catalog for the set of accepted `to_status` values; falls back to the in-code list if the catalog is empty (which happens in fresh in-memory test DBs before the seed has run). On a typo like `inprogress`, returns `error_type="invalid_status"`.

**Tests.** `tests/test_catalogs_and_other_reason.py::TestStatusTransitionsCatalog` covers the GET endpoint, verifies seeded rows include the version-only flag, and checks both the reject-on-typo and accept-when-in-catalog paths.

## Item 2 — Project owners master (table + GET/POST endpoints + create-project validator)

**Why.** Today `project.owner` is a free-text login string with a check that the user exists. Governance wanted a curated whitelist of which staff are allowed to own projects, separate from "can create projects".

**What landed.**

- New table `project_owners` ([model](app/infrastructure/db/models/project_owner.py)): `(id, user_id FK users.id, display_name, active, created_at, updated_at)`. Unique on `user_id` — toggling `active` deactivates rather than hard-deleting.
- New repository [`ProjectOwnerRepository`](app/infrastructure/db/repositories/project_owner_repository.py) with `list_active_with_user`, `is_login_an_active_owner`, `add_by_user_id`, `deactivate_by_user_id`.
- New endpoints in [catalogs/routes.py](app/api/v3/catalogs/routes.py):
  - `GET  /api/v3/project_owners` — auth required; lists active owners with backing user info.
  - `POST /api/v3/project_owners/create` — admin (`PROJECTS_CREATE`); accepts `userId` *or* `login`, with optional `displayName`.
  - `DELETE /api/v3/project_owners/{user_id}` — admin; soft-toggles `active=False`.
- Seed in `init_db` adds the bootstrap admin so the master is never empty in normal boots.
- Validator in `create_project` service: when a project create supplies an `owner`, the service now also checks `is_login_an_active_owner(owner)`. Rejected with 422 if not in the whitelist. Skipped silently when the catalog is empty (covers fresh per-test in-memory DBs before any seed has run — keeps existing tests green).

**Tests.** `TestProjectOwnersCatalog` (4 cases): empty list, add by login, unknown login → 404, owner-not-in-whitelist rejection on project create, deactivation.

## Item 3 — Variable name sanitization

**Direct rename.** `vendorIds` → `vendors` on `MilestoneCreateRequest` / `MilestoneUpdateRequest`. The old aliases (`vendorIds` and `vendor_ids`) still work as input via Pydantic's `AliasChoices`, so old clients don't break; the canonical name is `vendors` and Swagger now shows that.

**Other naming inconsistencies surveyed (not yet renamed).** Listed here so the team can decide which to fix in a coordinated breaking-change pass:

| Module | API field | Issue | Suggested fix |
|---|---|---|---|
| `meetings` | `scheduled_at`, `duration_minutes` | snake_case in JSON; everything else is camelCase | `scheduledAt`, `durationMinutes` |
| `meeting_participants` | `user_id` | snake_case | `userId` |
| `users` schemas | `access_token`, `refresh_token` | snake_case (matches OAuth2 RFC, but inconsistent with the rest of our API) | keep — RFC-conformant, not a bug |
| `work_package_types` | `internal_name`, `is_builtin`, `is_active` | snake_case | `internalName`, `isBuiltin`, `isActive` |
| `work_packages` | `done_ratio` | snake_case | `doneRatio` |
| Project responses | `parent_id` (also `parentId`) | both shapes appear | settle on `parentId`; remove `parent_id` from the formatter |
| Many models | column `id` and inline relationship `id` (e.g. `vendors[].id` inside a project response) | "ID" name collisions in nested structures cause confusion | leave the *column* name alone but document the nesting (see the Excel reference); could also expose nested IDs as `vendorId`, `userId`, `taskId`, etc., depending on context |

The Postman collection + the Excel reference (consolidated_docs/PMIS_API_Endpoints.xlsx) already reflect milestone's `vendors` rename. Other renames are scoped-out — they're breaking and need a coordinated FE update.

## Item 4 — Task / subtask type inheritance from parent

**Why.** Tasks and subtasks always had a `type` field that mirrored the parent activity's type in 99% of real flows. Cluttered the wizard UI; allowed inconsistent values (a "transactional" task under a "standard" activity made no sense).

**What landed.**

- `TaskCreateRequest` and `SubtaskCreateRequest` no longer accept `type` in the request body ([tasks/schemas.py](app/api/v3/tasks/schemas.py), [subtasks/schemas.py](app/api/v3/subtasks/schemas.py)).
- The create services now derive `type` from `activity.type` / `task.type` and validate the resource-mode shape against the inherited type:
  - Inherited type ≠ `resource` → reject `resourceMode` / `resourceCount` / `resource` in the body.
  - Inherited type = `resource` → require `resourceMode`; same `count` vs `details` validation as on activities.
- **Non-destructive:** the column is preserved; PATCH still accepts `type` so a future cross-type-mapping endpoint can override the inheritance. Service-layer functions still take `type` as an optional kwarg defaulting to `None`, which means non-API callers (admin scripts, a future cross-type endpoint) can still pass an explicit type.

**Tests.** `tests/test_catalogs_and_other_reason.py::TestTaskSubtaskTypeInheritance` (5 cases): standard task inherits standard, resource-task requires mode, count-mode happy path, standard activity rejects resource fields on its task, subtask inherits from parent task.

## Item 5 — DDL generation script

[`scripts/generate_ddl.py`](scripts/generate_ddl.py) walks `Base.metadata` and emits two SQL files into `scripts/ddl/`:

- `schema_postgres.sql` — Postgres dialect, the canonical from-scratch schema for prod / disaster-recovery rebuilds.
- `schema_sqlite.sql` — SQLite dialect, matches what `create_all` produces in tests.

Both are deterministic (alphabetical table order, FK-correct creation order documented in a trailing comment block, no timestamps in the output). Re-running after a model change shows only the actual diff in `git status`.

Output: 27 tables, both files generated (~32 KB each). Alembic remains the migration runner; this script is a snapshot tool for review and rebuilds.

## Item 6 — `categoryOtherReason` field on project

**Why.** When users select `category='others'` they have to provide a free-text label (`categoryOther`). Governance asked for an additional reason text — *why* didn't this fit MSAP/MSIP/BSP — for category-curation review.

**What landed.**

- New column `projects.category_other_reason VARCHAR(1000)`, nullable. ([model](app/infrastructure/db/models/project.py)).
- Field on `ProjectCreateRequest`, `ProjectUpdateRequest`, `ProjectUpsertRequest` ([schemas](app/api/v3/projects/schemas.py)) — alias `categoryOtherReason` (camelCase) ↔ `category_other_reason` (snake_case).
- Service validation in both `create_project` and `upsert_project`: required (1–1000 chars) when `category == 'others'`; rejected when category is anything else. Symmetric with the existing `categoryOther` rule.
- Domain dataclass + `to_dict()` updated; `format_project_response()` exposes `categoryOtherReason`; repository `create()` and `upsert_by_id()` pass it through.
- Version cloning carries the field forward.

**Tests.** `TestCategoryOtherReason` (4 cases): require on `others`, accept with reason, reject reason without `others`, upsert path also requires reason.

**Existing tests updated.** `tests/test_new_features.py::TestCategoryOthers::test_others_accepts_category_other` was renamed to `test_others_accepts_category_other_with_reason` and updated to send the reason.

## Item 7 — dependsOn removal preserves history (verified, no code change needed)

The current dep schema (post-doc-12) is already history-preserving:

- The three `*_dependencies` tables have surrogate UUID `id` PKs plus `deleted_at`/`deleted_by` columns.
- Reads filter `deleted_at IS NULL`. Removal stamps `deleted_at`. Re-adding inserts a *fresh* row (new UUID id) — the partial unique index `(source, target) WHERE deleted_at IS NULL` allows the dead row + live row pair to coexist.
- The `project_audit_logs` table also receives entries for any baseline M/A change that propagates to a version (action `*.cascade_from_baseline`).

**Test added.** `tests/test_long_cycle_dependency.py::test_dep_history_preserved_after_replace` — adds an edge, clears it, re-adds it, then asserts the table contains exactly 1 deleted + 1 live row for that source/target pair, with different `id` values (proving the re-add was a fresh insert, not a `deleted_at` reset).

## Item 9 — `parent_id` semantics

`parent_id` appears on the `ProjectModel` only. Its role:

| Use case | Description | Allowed value |
|---|---|---|
| Sub-project / portfolio hierarchy | A project can have a parent project, modelling portfolio → programme → project. Mostly a UI concern; no business logic depends on it today. | UUID of any live project (not soft-deleted), self-referencing. NULL means top-level. |
| Initial seed by frontend | The wizard can pre-set a `parentId` on a fresh create so the new project shows up under the chosen parent in the listing. | Same — must reference a live project. |
| Versions vs baselines | `parent_id` is **independent** of the version graph. Versions use `version_of` and `baseline_id`; both point at the baseline this version forks from. A version's `parent_id` is **inherited from the source baseline at clone time** — see [`version.py:80`](app/api/v3/projects/services/version.py#L80). The version is *not* its baseline's `parent`. | Inherited from baseline.parent_id (NULL on top-level baselines). |

Service-side validation: `create_project` and `upsert_project` both call `repo.exists_by_id(parent_id)` and reject with 404 if the parent is missing or soft-deleted. There is no protection against cycles (`A.parent=B`, `B.parent=A`) — the wizard isn't expected to author cycles, but if a future bulk-import path opens that risk, a DFS guard analogous to the dep-cycle one would be needed.

**`parent_id` does not flow into the M/A/T/S tree.** Milestone/activity/task/subtask all have `project_id` (and respective parent FKs in the M→A→T→S chain) but no concept of `parent_id`. M/A/T/S parentage is structural and lives entirely in the chain's foreign keys.

## Migration notes

- The two new tables (`project_status_transitions`, `project_owners`) are picked up by `Base.metadata.create_all` for tests. **For Postgres** they need an Alembic migration before the next deploy — run `alembic revision --autogenerate -m "add status transitions and project owners catalogs"` against a Postgres clone of prod, review the generated diff, commit. `init_db`'s seed runs after the migration so the catalogs end up populated on first boot.
- `categoryOtherReason` adds one nullable column to `projects` — same Alembic flow, low-risk migration.
- Task/subtask `type` removal from the request body is backward-incompatible for callers that were sending `"type": ...`. Pydantic's default is `extras="ignore"`, so old callers continue to receive 201 and the value is silently dropped (the inherited type wins). No active failures, just a behavioural shift to be aware of.
