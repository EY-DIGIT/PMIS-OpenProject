## §1 — Alembic migration for the doc-15 schema (`e1882df`, kamal21)

### Why

Doc 15 added two new tables (`project_status_transitions`, `project_owners`) and one new column (`projects.category_other_reason`) on the model side. Local SQLite dev + tests use `Base.metadata.create_all`, so they picked them up automatically. Postgres production runs `alembic upgrade head` and was therefore frozen at the initial schema — booting the post-doc-15 code against Postgres would have 500'd on the new GET endpoints + crashed `init_db`'s seed code.

I had drafted a hand-written migration during the doc-15 verification pass. kamal21 generated his via `alembic revision --autogenerate` shortly after; both functionally identical. I deleted mine to keep a single linear Alembic head.

### What landed

`alembic/versions/f9b8dd81f7dd_add_catalog_tables_and_category_other_.py` (70 lines, autogenerated). Chains from `1272a77b9407 → f9b8dd81f7dd`.

`upgrade()`:
- `op.create_table('project_status_transitions', …)` with the unique edge constraint and four indexes.
- `op.create_table('project_owners', …)` with FK to `users(id)`, unique `user_id`, and two indexes.
- `op.add_column('projects', sa.Column('category_other_reason', sa.String(length=1000), nullable=True))`.

`downgrade()` reverses all three in correct order.

Also in this commit: a one-line tweak to [`app/core/config.py`](app/core/config.py) — `extra="ignore"` added to the Pydantic `Settings` `ConfigDict`. Lets the loader tolerate undeclared `.env` keys (the docker-compose env-vars commits had introduced a few that the Settings class doesn't enumerate). Robustness improvement, no downside.

### Validation

I rendered `alembic upgrade --sql head` offline against a fake Postgres URL and confirmed the chain is `1272a77b9407 → f9b8dd81f7dd` (single head), the SQL emits the three expected DDLs, and the final `UPDATE alembic_version SET version_num='f9b8dd81f7dd'` lands.

## §4 — `actual_start_date` column on projects (`45424ff`, kamal21)

### Why

Mirrors the existing `actual_end_date` field. Versions need to record when work actually began (separate from the planned `start_date`), per the design's Project Details panel. Baselines leave it NULL.

### What landed

**Schema** — `projects.actual_start_date DATETIME NULL` ([`app/infrastructure/db/models/project.py:69`](app/infrastructure/db/models/project.py#L69)). Alembic migration `…87c_add_actual_start_date_column_to_projects.py`.

**Plumbing** — touches the same files I touched for `categoryOtherReason`:
- Domain dataclass + `to_dict()` ([`app/domain/projects/project.py`](app/domain/projects/project.py)).
- Repository `create()` accepts `actual_start_date` ([`project_repository.py`](app/infrastructure/db/repositories/project_repository.py)).
- Project create / update / version services pass it through.
- Version clone resets it to NULL on the new version row (matches the `actual_end_date` pattern).
- Response formatter exposes `actualStartDate` ([`response.py`](app/core/response.py)).
- Update schema accepts the field ([`schemas.py`](app/api/v3/projects/schemas.py)).
- Editable-fields whitelist `EDITABLE_FIELDS_VERSION` adds `"actual_start_date"` so it's PATCH-able on versions only ([`transitions.py`](app/api/v3/projects/services/transitions.py)). Baselines reject it with the existing 422 `invalid_field` path.
- Audit `project_snapshot` includes it.

### Tests

No new tests added in this commit (relies on existing project PATCH coverage). The edit-whitelist enforcement is covered structurally by the existing `TestPublishedBaselineEditable` and version-update tests — sending `actualStartDate` to a baseline returns the expected 422.

## §6 — Comments & attachments feature (`50d9cbb`, kamal21) — the big one

**41 files, +3,991 / -169.** Largest single-feature commit since the M/A/T/S landing. Polymorphic comments + file-storage-backed attachments scoped to any milestone, activity, task, or subtask.

### New API surface

Comments:
- `POST   /api/v3/{milestones|activities|tasks|subtasks}/{target_id}/comments` — create a comment on the target.
- `GET    /api/v3/{milestones|activities|tasks|subtasks}/{target_id}/comments` — list comments under the target.
- `DELETE /api/v3/comments/{comment_id}` — soft-delete (author or admin).

Attachments:
- `POST   /api/v3/{milestones|activities|tasks|subtasks}/{target_id}/attachments` — multipart upload; persists file to disk + a row in `attachments`.
- `GET    /api/v3/{milestones|activities|tasks|subtasks}/{target_id}/attachments` — list rows under the target.
- `GET    /api/v3/attachments/{attachment_id}/download` — stream the file bytes back.
- `DELETE /api/v3/attachments/{attachment_id}` — soft-delete row + best-effort `unlink()` of the file on disk.

Both modules wired into [`app/api/router.py`](app/api/router.py) via `comments_router` and `attachments_router`.

### New tables

- `comments` — `id`, `target_type` (`milestone | activity | task | subtask`), `target_id`, `body`, `author_user_id`, soft-delete + audit timestamps. Polymorphic via `(target_type, target_id)` lookup; no FK because the FK target table varies per row.
- `attachments` — `id`, `target_type`, `target_id`, `file_path`, `original_filename`, `content_type`, `byte_size`, `uploader_user_id`, soft-delete + audit timestamps. The `file_path` is relative to `ATTACHMENTS_STORAGE_BASE_PATH` so the row stays portable across mount points.

Alembic migration `4825a33f9ed3_add_comments_and_attachments_tables.py` creates both. Chains as `f9b8dd81f7dd → <actual_start_date> → 4825a33f9ed3`.

### File-storage subsystem

[`app/infrastructure/storage/file_storage.py`](app/infrastructure/storage/file_storage.py) (267 lines). Storage-agnostic API: `save(target, original_filename, file_obj) → file_path`, `open_for_read(file_path)`, `unlink(file_path)`, `health()`. Production points the env var at an NFS mount; dev falls back to `./local_uploads`. The `health()` probe is surfaced via the new `/health` endpoint so support can verify the mount.

### New env vars (10)

Added to `.env.example`. Functionally required: only `ATTACHMENTS_STORAGE_BASE_PATH`. The rest are tuning knobs (max bytes, allowed extensions, retention, on-unavailable behaviour) or informational (NFS server / export, surfaced in `/health` for verification).

### New permissions

25 lines added to [`app/core/rbac.py`](app/core/rbac.py): `COMMENTS_CREATE`, `COMMENTS_READ`, `COMMENTS_DELETE`, `ATTACHMENTS_CREATE`, `ATTACHMENTS_READ`, `ATTACHMENTS_DOWNLOAD`, `ATTACHMENTS_DELETE`, with sensible defaults per role.

### Failure-mode design

If the NFS mount is missing on the server, the app boots, schema applies, and:
- Comments without files: still work.
- Comments **with** files + standalone uploads: HTTP 503 `error_type: storage_unavailable`.
- Downloads of any file already uploaded: also 503 if the mount is down.

No data loss, no crash, only attachment-related endpoints degrade until the mount is fixed.

### Tests

- `tests/test_comments.py` (271 lines, 14 cases) — create / list / delete on each of the four target types, soft-delete preservation, RBAC, target-not-found 404s.
- `tests/test_attachments.py` (222 lines, 14 cases) — upload happy path with a tmp file, list, download, delete (file unlinks), oversize rejection, content-type filter, storage-unavailable 503, soft-delete + retention.

### DevOps action required on the server

See [`Kamal_docs/DEPLOYMENT_NOTES.md`](../Kamal_docs/DEPLOYMENT_NOTES.md) §"2026-04-27 — Comments & Attachments feature" for the exact NFS-mount + env-var + docker-compose volume-mount steps. Migration auto-applies on boot; everything else is one-time DevOps.

## Cumulative effect on what you have to do

### Local

```bash
.venv/Scripts/python.exe -m pip install -r requirements.txt   # no new deps, but venv refresh
rm pmis.db                                                      # let create_all rebuild fresh
uvicorn app.main:app --reload
```

If you'll exercise file uploads, set `ATTACHMENTS_STORAGE_BASE_PATH=$PWD/local_uploads` in your `.env`. Otherwise the default fallback applies.

### Server

Three steps, no data loss (everything additive):

```bash
git pull --ff-only
pip install -r requirements.txt
alembic upgrade head           # walks 1272a77b9407 → f9b8dd81f7dd → <actual_start_date> → 4825a33f9ed3
```

Then add the `ATTACHMENTS_*` block to the server's `.env` (only `ATTACHMENTS_STORAGE_BASE_PATH` is functionally required — see [`Kamal_docs/DEPLOYMENT_NOTES.md`](../Kamal_docs/DEPLOYMENT_NOTES.md) for the full list, NFS mount steps, and docker-compose bind-mount line). Restart the monolith. `init_db` re-runs `alembic upgrade head` automatically (idempotent).

`/health` should report `storage.healthy: true` once the mount is in place.
