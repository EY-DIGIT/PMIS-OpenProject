## §1 — Search Project sort: newest first

### Why

Per product rule: "the latest created project should come at the top of the project; sorting will be in descending order of date/time created when returned from backend." The Search Project table reads top-down, so row 0 should be the most recently created project.

### What changed

[`app/api/v3/projects/services/list.py`](app/api/v3/projects/services/list.py) — added `ORDER BY created_at DESC, id DESC` to the list query, before `OFFSET / LIMIT`. The `id DESC` tie-break keeps pagination stable when two rows share a `created_at` timestamp (possible on bulk seeds).

```python
query = query.order_by(
    ProjectModel.created_at.desc(),
    ProjectModel.id.desc(),
)
```

No new query parameter — the sort is the **default** for `GET /projects`. Same ordering reused by the new `GET /projects/all` endpoint (see §6).

## §2 — Inclusive date validation: `end_date == start_date` allowed

### Why

Per user report: *"If I give dates in the expected start and end dates and same dates (either or) in the milestone or activity or anything, it is showing error and not letting us choose. The dates should be in between including the extreme dates, not excluding the extreme dates."*

The milestone / activity / task / subtask date-floor checks in [`app/shared/date_rules.py`](app/shared/date_rules.py) were already inclusive (use `<` strictly less-than, so equal-to-parent is allowed). But the **project's own** `end_date > start_date` check was strict (`<=`) in seven places, and the same applied to work-packages. Single-day projects / milestones / activities were therefore being rejected.

### What changed

Eight locations switched from `<=` to `<`. The error message also changes from *"end_date must be after start_date"* to *"end_date cannot be before start_date"* — the new wording matches the new (inclusive) semantics.

| File | Where |
|---|---|
| [`app/api/v3/projects/schemas.py`](app/api/v3/projects/schemas.py) | Pydantic `validate_end_date_after_start_date` — three schemas (Create, Update, Upsert) |
| [`app/api/v3/projects/services/create.py`](app/api/v3/projects/services/create.py) | service-level guard |
| [`app/api/v3/projects/services/update.py`](app/api/v3/projects/services/update.py) | service-level guard |
| [`app/api/v3/projects/services/upsert.py`](app/api/v3/projects/services/upsert.py) | service-level guard |
| [`app/api/v3/work_packages/schemas.py`](app/api/v3/work_packages/schemas.py) | Pydantic `validate_end_after_start` |
| [`app/api/v3/work_packages/services/create.py`](app/api/v3/work_packages/services/create.py) | service-level guard |
| [`app/api/v3/work_packages/services/update.py`](app/api/v3/work_packages/services/update.py) | service-level guard |

The milestone / activity / task / subtask path was unchanged because [`validate_entity_dates`](app/shared/date_rules.py:42) already uses `<` for both the parent-floor check (`entity_start < parent_start`) and the entity end-after-start check (`entity_end < entity_start`). So `milestone.start_date == project.start_date` and `milestone.end_date == milestone.start_date` are already accepted; the regression was purely on the project / work-package layer above them.

### Future / upper-bound check

`validate_entity_dates` still has **no upper-bound check** against `parent.end_date` or `project.end_date` — by explicit design, since real projects overrun and end dates are allowed to slip arbitrarily. If a future product call reverses this and a milestone/activity end date should be capped to its parent's end date, the change goes in `validate_entity_dates`; nothing in this batch precludes it.

## §4 — Vendor soft-delete + restore

### Why

Per product rule: *"After deleting a Vendor, it should be soft deleted in the backend and the status will be inactive. The project mappings and everything will be associated with this vendor but will not show in the frontend. Later, if the vendor is undeleted, it should retain all its associated projects and information."*

Pre-change the vendor model only had an `active` flag. There was no DELETE endpoint at all — the only way to take a vendor out of circulation was a PATCH that flipped `active=False`, which was reversible but didn't carry an audit trail (who/when), and didn't compose with the new "for closed/completed projects, don't show them on a restored vendor" rule.

### What changed

#### Schema

[`app/infrastructure/db/models/vendor.py`](app/infrastructure/db/models/vendor.py) — two new columns:

- `deleted_at DateTime, nullable=True, index=True`
- `deleted_by Integer, FK→users.id, nullable=True`

Plus a new index on `created_at` (already covered in §3) and an existing index on `(active, name)` is left in place.

[`app/domain/vendors/vendor.py`](app/domain/vendors/vendor.py) — domain dataclass extended with `deleted_at` + `deleted_by` (both default `None`). `to_dict()` now exposes them (snake_case keys).

#### Repository

[`app/infrastructure/db/repositories/vendor_repository.py`](app/infrastructure/db/repositories/vendor_repository.py) — three behavioral changes:

1. `list_active()` — now filters `deleted_at IS NULL` in addition to `active=True`. Soft-deleted vendors disappear from the catalog.
2. `existing_active_ids(ids)` — same filter added. A soft-deleted vendor is treated as if it doesn't exist for any new project / milestone attachment, so the picker can't accidentally re-attach a deleted vendor.
3. New methods:
   - `get_by_id(vendor_id, include_deleted=False)` — list reads use the default; the restore route passes `True`.
   - `get_model_by_id(vendor_id, include_deleted=False)` — returns the raw `VendorModel` for write paths that need to mutate it (delete / restore / update).
   - `soft_delete(vendor_id, *, actor_id)` — stamps `deleted_at` / `deleted_by` and flips `active=False`. Idempotent on already-deleted rows. **Does NOT touch `project_vendors` / `milestone_vendors` mapping rows** — the whole point of soft-delete is to preserve the historical associations.
   - `restore(vendor_id)` — clears `deleted_at` / `deleted_by`, sets `active=True`. Idempotent on already-live rows.

The duplicate-name check in `get_by_name` learned `include_deleted` too, so the create endpoint can refuse to create a fresh vendor when a soft-deleted vendor with the same name already exists (DB has a UNIQUE constraint on `name`; the alternative would be a 500 from the DB, which is uglier than a 409 with a hint to restore).

#### Routes

[`app/api/v3/vendors/routes.py`](app/api/v3/vendors/routes.py) — route surface expanded from 3 endpoints (list, create, update) to 6:

| Method | Path | Permission | Purpose |
|---|---|---|---|
| `GET` | `/vendors` | `vendors:read` | Live vendors, newest first, **each with its mapped projects** (see §7) |
| `POST` | `/vendors/create` | `vendors:manage` | Create. Refuses if a soft-deleted vendor of the same name exists, with a hint to restore it |
| `PATCH` | `/vendors/{vendor_id}` | `vendors:manage` | Edit name / description / active |
| `DELETE` | `/vendors/{vendor_id}` | `vendors:manage` | Soft-delete. 404 on already-deleted; 204 on success. Mappings preserved |
| `POST` | `/vendors/{vendor_id}/restore` | `vendors:manage` | Undelete. Idempotent — calling on a live vendor returns the current snapshot rather than 409 |
| `GET` | `/vendors/{vendor_id}/projects` | `vendors:read` | Projects mapped to this vendor, **excluding closed/completed and soft-deleted projects** |

The "exclude closed/completed" rule on `/vendors/{id}/projects` (and on the embedded `projects` list in `GET /vendors` — see §7) is the implementation of the user's last sentence in the spec: *"for projects that are closed or completed, it should update and not show those projects anymore."* This is implemented as a **list-time filter** rather than a destructive cleanup at restore time. Mappings are preserved on disk for audit; the FE simply never sees closed/completed entries. If product later wants destructive cleanup at restore, the change is one query inside `restore()`.

`_HIDDEN_PROJECT_STATUSES = {"closed", "completed"}` is the single source of truth for the filter — `completed` is included today as a forward-compat marker even though the project lifecycle (`PROJECT_STATUS_CHOICES`) doesn't yet recognise it. If `completed` becomes a real status, the filter just starts firing.

### DB migration

See "Alembic migration" section at the end. The migration is additive only.

### Failure mode if DevOps skips the migration

App boots fine (Postgres path runs `alembic upgrade head` automatically; SQLite path heals via the drift block in `init_db`). If both paths are bypassed somehow, every vendor read raises `column vendors.deleted_at does not exist`. The fix is a one-liner: `alembic upgrade head` (or just restart the app, since `init_db` does this on boot).

## §5 — Status-transition validation now consults the catalog table at runtime

### Why

Doc 15 introduced the `project_status_transitions` table as a master catalog. But until this batch, the table was only used for two things:

1. The `GET /project_status_transitions` endpoint (so the FE can build dropdowns).
2. `known_to_statuses()` — string validation of the `status` value on create.

The actual edge / admin / version-only gating in `assert_transition_allowed` was still reading from the in-code `_LEGAL_TRANSITIONS`, `ADMIN_ONLY_TRANSITIONS`, `VERSION_ONLY_TRANSITIONS` constants. So ops could read the catalog but couldn't change behaviour by editing it — defeating the point of having a table.

### What changed

[`app/api/v3/projects/services/transitions.py`](app/api/v3/projects/services/transitions.py:138) — `assert_transition_allowed` now takes an optional `db: Session` parameter. When supplied:

1. Looks up the edge via `ProjectStatusTransitionRepository.find_edge(from_status, to_status)`.
2. If a row exists, uses `row.requires_admin` + `row.version_only` to gate the transition.
3. If no row exists (or `db` was `None`), falls back to the in-code constants.

The fallback is essential: tests use `Base.metadata.create_all` and **don't** call `init_db`, so the catalog seed never runs. `find_edge` returns `None` for everything in tests, and the in-code constants take over — exactly the previous behaviour, so the existing test suite continues to pass.

The three call sites — [`publish.py`](app/api/v3/projects/services/publish.py), [`close.py`](app/api/v3/projects/services/close.py), [`suspend.py`](app/api/v3/projects/services/suspend.py) — all gained `db=db` on their `assert_transition_allowed(...)` call. No other behavioural change to those services.

### Audit answer to the user's question

> *"currently the status of projects etc. are managed with transition tables which store current state and all possible states which are legal. I want you to check the project transition api and its functioning to see if it correctly implements this."*

**Verdict on the audit:** the table existed but was decorative — gating was still in code. **After this change**, the table is now the runtime source of truth for `requires_admin` / `version_only`, with in-code constants as a fallback for unseeded environments. Ops can now toggle a transition rule (e.g. flip `(draft → published).requires_admin = False` for a hackathon) by updating the row, no code change required. The seed in [`init_db`](app/infrastructure/db/session.py:485) keeps the table in sync with the in-code constants on every boot, so adding new edges in code still works the way it always did.

## §6 — Project delete disconnects mappings + new `GET /projects/all`

### Why

Per product rule:
- *"If I try to Remove or Delete any Project from the Search Project, then it marks project as deleted in db and does not show it in the response. Status should change and any associated vendor or user will be disconnected from the deleted project."*
- *"Create two apis: One to display all projects, one to display only the ones which are not deleted."*

Pre-change, project delete did soft-delete + cascade to M/A/T/S subtree, but:
- The project's `status` field was left at whatever it was (e.g. `published`) — confusing on the include-deleted view.
- The `project_vendors` and `project_members` rows were left in place — meaning a deleted project was still "associated" with its vendors / members from the perspective of any future query that joined those tables.
- There was no way to see deleted projects via the API at all.

### What changed

#### Delete service

[`app/api/v3/projects/services/delete.py`](app/api/v3/projects/services/delete.py) — three new behaviors layered onto the existing cascade:

1. **Status flip to `closed`.** The project (and each cascaded version) gets its `status` updated to `STATUS_CLOSED` so post-delete reads through `GET /projects/all` show a terminal status, not a stale in-flight one.
2. **Mapping disconnect.** New private helper `_disconnect_associations(db, project_id)` deletes all `project_vendors` and `project_members` rows for the project. Audit history of the project itself preserves the snapshot of what was attached at delete time, so we don't lose the trail.
3. **Order matters.** The status flip happens **after** `soft_delete` (which stamps `deleted_at`), not before. Reason: the partial unique index `ux_projects_active_version_per_baseline` defines "active" as `is_version AND status != 'suspended' AND deleted_at IS NULL`. Stamping status to `closed` before the soft-delete would temporarily turn an already-suspended sibling version into "active" (since `closed != suspended`) and collide with the live target version on the index. Soft-delete first → row falls out of the partial index (`deleted_at IS NOT NULL`) → status update is then safe. The `test_delete_baseline_cascades_to_versions` test caught this ordering bug on the first run.
4. `repo.update(..., include_deleted=True, ...)` is used for the post-soft-delete status flip, since the repo's `update()` method otherwise filters out soft-deleted rows.

#### List service + routes

[`app/api/v3/projects/services/list.py`](app/api/v3/projects/services/list.py) — `list_projects()` learned an `include_deleted: bool = False` parameter. Default `False` keeps the behaviour identical to before. `True` removes the `deleted_at IS NULL` filter from the query.

[`app/api/v3/projects/schemas.py`](app/api/v3/projects/schemas.py) — `ProjectListQuery` gained `includeDeleted: bool = Field(False)`.

[`app/api/v3/projects/routes.py`](app/api/v3/projects/routes.py) — two endpoints now:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/projects` | **Live only.** Backs the Search Project view. Pins `includeDeleted=False` |
| `GET` | `/projects/all` | **Includes soft-deleted.** Each row carries a `deletedAt` field; NULL for live projects, populated for deleted ones. Same `created_at DESC` newest-first sort as the live view |

Route registration order matters in FastAPI — `/all` is registered **before** `/{project_uuid}` so the static path wins over the dynamic catch-all.

[`app/api/v3/projects/controller.py`](app/api/v3/projects/controller.py) — threads `query.includeDeleted` through to the service.

[`app/core/response.py`](app/core/response.py) — `format_project_response` now emits `deletedAt` and `deletedBy` (the project domain entity has carried these for a while; just was never surfaced).

### Behavior summary

- `DELETE /projects/{id}` on a live project: 204, project soft-deleted, status now `closed`, `project_vendors` + `project_members` rows for this project removed, M/A/T/S subtree cascaded, audit row written.
- `DELETE /projects/{id}` on a baseline with live versions: same as above, plus each live version (regardless of status — including `suspended`) gets the same treatment.
- `GET /projects` after delete: deleted project doesn't appear.
- `GET /projects/all` after delete: deleted project appears with `status: "closed"`, `deletedAt` populated, no vendors / members linked (the old associations were removed in step 2 above).

## §7 — `GET /vendors` includes each vendor's mapped projects

### Why

Per user request, after the §3–§4 batch was implemented: *"in the vendor get api, displaying by date added should already be taken care of. Also return the projects that the vendor is mapped to. return project code and project name for each project in the list."*

The "displaying by date added" half is already done in §3. This §7 covers the second half: each vendor in the list response carries a `projects` array.

### What changed

[`app/api/v3/vendors/routes.py`](app/api/v3/vendors/routes.py) — two surface changes:

1. New batched helper `_projects_by_vendor(db, vendor_ids)` — one SQL query joins `project_vendors → projects`, filters `deleted_at IS NULL` and `status NOT IN _HIDDEN_PROJECT_STATUSES`, and returns `{vendor_id: [{id, projectCode, name}, ...]}`. Single query for N vendors — no N+1.
2. `_vendor_to_response(v, projects=None)` — now takes an optional `projects` list. Defaults to `[]` so create-vendor (which can't have any associations yet) doesn't need to call `_projects_by_vendor` at all. Update + restore + list all pass through the actual mapped projects.

The shape per project entry in the array:

```json
{ "id": "<uuid>", "projectCode": "UIDAI-PR…", "name": "Site rollout" }
```

Same exclusion rule as `/vendors/{id}/projects` — closed / completed / soft-deleted projects don't appear. So restoring a vendor doesn't suddenly resurrect a list of finished projects in the FE — it brings back the vendor with only its currently-relevant projects visible, which matches the spec's intent on "for projects that are closed or completed, it should update and not show those projects anymore."

### Why a batched helper, not a per-vendor call

A naive `for v in vendors: list_projects(v.id)` would issue N+1 queries (1 list + N per-vendor). For an org with 200 vendors this is 201 round-trips. The batched join is one query, indexed by `(project_vendors.vendor_id IN (...))`. List-endpoint latency stays O(1) regardless of vendor count.

## §8 — Alembic migration + SQLite drift handler

### `alembic/versions/7c4a91d8e3f0_add_vendor_soft_delete_columns.py`

New migration. Chains as `4825a33f9ed3 → 7c4a91d8e3f0`.

`upgrade()`:
- `op.add_column('vendors', sa.Column('deleted_at', sa.DateTime(), nullable=True))`
- `op.add_column('vendors', sa.Column('deleted_by', sa.Integer(), nullable=True))`
- `op.create_foreign_key('fk_vendors_deleted_by_users', 'vendors', 'users', ['deleted_by'], ['id'])`
- `op.create_index('idx_vendors_deleted_at', 'vendors', ['deleted_at'])`
- `op.create_index('idx_vendors_created_at', 'vendors', ['created_at'])`

`downgrade()` reverses in correct order. Additive only — safe to roll back with `alembic downgrade -1` if needed; no data loss because the new columns are nullable and the indexes carry no data.

`alembic heads` confirms a single linear chain:

```
<base> → 1272a77b9407 → f9b8dd81f7dd → eb3b19c7487c → 4825a33f9ed3 → 7c4a91d8e3f0 (head)
```

### SQLite drift handler

[`app/infrastructure/db/session.py`](app/infrastructure/db/session.py) — new block in the SQLite drift section, parallel to the existing project-columns / milestones-columns / activities-columns blocks:

```python
# vendors.deleted_at + vendors.deleted_by
res = conn.execute(text("PRAGMA table_info('vendors')"))
vcols = {r[1] for r in res.fetchall()}
for col, stmt in (
    ("deleted_at", "ALTER TABLE vendors ADD COLUMN deleted_at DATETIME"),
    ("deleted_by", "ALTER TABLE vendors ADD COLUMN deleted_by INTEGER REFERENCES users(id)"),
):
    if col not in vcols:
        conn.execute(text(stmt))
conn.execute(text("CREATE INDEX IF NOT EXISTS idx_vendors_deleted_at ON vendors(deleted_at)"))
conn.execute(text("CREATE INDEX IF NOT EXISTS idx_vendors_created_at ON vendors(created_at)"))
```

Idempotent. Catches legacy on-disk dev `pmis.db` files that predate the soft-delete feature.
