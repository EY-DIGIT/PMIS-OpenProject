# FE↔BE alignment audit — Project Management mockup vs backend v3 surface

## Sources
- Frontend mockup: `C:\Users\CL725CJ\Downloads\Project Management (1).html` (5,222 lines, body markup + inline `<script>` only; CSS skipped).
- Backend: `app/api/v3/` as of git HEAD `5f79df6`.
- Date: 2026-04-28.

## Summary
The mockup is a self-contained, in-memory prototype: every "save" lands in `demoProjects` rather than calling an API, so there is **no actual wire contract to compare** — every UI element implicitly needs an endpoint. Coverage is broadly there for the M/A/T/S surface and the project lifecycle, but there are **15 schema/vocabulary mismatches**, **3 hard validation drifts**, **2 missing endpoints** (project audit log, project tree-aware progress KPIs), and a noticeable **gap in vocabulary alignment** — the UI ships hard-coded English/uppercase labels (`'PUBLISHED'`, `'Not Completed'`, `'TMD1'`, `'Standard Type'`, etc.) while the backend uses lowercase enum codes (`'published'`, `'not_completed'`, `'tmd1'`, `'standard'`). Five backend endpoints are present with **no UI counterpart yet** (catalogs, attachments, comments, meetings, vendor restore). The mockup also assumes flat resource fields per node, while the backend exposes a typed activity create surface split into four endpoints — the FE will need a discriminator before it can call the right one.

**Notes:** Backend exposes the data, but the UI does client-side substring search across multiple fields with no API equivalent — there is no `q=` / `search=` query param on `GET /projects`. ## Missing backend support
Listed roughly in product-importance order:

1. **Audit log read endpoint** — UI tracks `auditLogs` for every project mutation (`addAudit`, line 2076) but has no display surface yet AND the backend has no `GET /projects/{id}/audit` route. If the audit page is on the roadmap, this is a real gap.
2. **Track Progress KPIs** — the entire `/track` page (HTML 3658+) is computed in JS. No `GET /projects/{id}/progress` or per-node progress aggregation exists. The FE can build it on top of `GET /tree`, but the classification thresholds (`delayed = today > endDate && !completed`) are JS-only.
3. **Project search query** — `GET /projects` has no `q=`/`search=` param; the UI does substring search across 11 fields client-side (line 2231). Won't scale past a few thousand projects.
4. **Project restore** — backend has `POST /vendors/{id}/restore` and a soft-delete model on projects, but no `POST /projects/{id}/restore`. UI doesn't expose restore either.
5. **`statusExplanation` UI input** — backend accepts and stores it on every create/update; the mockup never collects it.
6. **`categoryOtherReason` UI input** — backend now requires it when `category=='others'` (per change 15). UI's "Specify Category" textbox only fills `categoryOther`, not `categoryOtherReason`. Submission with `Others` will 422.
7. **Project / vendor / role / user / resource-type management screens** — sidebar has placeholders, no implementation.
8. **Login / logout flow** — no UI screens.

## Validation drift

| Field | UI rule | BE rule | Severity |
|---|---|---|---|
| Project `endDate` vs `startDate` | UI rejects `end < start` (line 2451) — allows `end == start` | BE rejects only `end < start` (inclusive, per change 17) | aligned ✓ |
| Project `startDate` / `endDate` future-only | UI does NOT enforce future dates (allows past dates in seed data) | BE `validate_dates_in_future` raises if date is in the past or now (`projects/schemas.py` line 86–94) | medium — UI will let users submit past dates that BE will 422. Note: `2026-04-01` seed dates are in the past relative to today's `2026-04-28`. |
| Milestone / activity / task / subtask `endDate` vs `startDate` | UI rejects `end < start` (line 4929) — allows `end == start` | BE rejects only `end < start` (inclusive, per change 17) | aligned ✓ |
| Parent-bounded date range (M inside project, A inside M, T inside A, S inside T) | UI enforces (line 4937, `getParentDateBounds`) | BE does NOT enforce parent-bounded dates on M/A/T/S create or update | medium — UI gives a tighter guarantee than BE. A direct API caller can create out-of-range children. |
| Comment file size | UI rejects per-file > 25 MB (line 4770) | BE does not advertise a file-size cap in the comments/attachments routes | medium — large uploads will succeed via API even if rejected via UI. |
| Required: project `Project Name`, `Owner`, `Expected Start Date`, `Expected End Date`, `Category` | UI requires all five (line 3603) | BE requires only `name`; `owner`, `start_date`, `end_date`, `category` are all `Optional` on `ProjectCreateRequest`/`ProjectUpsertRequest` | medium — BE is much more permissive; UI promise of mandatory fields isn't backed up. |
| Required: M/A/T/S `Name`, `startDate`, `endDate` | UI requires all three (line 4926) | BE requires all three on M; on A/T/S they're also required | aligned ✓ |
| `dependsOn` not-completed gate | UI blocks "mark Completed" if any dep is not effectively completed (line 4994) | BE doesn't enforce this on M/A/T/S — `status` can be set to `completed` regardless of dependency state | medium — pure FE rule. |
| Description max length | UI: `maxlength=5000` (lines 2391, 4670) | BE: `max_length=5000` on `description` everywhere | aligned ✓ |
| Project name max length | UI: no explicit cap | BE: `max_length=255` | low — long project names will 422. |
| Phrase-typed delete confirmation | UI requires the user to type a random phrase (line 2543) | BE has no equivalent — `DELETE /projects/{id}` is a one-shot call | aligned by design (UX gate, not API). |
| Vendor on milestone: must be in project's vendor list | Implicit on UI (vendor dropdown is built from `project.vendors`, line 4497) | BE's milestone create service enforces "each vendor id MUST also appear in the project's vendor list" (per `MilestoneCreateRequest` docstring) | aligned ✓ |

## Backend endpoints with no UI counterpart

These are real BE endpoints that the mockup doesn't yet exercise. Not bugs — gaps.

- `GET /api/v3/projects/all` — admin view including soft-deleted projects.
- `POST /api/v3/projects/{id}/suspend` — UI has no Suspend action (would only apply to versions).
- `POST /api/v3/projects/{id}/close` — UI's "Remove" calls DELETE; close-with-reason isn't surfaced.
- `GET /api/v3/projects/{id}/tree` — perfect fit for the Milestone Configuration grid; UI builds the tree from in-memory data instead.
- `GET /api/v3/project_status_transitions` — would let UI auto-generate a state-aware status dropdown rather than hard-coding labels.
- `GET /api/v3/project_owners`, `POST /api/v3/project_owners/create`, `DELETE /api/v3/project_owners/{user_id}` — UI hard-codes owner names (`'Admin', 'Supervisor', 'Manager'` in seed data).
- `GET /api/v3/vendors` (with embedded `projects` per change 17), `POST /api/v3/vendors/create`, `PATCH /api/v3/vendors/{id}`, `DELETE /api/v3/vendors/{id}` (NEW), `POST /api/v3/vendors/{id}/restore` (NEW), `GET /api/v3/vendors/{id}/projects` (NEW) — entire vendor-management UI is missing; sidebar has the placeholder.
- `GET /api/v3/resource_types`, `POST /api/v3/resource_types/create` — picker uses the hard-coded code list; admin-curation UI absent.
- `GET /api/v3/work_package_types`, plus full CRUD — no UI.
- `GET /api/v3/users`, `GET/PATCH/DELETE /api/v3/users/{id}`, password update — sidebar has User Management placeholder; no implementation.
- `GET /api/v3/roles`, full CRUD — no UI.
- `POST/GET/PATCH/DELETE /api/v3/projects/{id}/meetings`, plus participants and agenda items — entire meetings surface unused.
- `POST/GET/DELETE /api/v3/projects/{id}/memberships` (and `PATCH/DELETE /memberships/{id}`) — project members UI not in mockup.
- Comments delete + attachments download/delete — UI shows comment items but has no remove button or download link.
- `POST /api/v3/users/login`, `/logout`, `/introspect`, `/me` — no login screen.

## Recommendations
The biggest single win is **wiring the UI vocabulary to the BE catalogs**: stop hard-coding statuses, categories, divisions, resource types, vendors, and owners — call `GET /project_status_transitions`, `GET /resource_types`, `GET /vendors`, and `GET /project_owners` once on app load and drive every dropdown from those responses. That alone fixes most of the schema-mismatch table (statuses, categories, divisions, resource codes, vendor names). Second priority: **migrate from in-memory `demoProjects` to actual API calls**, starting with `PUT /projects/{uuid}` for the wizard (the BE was explicitly built to match this pattern) and `GET /projects/{uuid}/tree` for the configuration grid. Third: **collect `categoryOtherReason` and `divisionOther`** so the "Others" path doesn't 422, and add a `divisionOther` UI input that appears when the user picks `Others`. Fourth, low-priority but cheap: **add a `q=` search param to `GET /projects`** so the search box can move off client-side filtering.
