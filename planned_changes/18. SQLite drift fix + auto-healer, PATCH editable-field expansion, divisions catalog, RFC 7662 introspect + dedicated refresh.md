## §0 — SQLite drift bug fix + generic auto-healer

### The bug

User report:
```
GET /api/v3/projects → 500
"Failed to list projects: (sqlite3.OperationalError) no such column: projects.category_other_reason"
```

Root cause: the SQLite drift handler in `init_db` (which keeps legacy on-disk dev `pmis.db` files in sync as new model columns land) was hand-maintained and had not been updated to add two columns introduced in earlier migrations:

- `projects.category_other_reason` — added in doc-15 catalogs migration `f9b8dd81f7dd`.
- `projects.actual_start_date` — added in doc-16 migration `eb3b19c7487c`.

Postgres deployments were unaffected because Alembic ran the migrations correctly. The user's local Windows dev backend defaults to `DATABASE_URL=sqlite:///./pmis.db` (per `app/core/config.py:30`), so the local `/projects` route hit the stale schema and 500'd.

### What changed

#### Targeted: explicit ALTER for the two missing columns

[`app/infrastructure/db/session.py`](app/infrastructure/db/session.py) — added `category_other_reason` (VARCHAR(1000), nullable) and `actual_start_date` (DATETIME, nullable) to the `project_column_ddl` list inside the existing SQLite drift block. Idempotent: only added when missing from `PRAGMA table_info('projects')`.

#### Defensive: generic `_heal_sqlite_column_drift` pass

New module-level helper in [`app/infrastructure/db/session.py`](app/infrastructure/db/session.py):

- Iterates `Base.metadata.sorted_tables`.
- For each table that already exists, compares model columns against `PRAGMA table_info`.
- For any nullable model column missing from the DB, generates the dialect-specific DDL via `CreateColumn(column).compile(dialect=dialect)` and runs `ALTER TABLE … ADD COLUMN`.
- NOT NULL columns without a default are SKIPPED (SQLite can't add them without a default value) and logged as a `WARNING` so devs notice and add an explicit ALTER block above the auto-healer.
- Returns the list of `table.column` strings that were added, for logs / tests.

Wired in after the existing explicit-DDL blocks but before any post-create-all logic. Order:

1. `Base.metadata.create_all(bind=engine)` — creates new tables.
2. Existing explicit ALTER blocks — handles partial / hand-tuned drift.
3. `_heal_legacy_dep_tables()` — drops + rebuilds dep tables on schema-v1 → v2 migration.
4. **NEW:** `_heal_sqlite_column_drift()` — catches any remaining column drift.
5. Bootstrap admin / catalog seeds.

Audited the local DB after the change — only the two `vendors` columns added in doc-17 (`deleted_at`, `deleted_by`) were missing; both are already covered by the explicit drift block from doc 17. The auto-healer found no extra gaps.

### Why both targeted + generic

- The explicit list is fast on every boot (one PRAGMA + one ALTER per known column) and easy for devs to trace when reading the file.
- The generic auto-healer is the safety net for future drops where the explicit list isn't updated. Catches the bug class permanently without imposing maintenance burden.

### How to recover from the user-reported state

```bash
# Stop the app.
# (No data migration needed — the column will be added with NULL values.)
# Restart the app — init_db's drift handler adds the column on boot.
```

After this batch lands, restarting the app heals the schema; the 500 goes away. No manual ALTER required.

## §2 — `GET /api/v3/divisions` catalog endpoint

### Why

User report: *"there is a field called division which is used for adding information in projects. this is being retrieved from db. There is however no specific endpoint to query the db to fetch this list to display in a dropdown … create this endpoint to satisfy this requirement."*

Inventory: division values are an in-code `Tuple[str, ...]` constant in [`app/domain/resource_types/resource_type.py`](app/domain/resource_types/resource_type.py) (`tmd1`, `tmd2`, `others`). Used by activity-resource classification today and reused by the FE as a project-owner picker (HTML's `buildDivisionField` helper renders both). Pre-change there was no API surface for it — the FE hard-coded `DIVISION_OPTIONS = ['TMD1','TMD2','Others']`.

### What changed

[`app/api/v3/catalogs/routes.py`](app/api/v3/catalogs/routes.py) — new endpoint at the existing catalogs router. Authenticated, no specific permission required (matches `/project_status_transitions` and `/project_owners`).

```python
GET /api/v3/divisions
→ {
    "data": {
      "_type": "Collection",
      "_links": {"self": {"href": "/api/v3/divisions"}},
      "total": 3, "count": 3,
      "_embedded": {"elements": [
        {"_type": "Division", "code": "tmd1",   "label": "TMD1",   "requiresOther": false},
        {"_type": "Division", "code": "tmd2",   "label": "TMD2",   "requiresOther": false},
        {"_type": "Division", "code": "others", "label": "Others", "requiresOther": true}
      ]}
    }
  }
```

`code` is the lowercase wire value the API expects in `division` fields (consistent with `category` codes). `label` is the uppercase display string (UI design uses TMD1 / TMD2 / Others). `requiresOther` tells the FE to show the free-text follow-up input on the 'others' entry — same idiom as the project-category 'others' picker.

No DB table — values come from the in-code `DIVISION_CHOICES` constant. Adding a new division is a code change (one tuple entry + one label-map entry).

## §3 — RFC 7662 introspect + dedicated `/users/refresh` (Option C)

### Why

User report on the current introspect response:
```json
{ "data": { "_type": "Introspect", "active": true, "user": {...} } }
```
> *"now I am not sure how the flow for the refresh token generating the new token is supposed to work since this is not providing the required info."*

Pre-change behaviour:
- `POST /users/login` returned `{access_token, refresh_token, token_type, user}` — no expiry info on either token. FE had to decode the JWT (without the secret) to know when to refresh, or wait for a 401.
- `POST /users/introspect` was overloaded: with a valid access_token it returned `{active: true, user}`; with an expired access_token + valid refresh_token it ROTATED and returned a fresh token pair.
- There was no dedicated refresh endpoint — refresh was reachable only via introspect.

Three options were presented to the user; they picked **Option C** (RFC 7662-conformant introspect + dedicated `/users/refresh` + login expiry metadata).

### What changed

#### `POST /users/introspect` is now read-only

[`app/api/v3/users/services/introspect.py`](app/api/v3/users/services/introspect.py) — rewritten. Decodes whichever of `access_token` / `refresh_token` is supplied and returns metadata:

| Field | Meaning |
|---|---|
| `active` | true iff signature valid AND not expired AND (for access tokens) jti not in revoked-token blacklist AND (for refresh tokens) jti matches user row + stored expiry not in past |
| `tokenType` | `"access"` or `"refresh"` |
| `exp`, `iat` | unix timestamps from the JWT |
| `expiresAt`, `issuedAt` | ISO 8601 strings (FE convenience — same value, easier to parse) |
| `jti` | the token's unique identifier |
| `sub` / `username` | user login |
| `userId` | numeric user id |
| `email`, `role`, `isAdmin` | identity claims from the JWT |

When BOTH tokens are supplied, the response shape becomes `{access: {...}, refresh: {...}}` — caller can introspect a pair in one round-trip.

Inactive / expired / revoked / unparseable token → `{"active": false, "tokenType": ...}` at HTTP 200. Matches RFC 7662's "active=false on inactive tokens" — not an error condition.

NEVER rotates. Even posting a valid refresh token to introspect returns metadata only. The `test_logout_does_not_rotate_via_introspect` test guards against future regression.

#### New `POST /users/refresh` endpoint

[`app/api/v3/users/services/refresh.py`](app/api/v3/users/services/refresh.py) — new service. Body: `{refresh_token: string}`. Validates against:

1. JWT signature + expiry.
2. `user_row.refresh_token_jti` matches the token's jti (single-active-jti rotation; older refresh tokens that have already been rotated out fail here).
3. `user_row.refresh_token_expires_at` is in the future.

On success, mints a fresh access + refresh pair and atomically swaps the user row's stored jti via `update_refresh_token_metadata(..., expected_old_jti=token_jti)` — the conditional UPDATE means two concurrent refresh attempts with the same token can only succeed once. The loser gets 401.

Response:
```json
{
  "data": {
    "_type": "Refresh",
    "access_token": "...", "refresh_token": "...", "token_type": "bearer",
    "accessTokenExpiresAt":  "2026-04-28T18:30:00+00:00",
    "accessTokenIssuedAt":   "2026-04-28T18:15:00+00:00",
    "refreshTokenExpiresAt": "2026-05-05T18:15:00+00:00",
    "refreshTokenIssuedAt":  "2026-04-28T18:15:00+00:00",
    "expiresInSeconds": 900,
    "user": { "_type": "User", ... }
  }
}
```

Failure modes (all 401):
- Invalid / expired refresh token.
- Refresh token already rotated (jti no longer matches user row).
- User has been logged out (jti cleared on logout).
- Posting an access token where the refresh token is expected (different audience — verify_refresh_token returns None).

Missing body field → 422 from the Pydantic schema.

#### `POST /users/login` response now carries expiry metadata

[`app/api/v3/users/controller.py`](app/api/v3/users/controller.py) — login response now includes `accessTokenExpiresAt`, `accessTokenIssuedAt`, `refreshTokenExpiresAt`, `refreshTokenIssuedAt`, and `expiresInSeconds`. FE can schedule a preemptive `/users/refresh` ~30s before `accessTokenExpiresAt` without ever seeing a 401.

Implemented as a one-time post-mint decode via the new `_exp_metadata` helper in `services/refresh.py` (signature-verification skipped — we just minted these tokens, no need to re-validate).

### What broke (and was migrated)

One existing test relied on the old "introspect with refresh token = rotate" behaviour:

```python
# tests/test_users.py::test_logout_invalidates_refresh_endpoint  (BEFORE)
intro = client.post("/api/v3/users/introspect", json={"refresh_token": refresh})
assert intro.status_code == 401
```

Migrated to the new endpoint:

```python

assert ref.status_code == 401
```

If any FE caller still POSTs a refresh token to `/users/introspect` expecting rotation, they'll now get a 200 with `{"active": true, "tokenType": "refresh", ...}` — token metadata, not new tokens. The migration path is to call `/users/refresh` instead.

## §5 — `ownerOther` field + required-when-`owner=='others'` rule

### Why

User: *"do not allow empty owner. if other is selected, a non-empty value must be provided."*

Symmetric with the existing `categoryOther` / `categoryOtherReason` idiom, which has been in place since doc 15.

### What changed

**Schema:**
- `ProjectModel.owner_other` — new `String(255)` nullable column.
- `Project` domain dataclass + `to_dict()` carry `owner_other`.
- `ProjectRepository.create()` + `upsert_by_id()` accept and persist `owner_other`.
- All three Pydantic project schemas (Create / Update / Upsert) now have `ownerOther: Optional[str]` (alias `owner_other`, max_length=255).
- Controller passes `ownerOther` into the service call sites.
- `format_project_response` surfaces `ownerOther`.

**Validation** (in `validate_owner_pair`):
1. `owner` is REQUIRED on create + upsert (`require_owner=True`). Whitespace-only strings normalise to None and trigger `"Owner is required."`. Same rule on PATCH when `owner` is supplied.
2. When `owner == 'others'`, `owner_other` MUST be a non-empty string ≤ 255 chars (trimmed). Empty / missing → 422.
3. When `owner != 'others'`, `owner_other` MUST be None / empty. Supplying a non-empty value → 422.
4. PATCH special case: when `owner` is being moved AWAY from `'others'` without explicitly touching `owner_other`, the existing `owner_other` on the row is treated as None for cross-validation purposes (avoids forcing the FE to also clear the stale field — same TODO as `categoryOther` for an eventual repo-level explicit-null sentinel).

**Migration:** [`alembic/versions/b9e2f7c4a8d5_add_owner_other_column_to_projects.py`](alembic/versions/b9e2f7c4a8d5_add_owner_other_column_to_projects.py) — additive only, NULL-default. Plus an explicit `vendors`/`projects` SQLite drift entry in `init_db`.

### Tests added — `TestOwnerOthers` (12 tests)

- happy: `owner='others'` + `ownerOther='Custom Division'` → 201
- 422 if `owner='others'` and no `ownerOther` (or empty)
- 422 if `owner='tmd1'` and a non-empty `ownerOther` is supplied
- create rejects empty / missing `owner` (422 with "required" in message)
- casing normalisation (`Others`, `OTHERS`)
- whitespace stripping (`  others  `)
- close misspellings (`other`, `oth`, `tmd3`) → 422
- PATCH owner='tmd1' → 'others' requires `ownerOther`
- PATCH owner='others' → 'tmd1' WITHOUT having to also clear stale `ownerOther`
- PATCH casing normalisation + upsert insert/update with `'others'`
- round-trip: `owner='others'` + `ownerOther='Engineering'` survives a GET

### What changed about the upsert ownership gate

Pre-change, `upsert_project` had `if existing.owner != current_user_login: forbidden`. With owner now being a division, that comparison can never match for non-admins → would lock everyone except admins out of the wizard's update path. **Removed.** Route-level `PROJECTS_CREATE` permission is now the gate. `current_user_login` and `is_admin` remain in the call signature for stability but go unused. ## §6 — `divisions` DB table + user-supplied labels persist for future picker entries

### Why

User: *"when other is selected, and project is successfully created, then that value for owner will be added to divisions in the database as well."*

Net effect: a free-text `ownerOther` label entered once becomes a first-class division code that future projects can pick directly from the dropdown — no more going through the 'others' branch for the second project.

### What changed

#### New table: `divisions`

[`app/infrastructure/db/models/division.py`](app/infrastructure/db/models/division.py) + [`alembic/versions/c3a8d5e1b962_add_divisions_table.py`](alembic/versions/c3a8d5e1b962_add_divisions_table.py).

Columns:

Indexes on `code` and `active`.

The Alembic chain is now `… → b9e2f7c4a8d5 → c3a8d5e1b962 (head)`, single linear.

#### Repository

[`app/infrastructure/db/repositories/division_repository.py`](app/infrastructure/db/repositories/division_repository.py):
- `slugify(label)` — `'  Engineering R&D  '` → `'engineering_r_d'`.
- `list_active()` — built-ins first, then user-added in created order.
- `get_by_code(code)`, `is_known_code(code)` — picker-validation reads.
- `upsert_user_division(label)` — slugify; insert if missing, no-op if present (or re-activate if soft-disabled).

#### Seed in `init_db`

Three built-in rows seeded on first boot. Idempotent (matched by code). New section in `init_db` between the existing `project_status_transitions` and `project_owners` seeds.

#### Catalog endpoint

`GET /api/v3/divisions` now reads from the table. The endpoint is **defensive**: it always returns the three built-ins (in code order) plus any user-added rows, even if the table hasn't been seeded yet — so test environments without `init_db` still see a non-empty list. New response field `isBuiltin` per item.

#### Owner validator: catalog-driven

`validate_owner_pair(..., db=db)` now consults the divisions table at runtime. Logic:
1. Built-in codes (`OWNER_DIVISION_CODES`) are ALWAYS accepted, regardless of catalog state.
2. Active rows in the divisions table EXTEND the accepted set.
3. Anything else → 422 with `"Owner '{x}' is not a known division. Pick one from GET /divisions or use 'others' with a custom ownerOther label."`

#### Persistence on the create / update / upsert paths

When a project is saved with `owner == 'others'` AND a non-empty `ownerOther`, the service calls `DivisionRepository(db).upsert_user_division(owner_other)` BEFORE commit (or right after, in upsert's case where the repo commits internally). Idempotent — duplicates collapse via the slug. A `'Marketing'` typed once + `'  marketing  '` typed second + `'MARKETING'` typed third all collapse to a single `marketing` division row.

## §7 — Vendor contact details + GET /vendors/{id}

### Why

User: *"In vendor, the details are incomplete. When fetching vendor, I want the details such as email, project mapping, contact person, phone number to also be sent to the frontend. … In case these details are not recorded in vendor flow currently, also check and add it to vendor. project mapping is not done manually, but through project creation flow where vendor is assigned to project."*

Project mapping was already in place from doc 17 (the list endpoint embeds `projects: [{id, projectCode, name}, ...]` per vendor; mappings are written by the project-create `vendorIds` parameter, never directly). What was missing: contact-detail columns on the model, and a single-vendor detail endpoint to back the FE's "Vendor Detail" page.

### What changed

#### Schema

[`app/infrastructure/db/models/vendor.py`](app/infrastructure/db/models/vendor.py) — three new columns on the `vendors` table:

- `email VARCHAR(255), nullable, indexed` — primary contact email. Loosely RFC-5322 validated at the schema layer (Pydantic's `EmailStr`); not unique because multiple vendors at one parent org may share an inbox.
- `contact_person VARCHAR(255), nullable` — free-form name string for the FE's "who do we talk to?" field.
- `phone_number VARCHAR(50), nullable` — free-form phone string. No regex check (international formats vary too much for a one-size pattern); the FE applies its own client-side mask.

All three nullable, so vendors created before this batch keep their NULLs and the FE renders empty cells for missing values.

[`app/domain/vendors/vendor.py`](app/domain/vendors/vendor.py) — domain dataclass + `to_dict()` carry the three new fields. [`app/infrastructure/db/repositories/vendor_repository.py`](app/infrastructure/db/repositories/vendor_repository.py) — `_to_domain` reads them; `create()` accepts them as keyword args.

#### Schemas

[`app/api/v3/vendors/schemas.py`](app/api/v3/vendors/schemas.py) — both `VendorCreateRequest` and `VendorUpdateRequest` got the three new fields:

- `email: Optional[EmailStr]`
- `contactPerson: Optional[str]` (alias `contact_person`, max_length=255)
- `phoneNumber: Optional[str]` (alias `phone_number`, max_length=50)

`EmailStr` validates malformed addresses at the schema layer — `'not-an-email'` returns 422 before the service is even called.

#### Routes

[`app/api/v3/vendors/routes.py`](app/api/v3/vendors/routes.py) — three behavioural changes:

1. New endpoint: `GET /api/v3/vendors/{vendor_id}` — returns full vendor detail (name, description, email, contact_person, phone_number, soft-delete metadata) plus the mapped projects array (closed/completed/soft-deleted projects filtered out, same rule as the list endpoint and `/vendors/{id}/projects`). 404 on missing OR soft-deleted vendors — same hide-policy as the list endpoint.
2. `_vendor_to_response` helper now surfaces `email`, `contactPerson`, `phoneNumber` (camelCase per the wire convention).
3. `POST /vendors/create` and `PATCH /vendors/{id}` thread the three new fields through to the repository.

Route surface now (full picture):

| Method | Path | Purpose |
|---|---|---|
| `GET`    | `/vendors`                       | List live vendors (newest first, with mapped projects) |
| `GET`    | `/vendors/{id}`                  | **NEW** — full vendor detail + mapped projects |
| `POST`   | `/vendors/create`                | Create (with optional contact details) |
| `PATCH`  | `/vendors/{id}`                  | Edit (any field including contact details) |
| `DELETE` | `/vendors/{id}`                  | Soft-delete |
| `POST`   | `/vendors/{id}/restore`          | Undelete |
| `GET`    | `/vendors/{id}/projects`         | Mapped projects only (closed/completed filtered) |

#### Migration

[`alembic/versions/d4f1a8c5b6e7_add_vendor_contact_columns.py`](alembic/versions/d4f1a8c5b6e7_add_vendor_contact_columns.py) — additive: three nullable columns + an index on `email`. Chains as `c3a8d5e1b962 → d4f1a8c5b6e7 (head)`.

[`app/infrastructure/db/session.py`](app/infrastructure/db/session.py) — the existing `vendors` SQLite drift block was extended in-place with the three new columns + the email index. Single PRAGMA pass picks up everything missing.

### Project mapping is unchanged

The project-creation flow remains the source of mappings. No new "manual mapping" endpoint was added — that's deliberate per the user's spec ("project mapping is not done manually, but through project creation flow where vendor is assigned to project"). The existing surface:

```
POST /api/v3/projects/create  { name: "...", vendorIds: ["<vendor-uuid>", ...] }
PATCH /api/v3/projects/{id}   { vendorIds: [...] }   # replace full set
```

The `project_vendors` association table writes happen there. The vendor-side endpoints (list, detail, /vendors/{id}/projects) are pure reads of that table — there's no separate `POST /vendors/{id}/projects/{pid}` to create the mapping in the other direction.
