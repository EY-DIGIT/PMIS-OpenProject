## §0 — SQLite drift bug fix + generic auto-healer

### The bug

User report:
```
GET /api/v3/projects → 500
"Failed to list projects: (sqlite3.OperationalError) no such column: projects.category_other_reason"
```

Root cause: the SQLite drift handler in `init_db` (which keeps legacy on-disk dev `pmis.db` files in sync as new model columns land) was hand-maintained and had not been updated to add two columns introduced in earlier migrations:

- `projects.category_other_reason` — added in doc-15 catalogs migration `f9b8dd81f7dd`.
- `projects.actual_start_date` — added in doc-16 migration `eb3b19c7487c`.

Postgres deployments were unaffected because Alembic ran the migrations correctly. The user's local Windows dev backend defaults to `DATABASE_URL=sqlite:///./pmis.db` (per `app/core/config.py:30`), so the local `/projects` route hit the stale schema and 500'd.

### What changed

#### Targeted: explicit ALTER for the two missing columns

[`app/infrastructure/db/session.py`](app/infrastructure/db/session.py) — added `category_other_reason` (VARCHAR(1000), nullable) and `actual_start_date` (DATETIME, nullable) to the `project_column_ddl` list inside the existing SQLite drift block. Idempotent: only added when missing from `PRAGMA table_info('projects')`.

#### Defensive: generic `_heal_sqlite_column_drift` pass

New module-level helper in [`app/infrastructure/db/session.py`](app/infrastructure/db/session.py):

- Iterates `Base.metadata.sorted_tables`.
- For each table that already exists, compares model columns against `PRAGMA table_info`.
- For any nullable model column missing from the DB, generates the dialect-specific DDL via `CreateColumn(column).compile(dialect=dialect)` and runs `ALTER TABLE … ADD COLUMN`.
- NOT NULL columns without a default are SKIPPED (SQLite can't add them without a default value) and logged as a `WARNING` so devs notice and add an explicit ALTER block above the auto-healer.
- Returns the list of `table.column` strings that were added, for logs / tests.

Wired in after the existing explicit-DDL blocks but before any post-create-all logic. Order:

1. `Base.metadata.create_all(bind=engine)` — creates new tables.
2. Existing explicit ALTER blocks — handles partial / hand-tuned drift.
3. `_heal_legacy_dep_tables()` — drops + rebuilds dep tables on schema-v1 → v2 migration.
4. **NEW:** `_heal_sqlite_column_drift()` — catches any remaining column drift.
5. Bootstrap admin / catalog seeds.

Audited the local DB after the change — only the two `vendors` columns added in doc-17 (`deleted_at`, `deleted_by`) were missing; both are already covered by the explicit drift block from doc 17. The auto-healer found no extra gaps.

### Why both targeted + generic

- The explicit list is fast on every boot (one PRAGMA + one ALTER per known column) and easy for devs to trace when reading the file.
- The generic auto-healer is the safety net for future drops where the explicit list isn't updated. Catches the bug class permanently without imposing maintenance burden.

### How to recover from the user-reported state

```bash
# Stop the app.
# (No data migration needed — the column will be added with NULL values.)
# Restart the app — init_db's drift handler adds the column on boot.
```

After this batch lands, restarting the app heals the schema; the 500 goes away. No manual ALTER required.

## §1 — PATCH editable-field whitelist expanded per HTML edit-project flow

### Why

User report: *"the patch api for project editing api, /api/v3/projects/{project_uuid} rejects the requests where fields like category or status are shared. … modify the endpoint to allow the fields which are editable in the edit project flow to be editable from the backend."*

Cross-checked against the HTML edit flow ([HTML lines 2281–2511](C:\Users\CL725CJ\Downloads\Project%20Management%20(1).html)):

- **Baseline (any state, including published):** name, description, owner, expectedStartDate, expectedEndDate, actualStartDate, actualEndDate, isPublic, **category** (+ categoryOther / categoryOtherReason when 'others'), vendors. Read-only: projectId, baselineId, status.
- **Version:** owner, isPublic, actualStartDate, actualEndDate, vendors. Read-only: projectId, baselineId, status, name, dates, category — version inherits these from the baseline.

Pre-change the BE whitelist was much narrower:

| Whitelist | Pre | Post |
|---|---|---|
| `EDITABLE_FIELDS_BASELINE_UNPUBLISHED` | name, description, owner, start_date, end_date, public, active, status_explanation | + **actual_start_date, actual_end_date, category, category_other, category_other_reason** |
| `EDITABLE_FIELDS_BASELINE_PUBLISHED` | (same as unpublished) | (same as unpublished) |
| `EDITABLE_FIELDS_VERSION` | owner, public, actual_start_date, actual_end_date, status_explanation | (unchanged) |

`status` is **deliberately not** in any whitelist — the user clarified after the first pass that "in baseline, status should not be editable" and "in version, status should not be editable." Status changes flow through the dedicated `/publish`, `/close`, `/suspend`, `/save` endpoints, which apply the transition state machine (admin gating, version-only gating, catalog consultation). PATCHing `status` returns 422 `invalid_field` with a `rejected: ["status"]` detail block.

`project_code` and `baseline_id` are also not editable — they're system identifiers. `project_code` is in the repo's `_IMMUTABLE` set so it's silently dropped if supplied; `baseline_id` isn't in any whitelist so the patch returns 422 `invalid_field`. (Same effect; both are correct.)

### What changed

#### Whitelist update

[`app/api/v3/projects/services/transitions.py`](app/api/v3/projects/services/transitions.py) — three new fields added to `EDITABLE_FIELDS_BASELINE_UNPUBLISHED`. Inline comment now reads as the spec rather than the implementation:

```python
# Versions allow editing a small subset per the HTML edit flow:
# owner, isPublic, actualStartDate, actualEndDate, vendors. Project ID
# (project_code), baseline ID, and status are read-only — status changes
# go through the dedicated publish/close/suspend transition endpoints,
# project_code + baseline_id are immutable system identifiers.
```

#### Category 'others' idiom on PATCH

[`app/api/v3/projects/services/update.py`](app/api/v3/projects/services/update.py) — symmetric with `create_project` and `upsert_project`. When the patch touches `category`, `category_other`, or `category_other_reason`:

- Validates the effective category (patch ∪ existing row) against `PROJECT_CATEGORY_CHOICES`.
- When effective category == `others`: requires non-empty `category_other` (max 255) AND non-empty `category_other_reason` (max 1000).
- When effective category != `others`: rejects any non-empty `category_other` / `category_other_reason` with 422 `validation_error`.
- TODO documented inline: when switching FROM `others` TO another category, the previously-stored `category_other` / `category_other_reason` are left in place because the repo's `update()` treats `None` as "leave unchanged" — clearing them would need a small repo extension (sentinel for explicit-null). Low priority — display drift only, never validation.

#### Controller passthrough

[`app/api/v3/projects/controller.py`](app/api/v3/projects/controller.py) — the PATCH controller now passes `category_other` and `category_other_reason` from the request schema into the `patch` dict (was missing before, so even if the whitelist had allowed them they would have been dropped before reaching the service).

### Tests added (4 new, in `tests/test_catalogs_and_other_reason.py::TestPatchEditableFields`)

- `test_baseline_can_patch_category` — change MSAP → MSIP, assert 200 and the new value.
- `test_baseline_can_patch_to_others_with_reason` — full happy path with category + categoryOther + categoryOtherReason in one PATCH.
- `test_baseline_patch_to_others_without_reason_rejected` — 422 when categoryOther is supplied but categoryOtherReason isn't.
- `test_baseline_status_patch_rejected` — 422 `invalid_field` with `rejected: ["status"]`.
- `test_version_status_patch_rejected` — 422 on PATCHing `status`, `category`, `name`, or `start_date` on a version.

## §2 — `GET /api/v3/divisions` catalog endpoint

### Why

User report: *"there is a field called division which is used for adding information in projects. this is being retrieved from db. There is however no specific endpoint to query the db to fetch this list to display in a dropdown … create this endpoint to satisfy this requirement."*

Inventory: division values are an in-code `Tuple[str, ...]` constant in [`app/domain/resource_types/resource_type.py`](app/domain/resource_types/resource_type.py) (`tmd1`, `tmd2`, `others`). Used by activity-resource classification today and reused by the FE as a project-owner picker (HTML's `buildDivisionField` helper renders both). Pre-change there was no API surface for it — the FE hard-coded `DIVISION_OPTIONS = ['TMD1','TMD2','Others']`.

### What changed

[`app/api/v3/catalogs/routes.py`](app/api/v3/catalogs/routes.py) — new endpoint at the existing catalogs router. Authenticated, no specific permission required (matches `/project_status_transitions` and `/project_owners`).

```python
GET /api/v3/divisions
→ {
    "data": {
      "_type": "Collection",
      "_links": {"self": {"href": "/api/v3/divisions"}},
      "total": 3, "count": 3,
      "_embedded": {"elements": [
        {"_type": "Division", "code": "tmd1",   "label": "TMD1",   "requiresOther": false},
        {"_type": "Division", "code": "tmd2",   "label": "TMD2",   "requiresOther": false},
        {"_type": "Division", "code": "others", "label": "Others", "requiresOther": true}
      ]}
    }
  }
```

`code` is the lowercase wire value the API expects in `division` fields (consistent with `category` codes). `label` is the uppercase display string (UI design uses TMD1 / TMD2 / Others). `requiresOther` tells the FE to show the free-text follow-up input on the 'others' entry — same idiom as the project-category 'others' picker.

No DB table — values come from the in-code `DIVISION_CHOICES` constant. Adding a new division is a code change (one tuple entry + one label-map entry).

### Tests added (2 new, in `tests/test_catalogs_and_other_reason.py::TestDivisionsCatalog`)

- `test_endpoint_returns_three_divisions_with_labels` — payload shape, ordering, labels, and `requiresOther` flags.
- `test_endpoint_requires_authentication` — anonymous → 401.

## §3 — RFC 7662 introspect + dedicated `/users/refresh` (Option C)

### Why

User report on the current introspect response:
```json
{ "data": { "_type": "Introspect", "active": true, "user": {...} } }
```
> *"now I am not sure how the flow for the refresh token generating the new token is supposed to work since this is not providing the required info."*

Pre-change behaviour:
- `POST /users/login` returned `{access_token, refresh_token, token_type, user}` — no expiry info on either token. FE had to decode the JWT (without the secret) to know when to refresh, or wait for a 401.
- `POST /users/introspect` was overloaded: with a valid access_token it returned `{active: true, user}`; with an expired access_token + valid refresh_token it ROTATED and returned a fresh token pair.
- There was no dedicated refresh endpoint — refresh was reachable only via introspect.

Three options were presented to the user; they picked **Option C** (RFC 7662-conformant introspect + dedicated `/users/refresh` + login expiry metadata).

### What changed

#### `POST /users/introspect` is now read-only

[`app/api/v3/users/services/introspect.py`](app/api/v3/users/services/introspect.py) — rewritten. Decodes whichever of `access_token` / `refresh_token` is supplied and returns metadata:

| Field | Meaning |
|---|---|
| `active` | true iff signature valid AND not expired AND (for access tokens) jti not in revoked-token blacklist AND (for refresh tokens) jti matches user row + stored expiry not in past |
| `tokenType` | `"access"` or `"refresh"` |
| `exp`, `iat` | unix timestamps from the JWT |
| `expiresAt`, `issuedAt` | ISO 8601 strings (FE convenience — same value, easier to parse) |
| `jti` | the token's unique identifier |
| `sub` / `username` | user login |
| `userId` | numeric user id |
| `email`, `role`, `isAdmin` | identity claims from the JWT |

When BOTH tokens are supplied, the response shape becomes `{access: {...}, refresh: {...}}` — caller can introspect a pair in one round-trip.

Inactive / expired / revoked / unparseable token → `{"active": false, "tokenType": ...}` at HTTP 200. Matches RFC 7662's "active=false on inactive tokens" — not an error condition.

NEVER rotates. Even posting a valid refresh token to introspect returns metadata only. The `test_logout_does_not_rotate_via_introspect` test guards against future regression.

#### New `POST /users/refresh` endpoint

[`app/api/v3/users/services/refresh.py`](app/api/v3/users/services/refresh.py) — new service. Body: `{refresh_token: string}`. Validates against:

1. JWT signature + expiry.
2. `user_row.refresh_token_jti` matches the token's jti (single-active-jti rotation; older refresh tokens that have already been rotated out fail here).
3. `user_row.refresh_token_expires_at` is in the future.

On success, mints a fresh access + refresh pair and atomically swaps the user row's stored jti via `update_refresh_token_metadata(..., expected_old_jti=token_jti)` — the conditional UPDATE means two concurrent refresh attempts with the same token can only succeed once. The loser gets 401.

Response:
```json
{
  "data": {
    "_type": "Refresh",
    "access_token": "...", "refresh_token": "...", "token_type": "bearer",
    "accessTokenExpiresAt":  "2026-04-28T18:30:00+00:00",
    "accessTokenIssuedAt":   "2026-04-28T18:15:00+00:00",
    "refreshTokenExpiresAt": "2026-05-05T18:15:00+00:00",
    "refreshTokenIssuedAt":  "2026-04-28T18:15:00+00:00",
    "expiresInSeconds": 900,
    "user": { "_type": "User", ... }
  }
}
```

Failure modes (all 401):
- Invalid / expired refresh token.
- Refresh token already rotated (jti no longer matches user row).
- User has been logged out (jti cleared on logout).
- Posting an access token where the refresh token is expected (different audience — verify_refresh_token returns None).

Missing body field → 422 from the Pydantic schema.

#### `POST /users/login` response now carries expiry metadata

[`app/api/v3/users/controller.py`](app/api/v3/users/controller.py) — login response now includes `accessTokenExpiresAt`, `accessTokenIssuedAt`, `refreshTokenExpiresAt`, `refreshTokenIssuedAt`, and `expiresInSeconds`. FE can schedule a preemptive `/users/refresh` ~30s before `accessTokenExpiresAt` without ever seeing a 401.

Implemented as a one-time post-mint decode via the new `_exp_metadata` helper in `services/refresh.py` (signature-verification skipped — we just minted these tokens, no need to re-validate).

### What broke (and was migrated)

One existing test relied on the old "introspect with refresh token = rotate" behaviour:

```python
# tests/test_users.py::test_logout_invalidates_refresh_endpoint  (BEFORE)
intro = client.post("/api/v3/users/introspect", json={"refresh_token": refresh})
assert intro.status_code == 401
```

Migrated to the new endpoint:

```python
# tests/test_users.py::test_logout_invalidates_refresh_endpoint  (AFTER)
ref = client.post("/api/v3/users/refresh", json={"refresh_token": refresh})
assert ref.status_code == 401
```

If any FE caller still POSTs a refresh token to `/users/introspect` expecting rotation, they'll now get a 200 with `{"active": true, "tokenType": "refresh", ...}` — token metadata, not new tokens. The migration path is to call `/users/refresh` instead.

## Cumulative effect

### Local

1. `git pull` (no-op against `master`; everything in this batch is uncommitted at the time of writing).
2. **Restart the app.** On boot:
   - Postgres path: `alembic upgrade head` is already at `7c4a91d8e3f0` (doc-17 head) — no schema change in this batch.
   - SQLite path: the new explicit ALTER block adds the missing `category_other_reason` and `actual_start_date` columns; the generic auto-healer adds anything else that may have drifted.
3. `pytest tests/` — should land at **258 passed, 3 skipped**.

### Server (DevOps)

No new env var, no new mount, no schema change. Just deploy the new code. The `/projects` 500 (the user-reported bug) goes away because:
- Postgres deployments were never affected (Alembic was correct; the bug only manifested on SQLite).
- Local SQLite dev backends self-heal on restart.

### API surface delta

New endpoints:
- `GET  /api/v3/divisions`
- `POST /api/v3/users/refresh`

Changed responses:
- `POST /api/v3/users/login` — adds `accessTokenExpiresAt`, `accessTokenIssuedAt`, `refreshTokenExpiresAt`, `refreshTokenIssuedAt`, `expiresInSeconds`.
- `POST /api/v3/users/introspect` — fully restructured response (RFC 7662-style); single-token responses are flat, both-token responses are split. Inactive token returns 200 with `active: false` (was 401 in some paths).

Changed behaviour:
- `POST /api/v3/users/introspect` — no longer rotates. FE callers that relied on this for refresh must move to `POST /api/v3/users/refresh`.
- `PATCH /api/v3/projects/{id}` — now accepts `category`, `categoryOther`, `categoryOtherReason`, and `actualStartDate` / `actualEndDate` on baselines. Still rejects `status` on both baseline and version (use `/publish`, `/close`, `/suspend`).
