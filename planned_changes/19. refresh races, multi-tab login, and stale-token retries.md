# Refresh-token grace window — fixes concurrent /refresh races, multi-tab login, and stale-token retries

This document captures a single targeted backend fix on top of [doc 18](./18.%20SQLite%20drift%20fix%20%2B%20auto-healer%2C%20PATCH%20editable-field%20expansion%2C%20divisions%20catalog%2C%20RFC%207662%20introspect%20%2B%20dedicated%20refresh.md). The /users/refresh endpoint that doc 18 added was returning `401 "Refresh token invalid or already rotated."` to the FE in normal use — not because of a stolen-token replay (the original purpose of the message), but because the rotation logic was too strict for the way real frontends fire refresh calls in production.

| # | Author | Topic |
|---|---|---|
| 0 | **Chinmaya** | Bug fix: refresh-token rotation kicks the FE out under three normal usage patterns (concurrent refresh, multi-tab login, stale RT in retry queue). Adds a 120 s grace window around every rotation so the just-rotated-out jti remains acceptable. Login no longer instantly invalidates a live refresh token. The conditional atomic-swap that was the source of the concurrent-refresh race is removed. |

## §0 — The bug

### User report

> "facing this issue with refresh token when trying to get new access token at 12 minutes:
> ```
> { "data": null, "message": null,
>   "error": { "_type": "Error",
>     "errorIdentifier": "authentication_error",
>     "message": "Refresh token invalid or already rotated." },
>   "status": 401 }
> ```"

The 12-minute mark is significant: the access token TTL is 15 min and the FE pre-emptively refreshes ~3 min before expiry, so the first refresh attempt of any session lands at T+12 min.

### Reproduction (live server, before the fix)

Wrote a small diagnostic script (`C:\tmp\test_refresh.py`) that exercised seven scenarios:

| Step | Action | Result | OK / BUG |
|---|---|---|---|
| 1 | Login → RT1 | `jti=fa5e6fe8…` | OK |
| 2 | refresh(RT1) → RT2 | `jti=90c0c37c…`, status 200 | OK |
| 3 | refresh(RT1) again | 401 *already rotated* | Correct (RT1 is the rotated-out token) |
| 4 | refresh(RT2) → RT3 | status 200 | OK |
| 5 | re-login as same user → RT4 | status 200 | OK |
| 6 | refresh(RT3) (issued before re-login) | **401** *already rotated* | **BUG** — RT3 was a perfectly valid live token before re-login |
| 7 | Two concurrent refresh(RT4) calls | one 200, one **401** *already rotated* | **BUG** — race-loser shouldn't be locked out |

### Root causes

**Cause A — login overwrites the stored `refresh_token_jti` unconditionally.**

[`app/api/v3/users/services/authenticate.py:79`](../app/api/v3/users/services/authenticate.py) (pre-fix) called `update_refresh_token_metadata(user.id, refresh_jti, refresh_expires)` without checking whether a live refresh token already existed for the user. Any prior refresh token immediately became invalid the moment a second `/login` ran for the same user — common in real FE flows (open in another tab, mobile session, login replay during route transitions, automated test harnesses).

**Cause B — concurrent refresh requests race; the loser gets 401.**

[`app/api/v3/users/services/refresh.py:119`](../app/api/v3/users/services/refresh.py) (pre-fix) called `update_refresh_token_metadata(user_id, new_jti, new_expires, expected_old_jti=token_jti)`, which performed a conditional UPDATE in the repository: `WHERE refresh_token_jti = expected_old_jti`. Two simultaneous refreshes both pass validation (same stored jti at read time), but only one wins the swap; the other gets a `rows_updated == 0` and a 401 response.

This is the classic "single-writer atomic swap" pattern. It's correct for stolen-token replay defence, but it's wrong for the typical FE pain pattern: a preemptive-refresh timer firing at the same instant as a 401-interceptor catching an in-flight 401 from another request — both fire `/refresh` with the same RT in parallel, and one of them dies.

## §1 — The fix

### Design

Add a small bit of state to `users` so the BE remembers the just-rotated-out jti for a configurable window (default 120 s). During that window, presenting **either** the current OR the just-replaced refresh token is treated as valid; the conditional atomic-swap is removed.

This is the standard pattern auth providers (Auth0, AWS Cognito) use to absorb FE refresh races without weakening the single-active-token model long-term.

### Schema additions

Two new nullable columns on `users`:

| Column | Type | Purpose |
|---|---|---|
| `previous_refresh_token_jti` | `VARCHAR(64)` | The jti that was just rotated out. |
| `previous_refresh_token_jti_valid_until` | `DATETIME` (UTC) | When the grace window expires. Set to `now + REFRESH_TOKEN_GRACE_SECONDS` whenever previous is written. |

Plus a config knob:

```python
# app/core/config.py
REFRESH_TOKEN_GRACE_SECONDS: int = 120
```

### Behaviour change — login

[`app/api/v3/users/services/authenticate.py`](../app/api/v3/users/services/authenticate.py) now calls the new `repo.rotate_refresh_token(...)` method with a non-zero `grace_seconds` argument. The repository:

1. Reads the current `refresh_token_jti`.
2. If non-null, copies it into `previous_refresh_token_jti` with `valid_until = now + grace_seconds`.
3. Writes the new jti + expiry to the live columns.
4. Commits.

All four writes happen in the same transaction so concurrent callers don't see torn state.

### Behaviour change — refresh validation

[`app/api/v3/users/services/refresh.py`](../app/api/v3/users/services/refresh.py) — validation now reads all four metadata fields via the new `get_refresh_metadata_with_grace()` and accepts the token if **either**:

- `incoming_jti == current_jti`, **or**
- `incoming_jti == previous_jti AND now < previous_valid_until`

When the token resolves to the previous slot, hard-expiry on `current_expires` is **not** checked — the previous slot's lifetime is bounded by the grace window itself, which is shorter than the 7-day refresh TTL by design.

### Behaviour change — refresh rotation

The conditional atomic-swap is gone. Each successful validation now triggers an **unconditional** rotation:

```python
repo.rotate_refresh_token(
    user_id, new_jti, new_expires,
    grace_seconds=settings.REFRESH_TOKEN_GRACE_SECONDS,
)
```

Concurrent refreshes both succeed; each receives its own fresh access + refresh pair. The "loser" doesn't lose anymore — it just gets a slightly later `previous_jti` capture.

### Behaviour change — logout

[`app/api/v3/users/services/logout.py`](../app/api/v3/users/services/logout.py) now uses `rotate_refresh_token(user_id, None, None, grace_seconds=0)`, which clears **all four** refresh-related columns: live jti, live expiry, previous jti, previous valid_until. Explicit logout has no grace period — both the live and the just-rotated-out tokens die immediately.

### Behaviour change — introspect

[`app/api/v3/users/services/introspect.py`](../app/api/v3/users/services/introspect.py) — `_introspect_refresh()` now applies the same accept-either-jti rule. A refresh token is reported as `active: true` whether its jti matches the current slot or the previous slot (within grace).

### Repository methods

[`app/infrastructure/db/repositories/user_repository.py`](../app/infrastructure/db/repositories/user_repository.py):

- **New: `rotate_refresh_token(user_id, new_jti, new_expires_at, grace_seconds=0)`** — the unconditional rotation primitive. Captures outgoing jti as previous, writes new jti to live, all in one transaction. Pass `new_jti=None, grace_seconds=0` to clear everything (logout).
- **New: `get_refresh_metadata_with_grace(user_id) -> (current_jti, current_expires, previous_jti, previous_valid_until)`** — used by `refresh_tokens` and `_introspect_refresh`.
- **Kept: `update_refresh_token_metadata(...)`** — now a thin compat shim that delegates to `rotate_refresh_token` with `grace_seconds=0`. The `expected_old_jti` parameter is accepted but ignored — it was the source of the race we just fixed. No call site inside the auth services uses it after this rewrite; the shim exists in case external scripts / tests still reference it.

### Migration

New Alembic revision: [`alembic/versions/e7d2b3a4f981_add_refresh_token_grace_window_columns.py`](../alembic/versions/e7d2b3a4f981_add_refresh_token_grace_window_columns.py). Linear chain `c262a1b3e895 → e7d2b3a4f981`. Both new columns are nullable, so no data backfill is required for existing rows.

SQLite is handled by an extension to the existing drift-healer block in [`app/infrastructure/db/session.py`](../app/infrastructure/db/session.py): the two columns are added on boot if missing from `PRAGMA table_info('users')`.

## §3 — Operational notes

### Boot behaviour after deploy

Postgres: the boot sequence in [`app/infrastructure/db/session.py`](../app/infrastructure/db/session.py) runs `alembic upgrade head` automatically (per doc 18 §0), so the two new columns get added during startup with no manual intervention.

SQLite: the drift-healer adds them in-place on boot for any legacy on-disk `pmis.db` file.

### Security tradeoff

There is now a ≤120 s window during which two refresh tokens are valid for the same user — the just-rotated-out one and the freshly-issued one. This is the explicit cost of fixing the FE pain. Compared against the previous behaviour (single-writer atomic swap that locked legitimate users out), the tradeoff is favourable:

- **Before:** stolen-token replay was caught instantly (1 s after the legitimate refresh wins, the stolen-token call gets 401). Cost: legitimate users were also locked out under three normal patterns.
- **After:** stolen-token replay still gets 401, but only after the grace window closes. Cost: 120 s window where a stolen token is interchangeable with the legitimate one. Mitigation: tunable per environment via `REFRESH_TOKEN_GRACE_SECONDS` (could be tightened in higher-security envs).

The grace window does **not** weaken refresh-token TTL, expiry enforcement on the live slot, the access-token blacklist, or any unrelated auth invariant.

### What changes for the FE

**Nothing mandatory.** The whole point of this fix is to absorb the FE behaviours that were causing 401s without requiring the FE to change.

| FE behaviour | Before | After |
|---|---|---|
| Two concurrent /refresh calls (timer + 401-interceptor firing at once) | One 200, one 401 (logout dialog shown) | Both 200 |
| Re-login from another tab/device while a refresh is in-flight | Original RT instantly invalidated | Original RT valid for 120 s |
| Network retry queue holding a stale RT after rotation | 401 on retry | 200 on retry (within 120 s) |
| Stored RT replacement after successful refresh | Required | Required (unchanged) |
| /logout to end the session | Live RT cleared | Live + grace-slot RTs both cleared |

Optional FE-side improvements (defence-in-depth, not required):

- Serialize the refresh trigger so the timer + interceptor share a single in-flight Promise.
- Avoid auto-firing `/login` mid-session — each login still rotates the live jti and pushes the prior one into the grace slot for 120 s. It works, but it's wasteful.
- After successful refresh, replace BOTH stored tokens (already standard practice — calling it out because using the stale RT will hit the grace edge after 120 s).
