# Master-data router consolidation + divisions auto-insert removal + project_owners dropped

This document captures the catalog/master-data refactor that landed on top
of [doc 19](./19.%20refresh%20races%2C%20multi-tab%20login%2C%20and%20stale-token%20retries.md). Two
intertwined goals in a single user-driven change request:

| # | Author | Topic |
|---|---|---|
| 0 | **Chinmaya** | Stop auto-inserting user-supplied `ownerOther` labels into the divisions catalog. The free-text label still lives on the project row's `owner_other` column; what stops is the side-effect that mirrored every label into a divisions row (which had been producing rogue rows like `admin` / `test` from one-off project labels — directly responsible for tester Issue 41). The catalog is now strictly admin-managed. |
| 1 | **Chinmaya** | New consolidated `/api/v3/master/*` router that owns full CRUD for every catalog table. Four catalogs in scope: `divisions`, `project_status_transitions`, `resource_types`, `vendors`. The legacy per-catalog endpoints stay alive with a `Deprecation: true` HTTP header pointing at the successor URL. `project_owners` was removed entirely (table + repo + endpoints) — the whitelist had been dead since doc 18 made `project.owner` a strict division code. |

Final test count: **392 passed, 3 skipped** — up from doc 19's baseline of 361 / 3, a net +31 tests covering the full master-data CRUD surface plus the auto-insert-removal behavioural assertion (`tests/test_master_data.py`, 37 tests; offset by -6 tests removed from `tests/test_catalogs_and_other_reason.py` for the gone `TestProjectOwnersCatalog` and `TestDivisionsPersistedFromOwnerOther` classes — replaced with one negative-coverage class `TestOwnerOtherDoesNotPolluteDivisions`).

## §0 — Why this exists

The tester reported (Issue 41) that the project-owner dropdown contained `admin` and `test` rows that had no business being there. The root cause turned out to be a pair of design decisions that together produced the pollution:

1. The `divisions` catalog had an "auto-create on first use" path: when a project was created with `owner='others'` + a free-text `ownerOther='admin'`, the project create service called `DivisionRepository.upsert_user_division('admin')`, which slugified the label to `admin` and inserted a non-builtin divisions row. The next project's owner picker now showed `admin` as a selectable code.
2. The catalog had no admin-managed CRUD surface — the only way to mutate it was the auto-insert above. So once a bad label landed, no one could clean it up via the API.

Doc 20 splits the fix into two tightly-coupled changes:

- **Remove the auto-insert path** (Part 1). The catalog stops growing as a side-effect of project saves.
- **Add an admin CRUD surface** (Part 2). Admins can curate the catalog explicitly: add legitimate divisions, deactivate stale ones, restore ones deleted by mistake.

The user broadened Part 2's scope to "consolidate every catalog table under one router" in the same change. That captured `project_status_transitions` (admin-curated transition rules), `resource_types` (asg/ccn/rfp/...), and `vendors` (the existing entity, treated as master per the user's call that overrode the recommended exclusion). `work_package_types` was deliberately left out — the user noted work packages aren't being used in the project.

## §1 — Auto-insert removal (Part 1)

### Call sites removed

The auto-insert lived at three places in the project services:

- [app/api/v3/projects/services/create.py:212-216](../app/api/v3/projects/services/create.py#L212)
- [app/api/v3/projects/services/update.py:295-299](../app/api/v3/projects/services/update.py#L295)
- [app/api/v3/projects/services/upsert.py:171-175](../app/api/v3/projects/services/upsert.py#L171)

Each block was replaced with a comment explaining why the call was removed and pointing at the new admin endpoint. The `owner_other` text continues to be stored on the project row's `owner_other` column unchanged — the only thing that stops is the side-effect into the catalog.

### Repository method removed

`DivisionRepository.upsert_user_division()` (the slugify-and-insert primitive) was removed from [app/infrastructure/db/repositories/division_repository.py](../app/infrastructure/db/repositories/division_repository.py). No call site remains in the codebase.

### Behavioural test

[tests/test_master_data.py::TestOwnerOtherDoesNotPolluteDivisionsCatalog](../tests/test_master_data.py) snapshots the divisions catalog before and after a project create with `owner='others'` + `ownerOther='Marketing'`, asserts the catalog contents are identical, and asserts the project row does carry `ownerOther='Marketing'`. There's a parallel narrative-style test in [tests/test_catalogs_and_other_reason.py::TestOwnerOtherDoesNotPolluteDivisions](../tests/test_catalogs_and_other_reason.py) that replaces the deleted `TestDivisionsPersistedFromOwnerOther` class.

### Backwards behaviour

The two non-`others` `*Other` paths in the codebase did NOT have the same auto-insert and are unchanged:

- `categoryOther` → stored on the project row only; there's no `project_categories` catalog table.
- `divisionOther` on **users** and on **activity_resources** → stored on the row only; no catalog write.

## §2 — New `/api/v3/master/*` router (Part 2)

### Files added

```
app/api/v3/master_data/
  __init__.py          # 12 lines — exports master_data_router
  schemas.py           # ~140 lines — Pydantic create/update bodies per catalog
  routes.py            # ~470 lines — every CRUD endpoint, projection helpers
```

Plus a one-line registration in [app/api/router.py](../app/api/router.py).

### URL surface

| Catalog | Endpoints |
|---|---|
| Divisions | `GET /master/divisions`, `POST /master/divisions/create`, `PATCH /master/divisions/{code}`, `DELETE /master/divisions/{code}`, `POST /master/divisions/{code}/restore` |
| Project status transitions | `GET /master/project_status_transitions`, `POST /master/project_status_transitions/create`, `PATCH /master/project_status_transitions/{id}`, `DELETE /master/project_status_transitions/{id}`, `POST /master/project_status_transitions/{id}/restore` |
| Resource types | `GET /master/resource_types`, `POST /master/resource_types/create`, `PATCH /master/resource_types/{id}`, `DELETE /master/resource_types/{id}`, `POST /master/resource_types/{id}/restore` |
| Vendors | `GET /master/vendors`, `GET /master/vendors/{id}`, `POST /master/vendors/create`, `PATCH /master/vendors/{id}`, `DELETE /master/vendors/{id}`, `POST /master/vendors/{id}/restore`, `GET /master/vendors/{id}/projects` |

`include_inactive=true` query param on every list endpoint shows soft-disabled rows for admin views. Default list filters them out (matches the FE picker's behaviour).

### Vendor delegation

Vendor endpoints don't duplicate any logic — they import the existing handlers in [app/api/v3/vendors/routes.py](../app/api/v3/vendors/routes.py) and call them directly. The catch is that those handlers stamp a `Deprecation: true` header (since the legacy `/api/v3/vendors/*` URL is deprecated); the master-data wrapper strips that header before returning, since `/api/v3/master/vendors/*` IS the successor and must not advertise itself as deprecated. The strip is a 4-line helper in [app/api/v3/master_data/routes.py](../app/api/v3/master_data/routes.py) that removes the `Deprecation` and `Link` headers from the delegated response.

This avoids the impl-extraction refactor that would otherwise be needed across all seven vendor handlers, while keeping behaviour identical between the legacy and successor URLs.

### RBAC

Two new permissions added in [app/core/rbac.py](../app/core/rbac.py):

- `MASTER_DATA_VIEW` — granted to ADMIN, MEMBER, and VIEWER roles. Backs every `GET /master/*` endpoint.
- `MASTER_DATA_MANAGE` — granted to ADMIN only. Backs every POST / PATCH / DELETE / restore on `/master/*`.

The legacy per-catalog permissions (`VENDORS_READ` / `VENDORS_MANAGE`, `RESOURCE_TYPES_READ` / `RESOURCE_TYPES_MANAGE`) remain in place to keep the deprecated endpoints working.

### Soft-delete, with built-in protection

DELETE on every catalog is **soft** — sets `active=false`. Existing rows that reference the catalog (projects, users, activity_resources, project_vendors mappings) keep working; only the FE picker hides the deactivated row. Restore is exposed as `POST /master/{catalog}/{id}/restore` and just flips `active` back to true.

Built-in protection on divisions: `tmd1` / `tmd2` / `others` carry `is_builtin=true`. The route layer rejects PATCH (`label`/`requiresOther`) and DELETE on built-in rows with HTTP 403. The `code` itself is never patchable on any row — it's the wire identifier that every project's `owner` column points at; renaming would break every existing reference. Renames go through deactivate-and-create-new.

### Backwards-compat — `Deprecation: true` headers on legacy endpoints

A new `BaseController.stamp_deprecation()` helper (in [app/core/base_controller.py](../app/core/base_controller.py)) appends two HTTP headers to a response:

```
Deprecation: true
Link: </api/v3/master/divisions>; rel="successor-version"
```

The `Deprecation` header follows draft-ietf-httpapi-deprecation-header; the `Link` rel="successor-version" is RFC 8631. Both are widely understood by API client tooling.

Stamped on every response from:

- `GET /api/v3/divisions` ([catalogs/routes.py](../app/api/v3/catalogs/routes.py))
- `GET /api/v3/project_status_transitions` ([catalogs/routes.py](../app/api/v3/catalogs/routes.py))
- `GET /api/v3/resource_types` and `POST /api/v3/resource_types/create` ([resource_types/routes.py](../app/api/v3/resource_types/routes.py))
- All seven `/api/v3/vendors/*` endpoints ([vendors/routes.py](../app/api/v3/vendors/routes.py))

The FE can leave the calls untouched and notice the deprecation in DevTools, then migrate at its own pace. Removal of the legacy endpoints is **not** in scope for this doc.

### Repository extensions

Each catalog repository got new admin-CRUD methods:

- `DivisionRepository`: `create()`, `update()`, `set_active()`, `list_all()`, `get_by_code_any()`. Removed: `upsert_user_division()`.
- `ProjectStatusTransitionRepository`: `create()`, `update()`, `set_active()`, `list_all()`, `get_by_id()`, `find_edge_any()`.
- `ResourceTypeRepository`: `update()`, `set_active()`, `list_all()`, `get_model_by_id()`.

`VendorRepository` needed no extensions — the existing CRUD already supports everything the master_data router exposes via delegation.

## §3 — `project_owners` dropped (Part of §2)

The per-user project-owner whitelist became dead code in doc 18 when `project.owner` switched from a user-login reference to a strict division code. The catalog endpoints (`GET /project_owners`, `POST /project_owners/create`, `DELETE /project_owners/{user_id}`) and the underlying table were never consulted by any service-layer code after that change. Doc 20 removes them entirely:

- **Endpoints removed**: from [catalogs/routes.py](../app/api/v3/catalogs/routes.py). The file was rewritten to keep only the legacy `divisions` and `project_status_transitions` GET handlers (with deprecation headers).
- **Repository removed**: deleted [app/infrastructure/db/repositories/project_owner_repository.py](../app/infrastructure/db/repositories/project_owner_repository.py).
- **Model removed**: deleted [app/infrastructure/db/models/project_owner.py](../app/infrastructure/db/models/project_owner.py). Its import in `app/infrastructure/db/models/__init__.py` was dropped (with a comment explaining why).
- **Seed removed**: the bootstrap admin auto-seed into `project_owners` was deleted from [app/infrastructure/db/session.py](../app/infrastructure/db/session.py) (replaced with a comment).
- **Tests removed**: `TestProjectOwnersCatalog` and the `_add_admin_owner` helper in [tests/test_catalogs_and_other_reason.py](../tests/test_catalogs_and_other_reason.py). Replaced with `TestProjectOwnersRouterRemoved` in [tests/test_master_data.py](../tests/test_master_data.py) which asserts every legacy URL now returns 404.
- **Migration**: new Alembic revision [`f3c8a7b2d491_drop_project_owners_table.py`](../alembic/versions/f3c8a7b2d491_drop_project_owners_table.py). Linear chain `eea66b52f947 → f3c8a7b2d491`. Downgrade re-creates an empty table with the original schema (no row data restored — there were no functional consumers, so there was nothing to back up).

## §5 — Operational notes

### Boot behaviour after deploy

Postgres: the boot sequence in [app/infrastructure/db/session.py](../app/infrastructure/db/session.py) auto-runs `alembic upgrade head` (per doc 18 §0). The two new revisions (`eea66b52f947` merge from doc 19 + `f3c8a7b2d491` from doc 20) run in order; `project_owners` is dropped during startup with no manual intervention.

SQLite: `Base.metadata.create_all` no longer creates the `project_owners` table on a fresh DB (the model was deleted). On legacy on-disk dev `pmis.db` files the table will linger as an unused row of cruft; harmless, can be dropped manually if desired (`DROP TABLE project_owners`).

### What changes for the FE

Two distinct flavours of change:

1. **Optional migration** (no urgency): replace `/api/v3/divisions`, `/api/v3/resource_types`, `/api/v3/project_status_transitions`, `/api/v3/vendors/*` with the corresponding `/api/v3/master/*` URL. The body shapes are identical. Each legacy call now returns a `Deprecation: true` header that DevTools highlights. RBAC for the master endpoints uses `MASTER_DATA_VIEW` (read) / `MASTER_DATA_MANAGE` (write); both are bundled into the existing admin role.

2. **Mandatory removal** (immediate): stop calling `GET /api/v3/project_owners`, `POST /api/v3/project_owners/create`, and `DELETE /api/v3/project_owners/{id}`. They return 404 now. If the FE was using them anywhere, it would have been silently ignored anyway since the project create flow stopped consulting the whitelist in doc 18 — but explicit calls now visibly fail.

### Behavioural change visible to existing users

Pre-doc-20: creating a project with `owner='others'` + `ownerOther='Engineering'` would (a) create the project with that label, AND (b) silently add a `code='engineering', label='Engineering'` row to the divisions catalog. The next project could then pick `owner='engineering'` from the dropdown.

Post-doc-20: step (a) still happens. Step (b) does NOT. To make `engineering` available as a selectable owner code for future projects, an admin must explicitly call:

```
POST /api/v3/master/divisions/create
{"label": "Engineering"}
```

This is a change that needs to be communicated to users. The previous flow encouraged accidental catalog growth from typos and one-off labels (the source of the `admin`/`test` rows that triggered Issue 41); the new flow is intentional and reversible (admin can deactivate the row later).
