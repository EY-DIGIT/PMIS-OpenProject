# Doc 21 — Cross-milestone milestone dependencies + DB-driven RBAC

Two independent changes shipped in the same branch.

---

## Part A — Milestone-to-milestone dependencies

### Current state

- Activity, task, and subtask dependency edges already enforce *same-project*
  but allow *cross-milestone* targets — verified in
  `dependency_repository.existing_target_*` (filter is on `project_id` alone).
  No code change is needed for that part; we just add explicit tests to lock
  the behavior in.
- Milestones have a loose `depends` JSON column that was carried through the
  API as opaque strings. No referential integrity, no soft-delete, no cycle
  check, no propagation. Effectively unused as a feature.

### Target state

- A new `milestone_dependencies` edge table mirroring the
  `activity_dependencies` shape: surrogate UUID PK, `source_milestone_id`,
  `target_milestone_id`, `project_id`, `created_at`, `deleted_at`,
  `deleted_by`. Partial unique index on `(source, target) WHERE deleted_at IS
  NULL`.
- Repository methods on `DependencyRepository`:
  `list_milestone_dependencies`, `set_milestone_dependencies`,
  `existing_target_milestone_ids`, `would_create_cycle_milestone`,
  `cascade_remove_milestone_targets`.
- `MilestoneCreateRequest` / `MilestoneUpdateRequest`: replace the loose
  `depends` field with a typed `depends_on: List[str]` (alias `dependsOn`).
  Old `depends` JSON column kept readable but services stop writing to it
  and the response stops emitting it; the response now emits `dependsOn:
  [...]` from the edge table.
- Service-layer rules per existing convention:
  - same-project only (validated against `existing_target_milestone_ids`),
  - no self-edge,
  - no cycle (DFS over live edges),
  - replace-list semantics on PATCH.
- Cascade: when a milestone is soft-deleted, every live edge touching it is
  soft-deleted (`cascade_remove_milestone_targets`).
- Propagation: per the user's explicit answer (Q3), milestone-dependency
  edges propagate from baseline to active versions. This deliberately
  diverges from the existing pattern for activity/task/subtask deps (which
  are version-local). Implementation: when baseline edge B1→B2 is created or
  removed, locate each active version's twin pair (V1, V2) via
  `cloned_from_id` and mirror. New helpers in `baseline_version_sync.py`
  invoked from milestone create/update/delete services.
- Alembic migration creates the table.
- New tests in `tests/test_dependencies.py` cover:
  - cross-milestone activity/task/subtask deps explicitly succeed
  - milestone deps CRUD, same-project-only, no self-edge, cycle rejection
  - cascade on milestone delete soft-deletes touching edges
  - propagation: baseline edge → version twin edge

## Part B — DB-driven RBAC overhaul

### Current state

- `app/core/rbac.py` defines `Role` enum (4 values) and `Permission` enum
  (60+ values) plus a hard-coded `ROLE_PERMISSIONS` map.
- `users.admin: BOOL` short-circuits permission checks.
- JWT carries `role` and `is_admin` claims; auth middleware copies these to
  `request.state`.
- `require_permission(Permission.X)` decorator uses `has_permission(role,
  perm)` — pure in-memory dict lookup.
- `RoleModel` table exists but its `permissions` JSON column is unused for
  enforcement.

### Target state

#### Tables (new)

- `permissions` — code (PK string, e.g. `"projects:create"`), name, description,
  is_builtin, created_at, updated_at.
- `role_permissions` — role_id, permission_code (composite PK).
- `user_roles` — user_id, role_id (composite PK).
- `user_permissions` — user_id, permission_code (composite PK). Direct grants,
  additive to role-derived grants.

`RoleModel` keeps its existing `id`/`name`/`builtin` columns; the JSON
`permissions` column is dropped (replaced by the join table).

#### Drop `users.admin` column

After data migration: every user with `admin=True` gets assigned to the new
seeded `admin` role. The column is dropped. Bootstrap admin user (login
`admin`, password `admin123`) gets the admin role at init time.

#### Permission enforcement

- A constants module `app/core/permissions.py` exposes every permission code
  used by the codebase (the full set currently in `rbac.Permission`, plus the
  new RBAC-management codes listed below). This is the canonical *list of
  codes routes can check*.
- `require_permission` becomes a string-taking dependency:
  `require_permission("projects:create")`. The decorator looks up
  `request.state.user_permissions: Set[str]` (populated once per request by
  auth middleware via one DB query) and accepts/rejects accordingly.
- Auth middleware: after JWT decode, calls
  `RbacRepository.effective_permissions_for_user(user_id)` once and stores
  the result on `request.state`. Anonymous requests have an empty set.
- JWT no longer carries `role` or `is_admin`. The minimal claims become
  `{sub, user_id, email, jti, exp}`. Existing tokens issued before the
  rework keep working — the `role`/`is_admin` claims are simply ignored.

#### Startup sync

In `init_db`, after table creation:
1. Upsert every code in `app/core/permissions.py` into the `permissions`
   table (insert if missing, mark `is_builtin=True`). Existing rows for
   codes no longer in the registry are left untouched (allows graceful
   removal).
2. Ensure the `admin` role exists (`is_builtin=True`).
3. Ensure the `admin` role holds *every* permission code currently in the
   registry — automatically picks up newly added permissions on each boot.
4. Seed `member` and `viewer` roles with the current `ROLE_PERMISSIONS`
   mapping (also `is_builtin=True`, but deletable).
5. Bootstrap user `admin/admin123`: ensure `user_roles(admin_user, admin
   role)` row exists.

#### Protection rules

- `admin` role cannot be deleted, renamed, or have its permission list
  modified via API (returns 403). All other roles, including the seeded
  `member`/`viewer`, are fully editable.
- Lockout protection: any operation that would leave zero non-deleted users
  holding the `admin` role is rejected (mirrors the existing admin-lockout
  guard on user delete).
- Bootstrap admin user is itself deletable (subject to the lockout above) —
  matches the user's intent of being able to remove it once production
  admins are provisioned.

#### API surface

New module `app/api/v3/permissions/`:
- `GET    /api/v3/permissions` — list (paged)
- `POST   /api/v3/permissions` — create custom permission
- `GET    /api/v3/permissions/{code}` — get
- `PATCH  /api/v3/permissions/{code}` — edit name/description (code immutable)
- `DELETE /api/v3/permissions/{code}` — delete (blocks builtins)

Extend `app/api/v3/roles/`:
- `GET    /api/v3/roles/{id}/permissions` — list role's permissions
- `PUT    /api/v3/roles/{id}/permissions` — replace whole set (body:
  `{"permissions": ["projects:create", ...]}`)
- `POST   /api/v3/roles/{id}/permissions/{code}` — grant single
- `DELETE /api/v3/roles/{id}/permissions/{code}` — revoke single

Extend `app/api/v3/users/`:
- `GET    /api/v3/users/{id}/roles` — list user's roles
- `POST   /api/v3/users/{id}/roles/{role_id}` — assign role
- `DELETE /api/v3/users/{id}/roles/{role_id}` — unassign role
- `GET    /api/v3/users/{id}/permissions` — effective permissions
  (role-derived ∪ direct)
- `POST   /api/v3/users/{id}/permissions/{code}` — grant direct permission
- `DELETE /api/v3/users/{id}/permissions/{code}` — revoke direct permission
- `GET    /api/v3/users/me/permissions` — current user's effective set
  (used by FE to draw UI; bypasses RBAC manage permission)

New permissions for the management endpoints themselves:
- `permissions:read`, `permissions:manage`
- `rbac:assign` — covers user-role and user-permission assignments

#### Migration strategy

Alembic revision creates new tables. A separate data step (in the same
revision) does:
1. Create the four new tables.
2. Insert seed rows for all known permission codes.
3. Create seed roles (`admin`, `member`, `viewer`) with their permission
   sets.
4. For every existing user with `admin=True`: insert
   `user_roles(user.id, admin_role.id)`.
5. Drop `users.admin` column.

SQLite drift healer in `session.py` handles the column drop on dev.

#### Test impact

- `tests/conftest.py` admin/member fixtures: use the new flow (assign role
  via DB after creating user) and stop setting `admin=True` on the model.
- New `tests/test_rbac.py` covering: permission CRUD, role-permission
  assignment, user-role and user-permission assignment, effective
  permissions, lockout protection, admin-role protection, decorator
  behavior.
- Existing tests should pass once conftest is updated — none of them
  directly assert on `users.admin` column or the `role` JWT claim.

## Out of scope

- Per-project / per-resource scoped permissions. Everything stays global.
- Permission *deny* lists — additive grants only.
- UI for permission management — backend-only.
