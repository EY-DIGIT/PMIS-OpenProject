# Doc 22 — Display labels for M/A/T/S + dependsOn casing parity

## Why

Two related issues from FE / FE→BE contract review (May 2026):

1. The activity-create endpoint requires UUIDs for `dependsOn`, but the
   FE has been sending human-readable labels like `"A2.1"` because that's
   what its dependency-picker UI shows. Result: every create with a
   selected dependency 422s with `"Unknown or out-of-project activity
   dependency target(s): A2.1"`.

2. The milestone schemas accepted both `depends_on` and `dependsOn` on
   input via `validation_alias=AliasChoices(...)`, while
   activity/task/subtask schemas accepted only `dependsOn` via plain
   `alias`. Wire-level behavior was equivalent (both shapes worked on
   milestones; only camelCase worked on M/A/T/S) but the schema *style*
   differed across entities, which read as inconsistency.

## Out of scope

- Renaming Python internal `depends_on` snake_case variables to camelCase.
  Snake_case is correct PEP 8 and never crosses the wire.
- Reworking how `position` reorder cascades to dependency display.
  Reorder updates labels automatically on the next read; that's the
  feature, not a bug.
- Mirroring this work to the `pmis-project-service` microservice. Will
  be ported in a follow-up commit once monolith parity is verified.

## Label format

| Entity | Format | Example |
|--------|--------|---------|
| Milestone | `M{m}` | `M1`, `M2` |
| Activity | `A{m}.{a}` | `A1.2` (activity 2 under milestone 1) |
| Task | `T{m}.{a}.{t}` | `T1.2.3` |
| Subtask | `S{m}.{a}.{t}.{s}` | `S1.2.3.4` |

Where each digit is the **1-based rank** of the entity by
`(position ASC, id ASC)` among its **live** (non-soft-deleted) siblings.
Soft-deleted siblings are skipped, so deleting a middle activity shifts
the labels of every subsequent activity.

The new partial-unique index `(parent_id, position) WHERE deleted_at IS
NULL` (added in Alembic revision `c4d9a1b3e201`) guarantees that no two
live siblings ever share a position, so label resolution is unambiguous.

## API contract

### Inputs (`dependsOn` field on create / update)

Accepts a list of strings. Each string can be **either a UUID** OR a
**display label** in the format above. Mixed lists are allowed:

```json
{ "dependsOn": ["A1.2", "11d8e9f4-2c5e-44a1-b3a0-2c4b8b3e0a01"] }
```

The service resolves labels to UUIDs at write time (single DB lookup
per label). Stored representation is always the UUID.

Errors:

| Condition | HTTP | errorIdentifier | Message |
|-----------|------|-----------------|---------|
| Label syntactically invalid (e.g. `"A1"` for an activity, `"X1"`) | 422 | ValidationError | `"Invalid dependency label: 'X1'. Expected M{n} / A{m}.{a} / T{m}.{a}.{t} / S{m}.{a}.{t}.{s}."` |
| Label syntactically valid but no entity matches | 422 | ValidationError | `"Unknown or out-of-project ... dependency target(s): A99.1"` (same wording as today) |
| UUID syntactically valid but unknown | 422 | ValidationError | (same wording) |

### Outputs (every M/A/T/S response)

Every milestone, activity, task, subtask response — single GET, list,
tree node, create response, update response — gains:

| Field | Type | Meaning |
|-------|------|---------|
| `displayCode` | `string` | This entity's own label (e.g. `"A1.2"`) |
| `dependsOn` | `List[string]` | Existing — list of dependency UUIDs |
| `dependsOnDisplay` | `List[string]` | New — labels for the same dependencies, in the same order |

Examples:

```json
// Activity
{
  "id": "11d8e9f4-2c5e-44a1-b3a0-2c4b8b3e0a01",
  "displayCode": "A1.2",
  "name": "Vendor onboarding",
  "dependsOn": ["7c5f2…"],
  "dependsOnDisplay": ["A1.1"],
  ...
}

// Tree node
{ "id": "...", "displayCode": "T1.2.3", "dependsOn": [...], "dependsOnDisplay": [...] }
```

## FE migration guidance

- **For sending dependencies**: prefer UUIDs (the `dependsOn` field
  from the previous read). Send labels only when collecting fresh user
  input — and never echo back `dependsOnDisplay` from a read as the
  next write's `dependsOn`, because labels can drift between read and
  write if the user reorders / deletes siblings between the two calls.
- **For displaying dependencies**: read `dependsOnDisplay` from any
  response. Don't recompute client-side from raw `position` numbers.
- **For displaying an entity's own label**: read `displayCode` from
  the response.

## Test coverage (`tests/test_labels.py`)

- Format parsing: valid / malformed / wrong-depth / wrong-prefix
- Single-entity create with label input → 201, persisted as UUID, response shows label
- Mixed UUID + label input → resolved correctly
- List response includes `displayCode` for every entity + `dependsOnDisplay` for every dep
- Tree response includes labels at every nesting level
- Delete shifts labels on next GET (soft-delete semantics)
- Cross-milestone label dep (`A2.1` depending on `A1.1`) works
- Unknown label returns 422 with the exact label string in the message
- Position uniqueness constraint blocks duplicate live positions (DB-level guarantee for label unambiguity)
