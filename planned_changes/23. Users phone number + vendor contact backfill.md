## Scope

Two FE-driven contact-detail asks bundled together:

1. **Add `users.phone_number`** column. Required at the wire on user
   create (Pydantic-level), optional on update.
2. **Make `vendors.phone_number`** required at the wire on vendor
   create. The column already existed (added in doc 18 alongside
   `email` and `contact_person`); doc 23 just flipped the schema-side
   `Optional[str]` to a required field.

Both follow the same nullable-DB / required-API pattern used elsewhere
in the codebase: the column stays nullable in PostgreSQL so the
bootstrap admin row and any legacy pre-feature rows remain valid, but
the Pydantic create schema rejects requests that omit the field.

## Implementation

### `users.phone_number`

- Migration: `alembic/versions/d8e1f3a4b502_doc23_add_users_phone_number.py`
  - `op.add_column("users", sa.Column("phone_number", sa.String(50), nullable=True))`
  - Idempotent — wrapped in an `_has_column(inspector, "users", "phone_number")`
    check so re-running against an already-migrated DB is a no-op.
- Model: `users.phone_number = Column(String(50), nullable=True)`.
- Schema (`UserCreateRequest`): `phoneNumber: str` — REQUIRED at the wire.
- Schema (`UserUpdateRequest`): `phoneNumber: Optional[str]` — leave alone unless the caller sends one.
- Response shape: every user-bearing endpoint includes `phoneNumber`
  (`GET /users`, `GET /users/{id}`, `GET /users/me`, login response,
  etc.).

### `vendors.phone_number`

- Column already existed since doc 18 (`alembic/versions/d4f1a8c5b6e7_add_vendor_contact_columns.py`).
  Doc 23 only changed the Pydantic side.
- Schema (`VendorCreateRequest`): `phoneNumber: str` — REQUIRED.
- Schema (`VendorUpdateRequest`): `phoneNumber: Optional[str]` — preserve existing.
- The required-on-create rule applies to both `/api/v3/master/vendors/create` and
  the legacy `/api/v3/vendors/create` (both share the same Pydantic schema).

## Why two-in-one

The FE picker UI for "owner / contact" needed phone numbers populated
for both users (assignees, project owners) and vendors (project
vendors). Splitting into two docs would have meant two coordinated FE
releases to enable both halves; bundling kept the rollout atomic.
