# Doc 24 — Past start dates, nested subtasks, no-hierarchy dependencies

Three independent changes shipped in the same branch.

---

## Part 1 — Project start_date can be in the past

### Current state

[app/api/v3/projects/schemas.py](app/api/v3/projects/schemas.py) duplicates a
`validate_dates_in_future` validator on `("start_date", "end_date")` in
three classes (`ProjectCreateRequest`, `ProjectUpdateRequest`,
`ProjectUpsertRequest`). Both fields must be strictly greater than `now`.

### Target state

The validator runs only on `end_date`. `start_date` accepts any datetime.
The existing `start_date <= end_date` check stays. So a project that
started in the past but has not yet ended is now creatable.

End_date keeps the future-only requirement — completed projects are out
of scope here; if the user wants to enter historical projects later we
can revisit.

## Part 2 — Subtasks under subtasks (unlimited nesting)

### Current state

`SubtaskModel` has `task_id` FK to `tasks` and no parent-subtask pointer.
Subtasks are flat under a task. The position-uniqueness index is
`(task_id, position) WHERE deleted_at IS NULL`.

### Target state

A subtask can have either a task (top-level) OR another subtask (nested)
as its parent — modeled by **adding** `parent_subtask_id String(36)`
nullable FK to `subtasks.id`. The existing `task_id` column still always
holds the **root task** id so:

- "all subtasks under task X" stays a one-column-filter query
- the version-only writability guard (`assert_task_subtask_writable`,
  which loads the project from `task_id`) keeps working unchanged
- the soft-delete cascade tied to the parent task still finds every
  descendant in one pass

XOR semantics: top-level subtasks have `parent_subtask_id = NULL`,
nested subtasks have `parent_subtask_id <> NULL`.

#### New endpoint

```
POST /api/v3/subtasks/{parent_subtask_id}/subtasks/create
```

Identical body to the existing task-scoped create. The service infers
the root `task_id` from the parent subtask. Response shape includes
`parentSubtaskId` (new) alongside `taskId`.

The existing `POST /api/v3/tasks/{task_id}/subtasks/create` continues to
create top-level subtasks (parent_subtask_id stays NULL).

#### Position uniqueness

The single index `uq_subtasks_task_position_live` is replaced by two
partial-unique indexes that together preserve label unambiguity:

- `uq_subtasks_task_position_top_live` on `(task_id, position) WHERE
  deleted_at IS NULL AND parent_subtask_id IS NULL` — unique among
  top-level siblings under a task.
- `uq_subtasks_subtask_position_live` on `(parent_subtask_id, position)
  WHERE deleted_at IS NULL` — unique among children of any one subtask.

#### Configurable depth cap

New env-driven setting `SUBTASK_MAX_NESTING_DEPTH: Optional[int] = None`
in `app/core/config.py`. When `None` (default) nesting is unlimited.
When set, `create_subtask_under_subtask` walks up the parent chain, and
if creating a child would push the path length past the configured cap,
returns 422 with a clear error.

#### Cascade-on-delete

`SubtaskRepository.soft_delete_with_cascade` extends to recursively
soft-delete every descendant subtask. Iterative BFS to avoid recursion
limits at extreme depths. Dependency edges across the descendant set are
wiped via `DependencyRepository.cascade_remove_subtask_targets` per
descendant.

#### Labels

[app/shared/labels.py](app/shared/labels.py) extends the subtask label
format from `S{m}.{a}.{t}.{s}` to `S{m}.{a}.{t}.{s1}[.{s2}.{s3}…]`,
where each `sN` is the 1-based rank of the subtask among its siblings
(by `(position, id)` ordering) at that depth. The label index walks the
`parent_subtask_id` chain to compose the segments.

#### Tree endpoint

`GET /api/v3/projects/{id}/tree` recursively nests subtasks under their
parent subtask (currently flat under the parent task). Each tree node
keeps `displayCode` + `dependsOn` + `dependsOnDisplay` per the doc 22
contract.

#### Resource subtasks can have children

No type-based restriction on having descendants. A `type=resource`
subtask can have any number of nested subtasks beneath it. Resource
fields only constrain its own row.

#### Migration

Alembic revision adds the `parent_subtask_id` column + FK, drops the
old single position-uniqueness index, and creates the two new partial
indexes. SQLite drift healer picks up the column add automatically.
Existing subtask rows have `parent_subtask_id = NULL` (all top-level) —
no data migration needed.

## Part 3 — Drop dependency hierarchy rules across activity/task/subtask

### Current state

Three escalating constraint layers exist on dependency edges:

| Layer | Tasks check | Subtasks check |
|-------|-------------|----------------|
| Same project | yes | yes |
| No self / no cycle | yes | yes |
| **Parent must be linked** | source's parent activity must depend on target's parent activity (or same activity) | source's parent task must depend on target's parent task (or same task) |

The third layer lives in:
- `app/api/v3/tasks/services/{create,update}.py` — `_validate_task_deps_hierarchy`
- `app/api/v3/subtasks/services/{create,update}.py` — `_validate_subtask_deps_hierarchy`

### Target state

The third layer is removed entirely. Tasks and subtasks now follow the
exact same rule activities already follow:

- same project required
- no self-edge
- no cycle in the live edge graph
- target must be live

That's it. Cross-activity, cross-task, cross-parent — all allowed as
long as both endpoints are in the same project.

The hierarchy helpers (`_validate_task_deps_hierarchy`,
`_validate_subtask_deps_hierarchy`) and the
`DependencyRepository.task_pair_is_dependent` /
`activity_pair_is_dependent` helpers go unused after this change. The
helpers are deleted; the repository methods are kept for now (no
callers but harmless) and can be removed in a follow-up.

### Test impact

Tests in `tests/test_dependencies.py` that asserted the hierarchy rule
(e.g. `TestTaskDeps::test_target_task_under_unlinked_activity_rejected`,
`TestSubtaskDeps::test_target_subtask_under_unlinked_task_rejected` and
similar) flip from `422` to `201`. Updated to assert the relaxed
behavior.

## Out of scope

- Renaming subtask `task_id` to `root_task_id`. The current name still
  describes the intent ("the task this subtree lives under"); rename
  would churn every reader.
- Cross-version dependencies. Subtasks are version-local; deps still
  must be intra-version.
- Reparenting endpoint (move a subtask under a different parent). Only
  the create flow accepts a parent; existing rows are immutable on
  parent.
