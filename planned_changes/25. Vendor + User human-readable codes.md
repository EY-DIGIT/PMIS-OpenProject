# Doc 25 — Human-readable identifier codes for Vendor + User

Tester complaint: "Vendor ID is taking a big UUID. It must not look like
a session ID." Same problem reported for User where the FE shows raw
auto-increment integers (`1`, `2`, `3`).

Fix: add a human-readable code column to both entities, in the same
spirit as `project_code`. The existing UUID / integer `id` stays as the
canonical machine identifier (FK target, primary key, all internal
joins). The new code is what UI / search / cross-entity references
display to humans.

---

## Format

```
{prefix}-{slug}-{ist_timestamp}[-{collision_n}]
```

| Part        | Value                                  | Example          |
|-------------|----------------------------------------|------------------|
| `prefix`    | `VN` for vendor, `US` for user          | `VN`             |
| `slug`      | First 4 alphanumerics of the source field, uppercased, padded with `0` | `ACME` |
| `timestamp` | `YYMMDDHHMMSS` in IST (UTC+05:30)       | `260502143015`   |
| `-N`        | Optional `-2`, `-3`, … on collision     | `-2`             |

- **Vendor source field**: `name` → e.g. `"Acme Corporation"` ⇒ `ACME`.
- **User source field**: `login` → e.g. `"adminlike"` ⇒ `ADMI`.

Examples:

```
VN-ACME-260502143015
US-ADMI-260502143015
US-Z000-260502143015         # short login padded with zeros
VN-0000-260502143015         # punctuation-only name falls back
VN-ACME-260502143015-2       # collision against an earlier row
```

Total length: 20 chars (no collision suffix). The format is unambiguous
because the slug never contains `-` (regex strips it during slug
generation), and the timestamp is fixed-width.

## API impact

### Zero breaking changes

Every existing call site keeps working unchanged:

- `GET /api/v3/vendors/{uuid}` — still returns the vendor, now with an
  extra `vendorCode` field in the response.
- `GET /api/v3/users/{int}` — same.
- `POST /api/v3/users/create` with `vendorId: <uuid>` — still works.
- `POST /api/v3/projects/create` with `vendorIds: [<uuid>, ...]` —
  still works.

### New abilities

- `GET /api/v3/vendors/VN-ACME-260502143015` — same shape, code as path.
- `GET /api/v3/users/US-ADMI-260502143015` — same shape.
- `PATCH`, `DELETE`, `POST /restore` paths all accept either form.
- `POST /api/v3/users/create` with `vendorId: "VN-ACME-260502143015"` —
  resolves to the canonical UUID before writing the FK.
- `POST /api/v3/projects/create` with `vendorIds: [<uuid>, "VN-..."]` —
  mixed UUID + code in the same list works; the persisted FKs are all
  canonical UUIDs.

### Response additions

}

## Migration behavior

Both migrations follow the same shape:

1. `ALTER TABLE … ADD COLUMN <col> VARCHAR(50)` (nullable).
2. Backfill every row where the new column is NULL — compute the code
   from `(source_field, created_at)`, append `-N` on collision.
3. `CREATE UNIQUE INDEX uq_…_<col> ON … (<col>)`.

All three steps run in one alembic transaction. If step 2 raises, step
1 rolls back too — no half-migrated state. Inspector checks make every
step idempotent so re-running the migration on an already-migrated DB
is a no-op (same pattern as every other migration in this chain).

The backfill is **deterministic**: the same row produces the same code
on every re-run. So a DR rebuild from a SQL dump (or a migration
re-run after a partial failure) reconstructs the same codes.

The unique-index step is the DB-level guard against future code
collisions; the Python-side `generate_unique_code` is the proactive
guard. Belt-and-braces.

### SQLite dev DBs

The drift healer in `app/infrastructure/db/session.py` adds the two
new columns inline so legacy on-disk `pmis.db` files keep booting.
Backfill on SQLite is left to the next normal create / repository
call (the column is nullable; the picker handles NULL gracefully).

## Out of scope (for this doc)

- The integer `users.id` stays as-is. Codes are display-only; the
  integer is still the FK target for `project_members`,
  `user_roles`, audit logs, etc.
- The vendor UUID stays as-is for the same reason.
- The format chosen is intentionally close to `project_code` for
  visual consistency in admin UIs that show all three side by side.
