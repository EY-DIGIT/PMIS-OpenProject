# Doc 26 — `users.id` flipped from Integer to UUID String(36)

Senior reviewer rule: every public-facing identifier must be a UUID, not
an auto-incrementing integer. Vendors / projects / milestones / tasks /
subtasks / activities / comments / attachments / dependencies already
use UUIDs. The only remaining hold-out was `users.id` — visible to the
tester as raw `1`, `2`, `3` integers in the Search Users grid and in
every embedded `createdBy` / `actorId` / `assigneeId` / `userId` field
across the API.

This commit flips it.

The doc 25 `userCode` (`US-XXXX-YYMMDDHHMMSS`) stays as the
human-readable display identifier; this commit only changes the
underlying machine ID's type from `Integer autoincrement` to UUID
`String(36)`.

---

## Scope

### Tables flipped

Just **`users`**. Everything else with an integer PK (meetings,
work_packages, project_members, roles, divisions, etc.) was explicitly
left alone — those modules are either not in product use or their PKs
are admin-only catalog rows that never appear in user-facing IDs.

### FK columns retyped (Integer → String(36))

Every column that previously held a `users.id` foreign key — ~30
columns across the schema:

```
vendors.deleted_by
projects.created_by                 milestones.created_by
projects.updated_by                 milestones.updated_by
projects.deleted_by                 activities.created_by
project_audit_logs.actor_id         activities.updated_by
project_members.user_id             tasks.created_by
comments.author_user_id             tasks.updated_by
comments.deleted_by                 subtasks.created_by
attachments.uploaded_by_user_id     subtasks.updated_by
attachments.deleted_by              users.deleted_by  (self-FK)
activity_dependencies.deleted_by    user_roles.user_id  (composite PK)
task_dependencies.deleted_by        user_roles.created_by
subtask_dependencies.deleted_by     user_permissions.user_id  (composite PK)
milestone_dependencies.deleted_by   user_permissions.created_by
revoked_tokens.user_id              meetings.created_by_id
work_packages.assignee_id           meeting_participants.user_id
```

The "leave alone" tables (meetings, work_packages, meeting_participants)
still own integer PKs of their own — only their FK columns to `users.id`
get the type change.

---

## Why this works without breaking anything

1. **The PK column default is `lambda: str(uuid4())`** — every fresh
   row gets a UUID at insert time, just like vendors/projects.
2. **`UserRepository.create()` already used the column default** — it
   never assigned `id` explicitly, so no code change was needed there.
3. **The polymorphic lookup gets simpler.** Doc 25's `get_by_id_or_code`
   used to dispatch on "is this a US-... code or an int-coercible
   string?". Post-doc-26 it dispatches on "is this a US-... code or a
   UUID string?" — identical to vendor's `get_by_id_or_code`. The int
   coercion branch is gone.
4. **JWT claims pass through as strings.** `create_access_token` accepts
   a generic dict; the `user_id` field is whatever the caller passes.
   Auth middleware reads it back as-is from `payload.get("user_id")`
   and stamps it on `request.state.user_id`. No JSON-encoding surprise
   either way.
5. **Response builders are duck-typed.** `format_user_response` does
   `user_data.get("id")` and emits whatever's there. Same for embedded
   `createdBy` / `actorId` blocks. No change needed in response code.

## API impact

### Zero breaking changes for any caller using user_code lookups

`GET /users/{userCode}` works identically — doc 25 polymorphism
preserved.

### Hard breaking change for callers using integer ids in the path

`GET /users/1` no longer resolves — `1` is not a UUID and not a
US-code. The FE must use either the UUID returned in the response or
the user_code added in doc 25.

### JWT tokens minted before the migration are invalid

Their `user_id` claim is an integer that no longer matches any
`users.id` row (every row got a fresh UUID during the migration).
Users have to re-log in once. Same pattern as the project_id UUID
flip.

### Response payloads — every user-id-bearing field now carries a UUID string

```jsonc
// Before doc 26
{ "id": 1, "createdBy": 5, "actorId": 5 }

// After doc 26
{
  "id": "8bd99f06-5f2a-424c-aaff-10ab163c3e42",
  "createdBy": "11c5d2a4-9e3b-4f8d-9c2a-3f8e1c0b4a7d",
  "actorId": "11c5d2a4-9e3b-4f8d-9c2a-3f8e1c0b4a7d"
}
```

The doc 25 `userCode` field stays untouched in every user response.

## Migration behavior

### Postgres

Single-transaction sweep:

1. Add `users.id_new VARCHAR(36)`, populate with `uuid4()` per row.
2. For every dependent FK column, add `<col>_new VARCHAR(36)` and
   backfill via `UPDATE … FROM users u WHERE … = u.id`.
3. Drop FK constraints + composite PK constraints (user_roles +
   user_permissions).
4. Drop legacy columns; rename `<col>_new` → `<col>`.
5. Re-add PK on `users(id)` and composite PKs on the junction tables.
6. Re-add FK constraints across every dependent column.

If anything fails, the whole transaction rolls back to the
pre-migration shape. Idempotent — gated on a column-type inspection
so re-runs are no-ops.

### SQLite

Migration is a **no-op** (skipped via dialect check). The model
definitions already use `String(36)`, so:

- **Tests** create fresh in-memory DBs via `Base.metadata.create_all()`
  — they pick up the new shape automatically.
- **Legacy on-disk `pmis.db`** files need a wipe-and-rebuild. Same
  precedent as the project_id UUID flip and the task_dependency v2
  schema rebuild. The drift healer can't retype a column in place.

## Out of scope

- The other integer-PK tables (meetings, work_packages,
  meeting_participants, project_members, roles, divisions,
  project_status_transitions, project_audit_logs surrogate id) stay
  integer. Per the senior's earlier decision, only `users.id` is
  product-facing enough to require the UUID treatment right now.
- The downgrade is a no-op. Reverting would require re-numbering UUID
  rows back to integers (impossible without losing identity) plus
  invalidating every JWT issued post-migration. If a rollback is
  genuinely needed, restore from a pre-migration DB snapshot.
