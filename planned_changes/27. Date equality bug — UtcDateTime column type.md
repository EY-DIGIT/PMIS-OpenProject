# Doc 27 — Date-equality bug fix via `UtcDateTime` column type

## The bug

Tester report: *"If I give same start date and end date for project and
milestone of the project, it shows error and won't let me save."*

What was actually happening: when the FE sent `2026-07-10T00:00:00+05:30`
(IST midnight) for both project create and milestone create — the same
calendar date — the BE rejected the milestone with
`"Milestone start date cannot be before the project start date (2026-07-10)."`

## Root cause

`SQLAlchemy`'s `Column(DateTime, ...)` maps to `TIMESTAMP WITHOUT TIME
ZONE` on Postgres (and a plain string on SQLite). When a tz-aware
datetime hits the column on the bind path, the driver **silently drops
the offset and stores only the wall-clock value**:

```
INPUT:  2026-07-10T00:00:00+05:30   (IST midnight = 2026-07-09 18:30 UTC)
STORED: 2026-07-10 00:00:00          (the wall clock, tz info gone)
```

On read, SQLAlchemy returns a naive `datetime(2026, 7, 10, 0, 0)`.

Then in `app/shared/date_rules.py`, the `_normalize` helper handles the
two sides differently:

| Source | tzinfo | `_normalize` does | Result |
|--------|--------|-------------------|--------|
| Project (from DB) | None | passes through unchanged | `2026-07-10 00:00` (interpreted as UTC) |
| Milestone (from request) | +05:30 | converts to UTC, strips tz | `2026-07-09 18:30` |

Comparison: `milestone_start (Jul 9 18:30) < project_start (Jul 10 00:00)` → True → REJECTED.

The user picked the same calendar date in IST for both forms but the BE
saw them 5h30m apart. This bug fires on any FE that uses an IST-locale
date picker — which is the entire PMIS front end.

## Fix

Convert datetimes to canonical naive UTC at the **storage boundary**,
*before* the driver sees them. This guarantees the DB always holds UTC,
which is what `_normalize` and `ensure_aware_utc` already assume for
naive values.

Implemented as a SQLAlchemy `TypeDecorator`:

### NEW — `app/infrastructure/db/utc_datetime.py`

```python
class UtcDateTime(TypeDecorator):
    impl = DateTime
    cache_ok = True

    def process_bind_param(self, value, dialect):
        if value is None or not isinstance(value, datetime):
            return value
        if value.tzinfo is not None:
            value = value.astimezone(timezone.utc).replace(tzinfo=None)
        return value

    def process_result_value(self, value, dialect):
        return value
```

34 model files swept: each `Column(DateTime, …)` → `Column(UtcDateTime, …)`,
plus the `from ..utc_datetime import UtcDateTime` import added.

## Why a TypeDecorator (vs. service-layer normalization)

- **Single source of truth.** One place enforces the canonical form, no
  matter which service / repo / admin script writes a row.
- **No migration needed.** The Postgres column type stays
  `TIMESTAMP WITHOUT TIME ZONE`; only the Python-side bind logic changed.
- **Backward compatible reads.** Reads still return naive datetimes
  (matches the existing `_normalize` assumption that naive = UTC).
- **Future-proof.** Any new endpoint / migration / data-import script
  that goes through SQLAlchemy automatically inherits the normalization.

## What this changes for the API

### User-visible: bug is fixed

`POST /milestones/create` with `startDate` and `endDate` matching the
parent project's now succeeds. Same goes for activity vs milestone, task
vs activity, subtask vs task. The "extreme dates" cases the user
reported all work.

### Storage shape (Postgres + SQLite both)

Old behavior: an IST midnight was stored as `2026-07-10 00:00:00` (the
wall clock, tz-info dropped).

New behavior: an IST midnight is stored as `2026-07-09 18:30:00`
(canonical UTC).

### Existing rows

Rows written before this commit keep their wall-clock-IST values. They
will compare correctly against new tz-aware requests *only if the
wall-clock value happens to match what the new request would normalize
to* — which is unlikely. In practice, on any environment with
pre-existing data, you may see edge-case comparison drift on the old
rows. Two options:

1. **Accept the drift** — the FE always sends the same offset, so for
   any single-row equality the new write fixes the row going forward.
   PATCH operations rewrite both ends and the row becomes canonical.
2. **One-time data fix** — run a SQL migration that subtracts 5h30m
   from every datetime column on legacy rows. We did **not** ship this
   migration because the dev DB is wiped between major changes anyway,
   and shared Postgres has no real data yet.

If the user wants the data-fix migration, ask and I'll write it.

## Out of scope

- The "scenario C" mismatch (project sent naive, milestone sent IST in
  the same flow) is not a real FE pattern — date pickers are consistent
  per locale. If we ever build a multi-region FE, revisit.
- The `<= now` "Date must be in the future" check on project end_date
  (in `projects/schemas.py`) is unchanged. That rejection is about
  absolute time, not about milestone-vs-project equality, so it's
  unrelated to this bug.
