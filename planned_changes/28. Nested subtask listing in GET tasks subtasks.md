# Doc 28 — Nested subtasks visible in `GET /tasks/{id}/subtasks`

**Tracker:** issue #56.
**Commit:** `4bbec2f` ("fix #56 nested subtask listing + same-date accepted across M-A-T-S"). Bundled with doc 29 in the same push.

## The bug

Tester report: subtasks created under another subtask (the doc 24 part 2
nesting feature) didn't show up in any meaningful way when listing
subtasks under their parent task. The endpoint
`GET /api/v3/tasks/{task_id}/subtasks` was returning every subtask
under the task — top-level **and** nested — as a flat list, sorted by
`(position, id)`. The FE rendered each row at the same indentation, so
the parent/child relationship was invisible. Effectively: nested
subtasks were unlisted from a UI perspective.

## Requested change

The list endpoint should return only **top-level** subtasks
(`parent_subtask_id IS NULL`) as the paginated rows, and embed every
descendant under each top-level row via a recursive `subtasks: [...]`
field. Same shape the tree endpoint already produces.

## Fix

### `app/api/v3/subtasks/services/list.py`

`PagedSubtasks` gained a `nested: List[Subtask]` field alongside `items`:
- `items` — paginated **top-level** subtasks (`parent_subtask_id IS NULL`).
- `nested` — every other subtask under the same task, flat. The
  controller groups these by `parent_subtask_id` to embed children.
- `total` — count of top-level subtasks only (correct semantics for
  pagination — each "page" is a slice of top-level rows; their entire
  subtrees come along).

The dependency-list bulk-load was widened from "page top-level rows
only" to "every subtask the response will include" (top-level +
nested) so a single indexed query covers the whole subtree.

### `app/infrastructure/db/repositories/subtask_repository.py`

New method `list_nested_under_task(task_id, include_deleted)` returns
every subtask with `task_id == :task_id AND parent_subtask_id IS NOT
NULL`, ordered by `(position, id)` so the nested ordering matches the
tree endpoint and the underlying SQL.

### `app/api/v3/subtasks/controller.py`

Two changes:

1. `format_subtask_response` gained a keyword-only `nested_subtasks`
   parameter. When present, it's emitted under the `subtasks` key —
   matching the tree endpoint's subtask node shape. When absent,
   single-row responses stay flat (single-GET behavior unchanged).

2. `SubtaskController.list` rewrote the formatting path. It builds an
   adjacency map keyed on `parent_subtask_id` from the flat nested
   list, then formats each top-level row by recursively walking its
   subtree. Each level passes its children through
   `format_subtask_response(..., nested_subtasks=[...])`.

The label index is built once across top-level + nested rows (all
share a project_id since they're all under the same task), so the
recursive formatting reuses one index.

## Response shape

```json
{
  "data": {
    "_type": "Collection",
    "total": 2,
    "count": 2,
    "_embedded": {
      "elements": [
        {
          "_type": "Subtask",
          "id": "...", "name": "S1", "displayCode": "S1.1.1",
          "subtasks": [
            {
              "_type": "Subtask",
              "id": "...", "name": "S1.1", "displayCode": "S1.1.1.1",
              "subtasks": [
                { "_type": "Subtask", "id": "...", "name": "S1.1.1", "displayCode": "S1.1.1.1.1" }
              ]
            }
          ]
        },
        { "_type": "Subtask", "id": "...", "name": "S2", "displayCode": "S1.1.2", "subtasks": [] }
      ]
    }
  }
}
```

`subtasks` is always present on a list-endpoint row (empty list if no
children). Single-GET responses (`GET /subtasks/{id}`) stay flat — no
`subtasks` key.

## Tests

`tests/test_doc28_subtask_list_nested.py` — 332 lines covering:

- Top-level subtasks with no nesting → flat-shape preserved.
- Two-deep nesting → `subtasks[0].subtasks[0]` populated.
- Variable-depth nesting (tested up to 5 levels deep).
- Pagination slices top-level rows only — full subtree of each
  page row is included regardless of how deep it goes.
- Display labels match the tree endpoint.
- `dependsOn` / `dependsOnDisplay` populated for every descendant
  (the bulk-load widening).
- Soft-deleted nested rows excluded (`includeDeleted=False` default).
- Single-GET response shape unchanged (no `subtasks` key).
