# Doc 29 — Calendar-date input normalization across submission formats

**Commit:** `4bbec2f` ("fix #56 nested subtask listing + same-date accepted across M-A-T-S"). Bundled with doc 28 in the same push.

## The bug (continued from doc 27)

Doc 27 fixed the storage-side half: every persisted datetime is now
normalized to canonical naive UTC at the SQLAlchemy bind boundary via
the `UtcDateTime` column type.

But the input side still has a problem. The PMIS UI is calendar-date-
driven — a user picks "May 4" on a date widget; what they mean is
"the calendar date May 4 in IST." Different FE form components
serialize that same picked date inconsistently:

| Submitted string | Meaning to user | UTC instant |
|---|---|---|
| `2026-05-04T00:00:00+05:30` | May 4 IST | May 3 18:30 UTC |
| `2026-05-04T00:00:00.000Z` | May 4 IST | May 4 00:00 UTC |
| `2026-05-04T23:59:59+05:30` | May 4 IST | May 4 18:29 UTC |
| `2026-05-04T23:59:59.000Z` | May 4 IST | May 4 23:59 UTC |
| `2026-05-04T23:59:59` (naive) | May 4 IST | May 4 23:59 UTC (treated as UTC) |

All five are "May 4" to the user but produce **five different UTC
instants**. When the BE compares them across entities (project vs
milestone, milestone vs activity, etc.) — even after the doc 27
storage normalization — inputs the user picked as the same calendar
date can land 5h30m–24h apart and trip the `start >= parent.start`
floor check.

## Requested change

Collapse any submitted datetime to a single canonical instant per
calendar date, **at the schema layer** (before service-layer
comparisons run), so cross-format inputs that mean the same calendar
day land on the same value.

## Fix

### `app/shared/datetime.py` — `to_ist_calendar_midnight()` helper

```python
IST = timezone(timedelta(hours=5, minutes=30))

def to_ist_calendar_midnight(dt: Optional[datetime]) -> Optional[datetime]:
    if dt is None:
        return None
    if dt.tzinfo is None:
        # Treat naive as UTC (matches `ensure_aware_utc` semantics).
        dt = dt.replace(tzinfo=timezone.utc)
    ist_dt = dt.astimezone(IST)
    return datetime(ist_dt.year, ist_dt.month, ist_dt.day, tzinfo=IST)
```

Returns a tz-aware `YYYY-MM-DDT00:00:00+05:30` (IST midnight of the
IST-local calendar date). Combined with the doc 27 `UtcDateTime`
storage path, every "May 4" input ends up stored as the same value
(`2026-05-03 18:30:00` UTC).

### `app/shared/datetime.py` — Pydantic-friendly `IstCalendarDate` annotation

```python
from pydantic import AfterValidator
IstCalendarDate = Annotated[datetime, AfterValidator(_validate_ist_calendar_midnight)]
```

Schemas use `IstCalendarDate` in place of `datetime` for any
calendar-date semantic field. After Pydantic parses the incoming
string into a `datetime`, the `AfterValidator` normalizes it to IST
midnight. None passes through. Non-datetime inputs pass through to
let Pydantic raise its own type error.

The import is wrapped in a `try/except ImportError` so
`app.shared.datetime` stays usable in non-Pydantic contexts (admin
scripts, CLI).

### Schemas wired (M-A-T-S)

`start_date`, `end_date`, `actual_start_date`, `actual_end_date` on:
- `app/api/v3/projects/schemas.py`
- `app/api/v3/milestones/schemas.py`
- `app/api/v3/activities/schemas.py`
- `app/api/v3/tasks/schemas.py`
- `app/api/v3/subtasks/schemas.py`

Each `datetime` field on those schemas became `IstCalendarDate`. No
service-layer code changed — the normalization happens at the schema
boundary, before any cross-entity comparison runs.

## Why schema-layer (vs. service-layer)

- **Single source of truth.** One annotation per field; the service
  layer keeps assuming "naive == UTC" and the comparisons stay simple.
- **Doc 27 + doc 29 are layered cleanly.** Doc 27 normalizes at
  storage, doc 29 normalizes at input. Together they guarantee that
  cross-entity comparisons of "calendar dates" always work, regardless
  of which FE picker produced the string.
- **Future-proof.** Any new calendar-date field on any schema just
  needs the `IstCalendarDate` annotation — the helper handles every
  format the FE might emit.

## What this changes for the API

- All five input formats from the table above now compare equal at the
  service layer for any cross-entity rule (parent floor, dep-date,
  publish gate, etc.).
- Stored value for any "May 4 IST" submission is now `2026-05-03
  18:30:00` UTC (canonical), matching the doc 27 storage shape.
- Existing rows from before doc 27 may carry wall-clock-IST values
  (no migration shipped) — same caveat as doc 27.

## Tests

`tests/test_doc29_calendar_date_normalization.py` — 212 lines covering:

- All five input formats from the table normalize to the same stored
  value when written to a milestone.
- Cross-entity flows (project + milestone, milestone + activity, etc.)
  with mixed-format inputs all pass parent-floor checks.
- Helper unit tests: tz-aware → IST midnight; naive → IST midnight via
  the assume-UTC step; None → None.
- The `IstCalendarDate` annotated type is wired on every M-A-T-S
  schema's start/end/actual_start/actual_end field (introspection
  test).
- Negative test: a genuinely earlier calendar date STILL gets
  rejected (the normalization doesn't paper over real bugs).
