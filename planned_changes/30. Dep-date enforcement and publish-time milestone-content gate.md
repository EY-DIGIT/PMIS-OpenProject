# Doc 27 — Dependency-aware date enforcement + publish-time milestone-content gate

Three validation questions came in from the tester against
`http://10.1.131.199:8000/docs#`. Q1 needed no code change; Q2 and
Q3 are now implemented.

---

## Q1 — Milestone/activity `start_date` vs project `start_date`

**Reported behaviour:** "milestone is not taking date of the start date as
valid, it is only taking start_date + 1 as valid."

**Audit result:** **No backend bug.** The shared rule at
[app/shared/date_rules.py:68](../app/shared/date_rules.py#L68) is

```python
if entity_start_n < parent_start_n:
    raise ValidationError(...)
```

`<` (strict less-than) — `entity_start_n == parent_start_n` passes
cleanly. Both [milestones/services/create.py:69-78](../app/api/v3/milestones/services/create.py#L69-L78)
and [activities/services/create.py:72-81](../app/api/v3/activities/services/create.py#L72-L81)
funnel through this single helper, so the rule is uniform.

**Likely actual cause** (not backend):
1. **Timezone clipping.** If the FE submits `2026-05-04T00:00:00+05:30`
   for a milestone start date and `2026-05-04T00:00:00Z` for the
   project, the helper coerces both to naive UTC — the milestone
   becomes `2026-05-03T18:30:00`, which is < the project start. Always
   send dates as date-only `YYYY-MM-DD` (parsed identically) or both
   in the same timezone offset.
2. **FE-side validator** has its own off-by-one and rejects equality
   before the request leaves the browser.

**Action:** **No code change.** Repro steps for the tester are
captured below — if the BE rejects the equal-date case under any of
these conditions, attach the curl + response and re-open.

```bash
BASE=http://10.1.131.199:8000
TOKEN=$(curl -s -X POST $BASE/api/v3/users/login \
  -H 'Content-Type: application/json' \
  -d '{"login":"admin","password":"admin123"}' \
  | python -c "import sys,json;print(json.load(sys.stdin)['data']['access_token'])")

PID=$(curl -s -X POST $BASE/api/v3/projects/create \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"Q1","owner":"tmd1","category":"msap","startDate":"2026-07-01T00:00:00Z","endDate":"2026-12-31T00:00:00Z"}' \
  | python -c "import sys,json;print(json.load(sys.stdin)['data']['id'])")

# Equal dates — must return 201:
curl -i -X POST $BASE/api/v3/projects/$PID/milestones/create \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"M1","startDate":"2026-07-01T00:00:00Z","endDate":"2026-08-01T00:00:00Z"}'
```

## Q2 — Successor cannot start before predecessor's end date

**Status:** **Implemented.** New shared helper +
forward + reverse wiring in seven service paths + 19 new tests.

### What's enforced

```
source.start_date >= target.end_date    (equality allowed)
```

Equality matches the existing date semantics (entity start can equal
parent start; same-day handoff is a clean transition, not a conflict
— answer to Q2.1).

Both directions are guarded (answer to Q2.2):

- **Forward** — when `dependsOn` is being assigned/replaced on a
  source, OR when the source's `start_date` moves and the existing
  outgoing dep set must be re-validated. Validates `source.start >=
  target.end` for every target.
- **Reverse** — when a target's `end_date` is being moved forward,
  every existing live source pointing at this target is checked. The
  error message lists every successor whose `start_date` would be
  violated by the new end_date (Q2.2 ask: name the offenders).

### Files

**New helper:** [app/shared/dep_date_rules.py](../app/shared/dep_date_rules.py)

Exports:
- `collect_forward_violations(source_start, targets) -> List[(label, end)]`
- `collect_reverse_violations(target_end, sources) -> List[(label, start)]`
- `raise_forward_if_violations(...)` — raises a `ValidationError`
  listing every offender, OR no-ops on empty input.
- `raise_reverse_if_violations(...)` — same shape for the reverse direction.

**Wired into** (Q2.3 — applies uniformly to all four kinds, including
milestone-to-milestone deps from doc 21A):

| Service | File | Forward | Reverse |
|---|---|---|---|
| Activities | [create.py](../app/api/v3/activities/services/create.py), [update.py](../app/api/v3/activities/services/update.py) | ✓ | ✓ |
| Tasks | [create.py](../app/api/v3/tasks/services/create.py), [update.py](../app/api/v3/tasks/services/update.py) | ✓ | ✓ |
| Subtasks | [create.py](../app/api/v3/subtasks/services/create.py), [update.py](../app/api/v3/subtasks/services/update.py) | ✓ | ✓ |
| Milestones | [create.py](../app/api/v3/milestones/services/create.py), [update.py](../app/api/v3/milestones/services/update.py) | ✓ | ✓ |

### Error format

Forward violation:
```
Activity 'A1.2' cannot start on 2026-07-15 — the following dependency
target(s) end after that date: 'A1.1' (ends 2026-07-20).
```

Reverse violation (name + date for every offender):
```
Activity 'A1.1' cannot end on 2026-07-30 — the following dependent(s)
would then start before this target ends: 'A1.2' (starts 2026-07-25),
'A1.3' (starts 2026-07-27).
```

Display labels (e.g. `A1.2`, `T1.1.3`, `M2`) are used wherever
available; the entity's own name is the fallback. The label-index
build is one extra `build_label_index_for_project` call per request
that touches deps — four short queries.

### Tests

[tests/test_doc27_dep_dates.py](../tests/test_doc27_dep_dates.py) — 19
tests covering:
- Activity forward (create + update, equality allowed, violation rejected)
- Activity reverse (target end_date moves forward, equality allowed,
  violations listed, multiple successors enumerated)
- Milestone forward + reverse
- Task forward + reverse on a version
- Subtask forward + reverse on a version
- Empty / null handling: clearing `dependsOn` skips the check;
  unrelated PATCH (name-only) doesn't trigger the check.

### Migration / DDL impact

None. Pure service-layer rule.

### Existing-test impact

Many existing dep tests were structured with identical date defaults
across activities (e.g. A1 and A2 both start day+3, end day+80). Under
the new rule that's an unconditional rejection. Helpers in
`test_dependencies.py`, `test_long_cycle_dependency.py`,
`test_nested_subtasks.py`, `test_labels.py`, `test_activity_split.py`,
and a handful of `test_new_features.py` cases were updated to use
staggered dates. The cycle-detection tests now pin all participants to
the same day so dep-date passes via the equality branch and the cycle
rule is the only thing under test. **No production code in the
existing tests was logically changed** — only the date offsets in test
fixtures.

## Q3 — Reject publish if any milestone has zero activities

**Status:** **Implemented.** Two structural-completeness gates added
to the publish path + 7 new tests.

### What's enforced

In order, before `publish_project` flips status to `published`:

1. **Zero-milestones gate** (Q3.1 ask): if the project has zero live
   milestones, fail with `errorIdentifier = "no_milestones"`.
2. **Empty-milestone gate**: if any live milestone has zero live
   activities, fail with `errorIdentifier = "milestone_without_activity"`.
   The error lists **every** empty milestone (Q3.3 ask — no cap).

Both gates apply uniformly to baselines and versions (Q3.2 ask) —
the helper queries by `project_id`, which is the version's own id
when publishing a version.

### File

[app/api/v3/projects/services/publish.py](../app/api/v3/projects/services/publish.py)
— two new helpers (`_milestones_without_activities`, `_live_milestone_count`)
+ the gate block between transition-assert and the actual update.

[app/api/v3/projects/controller.py](../app/api/v3/projects/controller.py)
— added `"invalid_publish": 422` to the HTTP-status mapping so the new
gates surface as 422 (validation-style failure), not 400.

### Error format

Zero milestones:
```json
{
  "_type": "Error",
  "errorIdentifier": "invalid_publish",
  "message": "Cannot publish: the project has no milestones. Add at least one milestone with one activity before publishing.",
  "_embedded": {
    "details": { "errorIdentifier": "no_milestones" }
  }
}
```

Empty milestone(s):
```json
{
  "_type": "Error",
  "errorIdentifier": "invalid_publish",
  "message": "Cannot publish: the following milestone(s) have no activities: 'M2', 'M5'. Add at least one activity to each, or delete the empty milestone.",
  "_embedded": {
    "details": {
      "errorIdentifier": "milestone_without_activity",
      "milestoneIds": ["uuid-m2", "uuid-m5"],
      "milestoneNames": ["M2", "M5"]
    }
  }
}
```

The outer `errorIdentifier` is the HTTP-status bucket (`invalid_publish`
→ 422). The specific identifier the FE branches on is in
`_embedded.details.errorIdentifier`. Same-shape pattern used by other
publish-time validations.

### Tests

[tests/test_doc27_publish_gate.py](../tests/test_doc27_publish_gate.py)
— 7 tests covering:
- Publish with zero milestones rejected (`no_milestones`)
- Publish with one empty milestone rejected (`milestone_without_activity`)
- Publish with one milestone + one activity allowed
- Publish with mixed empty + populated milestones lists every empty one
- Soft-deleting the only activity blocks subsequent publish
- Version-publish gate fires when a version's milestone is emptied
- Version inherits a publishable graph (sanity)

### Migration / DDL impact

None. Pure service-layer rule.

### Existing-test impact

Several existing tests used to call `publish` on bare projects
(milestones-only or no content at all) — those were never realistic
production states but happened to slip through. They've been updated
to attach a milestone + activity before publish. Affected:
`tests/test_projects.py`, `tests/test_new_features.py`,
`tests/test_activity_split.py`, `tests/test_catalogs_and_other_reason.py`,
`tests/test_dependencies.py` (TestMilestoneDeps propagation test).
