# Doc 31 — Milestone-specific dep-date rules + status-completion gate

Three changes scoped to **milestones only**. Activities, tasks, and
subtasks continue to use the doc 30 generic rule
(`source.start >= target.end`, equality allowed).

---

## Rules

For a milestone A that depends on a milestone B:

| # | Rule | Operator |
|---|------|----------|
| 2a | A.start_date >= B.start_date | `>=` (equality allowed) |
| 2b | A.end_date > B.end_date | `>` (strict — equality REJECTED) |
| 2c | A cannot be marked `completed` while any dep target is not `completed` | hard gate |

### Why the milestone rule is different

Milestones model project phases that often run in parallel. The doc 30
generic rule (`source.start >= target.end`) is too restrictive for them
— it would forbid a phase from starting before its predecessor finishes,
which is the normal case for overlapping workstreams.

The doc 31 rule splits into two halves:
- **Start floor** — A can begin any time on or after B begins (parallel work allowed).
- **Strict end** — A must wrap around B and outlast it (encodes the "depends-on" semantic).

The strict end is what makes a date-valid milestone cycle structurally
impossible: a closed loop forces some milestone to outlast itself.
Cycle detection still runs but is unreachable for milestones; the
date rule fires first.

## Code changes

### Helper: [app/shared/dep_date_rules.py](../app/shared/dep_date_rules.py)

Added milestone-specific functions alongside the doc 30 generic ones:

- `collect_milestone_forward_violations(source_start, source_end, targets)` — returns a `(starts, ends)` tuple. Each list contains the offenders for that rule, with their reference dates.
- `collect_milestone_reverse_violations(target_start, target_end, sources)` — symmetric for the reverse direction.
- `raise_milestone_forward_if_violations(...)` — raises a single `ValidationError` whose message lists every start-rule and end-rule offender in one combined response.
- `raise_milestone_reverse_if_violations(...)` — same shape for the reverse direction.

The doc 30 functions (`collect_forward_violations`, etc.) are still
used by activities, tasks, and subtasks — unchanged.

### Service: [app/api/v3/milestones/services/create.py](../app/api/v3/milestones/services/create.py)

Replaced the doc 30 `collect_forward_violations` call with the
milestone-specific variant. Now passes both `source_end` and queries
`target.start_date` alongside `target.end_date`.

### Service: [app/api/v3/milestones/services/update.py](../app/api/v3/milestones/services/update.py)

Two changes:
1. **Doc 31 dep-date wiring**: replaced the doc 30 helper calls with the milestone variant. Forward direction now re-validates when the dep set is replaced OR when EITHER `start_date` or `end_date` moves (was: only `start_date`). Reverse direction now fires on either-column edit because both rules use both columns of the target.
2. **Status-completion gate** (rule 2c): new helper `_gate_milestone_status_against_deps` mirrors the activity-side `_gate_status_against_deps`. Fires when the caller patches `status="completed"`; reads the live dep set from `milestone_dependencies`, checks each target's `status`, and raises with up to 3 blocker names (`+N more` if more). Backward transitions (`completed → not_completed`) are not gated — matches activity semantics.

### No changes elsewhere

- Activities, tasks, subtasks: unchanged. Doc 30 rule still in force.
- Schema, migrations, repositories: untouched.
- The `MILESTONE_STATUS_COMPLETED` constant added to the import set in
  `update.py` — was already defined in `app/domain/milestones/milestone.py`.

Under doc 31, milestone cycles are date-impossible, so the cycle path is structurally unreachable. The test now asserts the strict-end rule fires (which is what the user would actually see), so a future regression that loosens the end rule would be caught.
