## Change 1 — Inline comment + files multipart on every M/A/T/S create

### Requested change

The original create endpoints for milestones / activities (4 variants)
/ tasks / subtasks (top-level + nested) only accepted JSON. Adding a
comment or attaching files required two extra round-trips to the
respective `/comments/create` and `/attachments/create` endpoints.
Tester ask: let the create call do it all in one multipart request.

### Behaviour

All 7 create endpoints now accept either JSON (existing contract,
unchanged) **or** multipart on the same URL. The server inspects
`Content-Type` to choose the path:

| Method | Path | Content-Type accepted |
|---|---|---|
| POST | `/projects/{id}/milestones/create` | `application/json` OR `multipart/form-data` |
| POST | `/milestones/{id}/activities/standard/create` | same |
| POST | `/milestones/{id}/activities/resource/count/create` | same |
| POST | `/milestones/{id}/activities/resource/details/create` | same |
| POST | `/milestones/{id}/activities/transactional/create` | same |
| POST | `/activities/{id}/tasks/create` | same |
| POST | `/tasks/{id}/subtasks/create` | same |
| POST | `/subtasks/{parent_id}/subtasks/create` | same |

Multipart adds two optional fields beyond the JSON schema:

- **`body`** — a free-text comment to attach to the just-created entity.
- **`files`** — one or more file uploads to attach.

If `body` is set with no `files`, a comment is created. If `files` are
set with no `body`, standalone attachments are created. Both can be
present.

### Implementation

- **New: [app/api/v3/_inline_attachments.py](../app/api/v3/_inline_attachments.py)** (459 lines) — shared multipart machinery:
  - `parse_form_fields` — generic form parser keyed by required-string / optional-string / int / array / object key sets per variant.
  - `pre_validate_files` — file count, individual size, total payload size, mime type whitelist. Runs **before** the create-entity service so a rejected file doesn't leave behind an orphan entity.
  - `extract_files_from_form` — pulls `UploadFile` instances out of the form.
  - `persist_inline_comment_or_files` — dispatches to the existing comment / attachment services after the entity row exists.
  - `sanitize_pydantic_errors` — strips traceback noise + locals from Pydantic's error tuples for clean 422 responses.
  - `Multipart422` — internal exception type to short-circuit the parse path with a clean 422.
- **Per-controller wiring** in [milestones/controller.py](../app/api/v3/milestones/controller.py), [activities/controller.py](../app/api/v3/activities/controller.py), [tasks/controller.py](../app/api/v3/tasks/controller.py), [subtasks/controller.py](../app/api/v3/subtasks/controller.py) — each gained:
  - A `_parse_and_validate_multipart_*` helper that runs the shared parser with the variant's key spec then validates against the variant's existing Pydantic schema.
  - A `_persist_*_inline` helper that runs the per-entity create service, then routes the comment/files through `persist_inline_comment_or_files`.
- **Routes** in [milestones/routes.py](../app/api/v3/milestones/routes.py), [activities/routes.py](../app/api/v3/activities/routes.py), [tasks/routes.py](../app/api/v3/tasks/routes.py), [subtasks/routes.py](../app/api/v3/subtasks/routes.py) — each create route gained a multipart variant on the same URL (FastAPI dispatches by content-type via two route handlers).
- **Repository methods** added across milestone/activity/task/subtask repositories to support the new flow.

### Why this design

- The JSON contract is **unchanged** — every existing client keeps working.
- File pre-validation runs before the entity insert so failures don't leave orphan rows.
- The comment/attachment writes reuse the existing services — no duplication of comment/attachment business logic.
- The shared parser is variant-agnostic — adding multipart to a future create endpoint takes ~20 lines in the controller.

## Change 2 — `_normalize` collapses to IST calendar midnight

### Requested change

Tester report: a milestone whose project was created BEFORE doc 29
(the IstCalendarDate annotation) was being rejected on the same-IST-day
floor check. Cause: the project's `start_date` was stored as raw UTC
midnight (e.g. `2026-07-10 00:00 UTC`), 5h30m AHEAD of the doc-29
canonical IST-midnight value (`2026-07-09 18:30 UTC`). When the
milestone — picked as the same calendar date in IST and now stored
canonically — was compared against the legacy project value, the
floor check fired.

### Fix

[app/shared/date_rules.py](../app/shared/date_rules.py) — `_normalize`
now collapses to IST calendar midnight via the doc-29
`to_ist_calendar_midnight` helper, instead of UTC-naive coercion.
Same-IST-day inputs from any era now compare equal regardless of how
they were stored.

The followup also kept [app/shared/dep_date_rules.py](../app/shared/dep_date_rules.py)
in sync (its `_normalize` was a separate copy that mirrored the OLD
date_rules behavior). Updated in this commit's integration step so
the dep-date checks have the same legacy-row tolerance as the parent-
floor checks.

### Tests

- [tests/test_doc30_legacy_project_date_equality.py](../tests/test_doc30_legacy_project_date_equality.py) — 203 lines verifying same-IST-day comparisons across legacy and canonical storage formats.

## Change 3 — Position auto-bump on collision

### Requested change

Bug: a caller-supplied `position` colliding with an existing live row
would 500 on the `uq_*_position_live` partial unique index. Most
visible in Swagger UI's multipart "Try it out" path, which auto-fills
the `position` field with `0` — making the second milestone (or A/T/S)
created via Swagger a guaranteed crash.

### Fix

The create services for milestone / activity / task / subtask now
auto-bump to the next free position when the caller's preferred slot
is taken. Position is only an ordering hint; if a caller's slot is
filled the service silently falls back rather than reject. Genuine
"insert at the top" semantics aren't a thing on these endpoints —
repositioning happens via separate update / move endpoints.

Implementation: each create service now calls
`repo.next_position(...)` when `position` is `None` AND when it's
specified but already taken. The repositories gained
`next_position_after_collision(...)` (or equivalent) helpers.
