# Doc 33 — Versioning removal, vendor role, RBAC extension, notifications

This doc covers three independently-shippable changes scoped together
because the user requested them as one work item:

1. **Versioning removal** — drop the entire baseline/version split.
   Projects are the single source of truth.
2. **RBAC extension** — runtime permission registration, module
   taxonomy, artifact cleanup.
3. **Notification-driven 2FA + forgot-password** — new microservice
   client, OTP login flow, self-service password reset.

Each ships as its own commit. **Status as of this doc snapshot:**
change 1 is implemented and tested. Changes 2 and 3 follow in
subsequent commits.

The commit boundary keeps blast-radius narrow per feature. If anything
goes wrong with notifications, it doesn't affect the versioning
removal that's already live.

## Change 2 — RBAC extension (shipped)

### What was already in place (pre-doc-33)

The Q&A round assumed runtime permission registration was a brand-new
need, but auditing the existing code showed doc 21B already shipped:

- `POST /api/v3/master/permissions/create` accepts a free-form code
  (validated as `module:action`) + name + description and inserts a
  custom `permissions` row with `is_builtin=False`.
- `PATCH /api/v3/master/permissions/{code}` lets admins edit name +
  description.
- `DELETE /api/v3/master/permissions/{code}` deletes custom rows.
  Built-in rows are protected by a 403.
- Custom rows show up in every catalog read (the listing isn't filtered
  by `is_builtin`) and can be granted to any role via the existing
  `PUT /api/v3/master/roles/{id}/permissions` body.

So the runtime-registration ask was already satisfied — change 2 just
added the missing UX piece + cleared dead code.

### What was added in this commit

**New endpoint: `GET /api/v3/master/permissions/by-module`** —
[app/api/v3/master_data/routes.py](../app/api/v3/master_data/routes.py).

Returns the entire permission catalog grouped by module (the leading
segment of `module:action`). Response shape:

```json
{
  "data": {
    "_type": "PermissionsByModule",
    "moduleCount": 13,
    "totalPermissions": 50,
    "_embedded": {
      "modules": [
        {
          "_type": "PermissionModule",
          "module": "activities",
          "count": 5,
          "permissions": [
            {"code": "activities:create", "name": "Create activity", ...},
            ...
          ]
        },
        {"module": "projects", "count": 9, "permissions": [...]},
        ...
      ]
    }
  }
}
```

Modules are alphabetised; permissions inside a module are sorted by code.
Custom permissions added at runtime appear in the same response — if
their code uses a brand-new module prefix (e.g. `custom_module:my_action`),
that bucket is created on the fly. The FE renders the buckets as the
permission picker tree without parsing codes client-side, which closes
the original "more modules and permissions will get added" ask.

The flat `GET /api/v3/master/permissions` endpoint is unchanged — it
still returns the paginated list view that callers building their own
UIs prefer.

## Change 3 — Notifications + 2FA + forgot-password (shipped)

### Schema additions

Migration: [alembic/versions/e6f7a8b9c1d2_doc33_change3_otp_password_reset_notifications.py](../alembic/versions/e6f7a8b9c1d2_doc33_change3_otp_password_reset_notifications.py).

- **`users.two_factor_enabled BOOLEAN NOT NULL DEFAULT TRUE`** — per Q3a.4, 2FA is mandatory by default. Admins can opt individual users out via `PATCH /users/{id}` (e.g. service accounts). Backfilled to TRUE for existing rows.
- **`notification_log`** — every dispatched notification recorded regardless of which backend (`mock` / `http`) handled it. Columns: `id`, `user_id`, `channel`, `recipient`, `template_kind`, `payload (JSON)`, `status`, `error`, `created_at`.
- **`otp_codes`** — login 2FA. Columns: `id`, `user_id`, `channel`, `code_hash`, `ephemeral_token_hash`, `generated_at`, `expires_at`, `consumed_at`, `attempt_count`, `last_sent_at`. Code stored as `HMAC-SHA256(server_pepper, code)` so DB readers can't replay active OTPs. Single-use semantics — verify consumes the row; resend invalidates the previous and inserts a new row.
- **`password_reset_tokens`** — self-service password reset. Columns: `id`, `user_id`, `channel`, `token_hash` (UNIQUE), `generated_at`, `expires_at`, `consumed_at`. Email channel uses a 32-byte URL-safe random token; SMS channel uses a 6-digit numeric OTP. Both hashed identically.

### Configuration

New env vars in [`app/core/config.py`](../app/core/config.py):

| Setting | Default | Purpose |
|---|---|---|
| `REQUIRE_2FA` | `True` | Global force-on. `False` disables 2FA for everyone (escape hatch); `True` honours the per-user `two_factor_enabled` flag. |
| `OTP_TTL_SECONDS` | `300` | OTP validity (5 min). |
| `OTP_RESEND_COOLDOWN_SECONDS` | `60` | Min seconds between resends. Returns 429 inside the window. |
| `OTP_MAX_ATTEMPTS` | `5` | Wrong-code budget per OTP. Once exhausted the row is invalidated; user must request a new OTP. |
| `OTP_CODE_LENGTH` | `6` | Number of digits per OTP code. |
| `OTP_HASH_PEPPER` | `""` (falls back to `SECRET_KEY`) | Server-side pepper added to HMAC. |
| `PASSWORD_RESET_TTL_SECONDS` | `3600` | Password-reset token validity (1 hour). |
| `NOTIFICATION_CLIENT` | `mock` | `mock` writes to `notification_log` only; `http` POSTs to the real microservice (stub today). |
| `NOTIFICATION_SERVICE_URL` | `""` | Real microservice base URL (HTTP backend). |

### Notification client

[`app/shared/notifications.py`](../app/shared/notifications.py) introduces a `NotificationClient` abstract with two backends:

- **`MockNotificationClient`** — terminal sink. Writes a row to `notification_log` with `status="sent"` and returns. The mock surfaces the actual code in `payload` so dev/tests can read it.
- **`HttpNotificationClient`** — production. Stamps `status="queued"` then would `httpx.post(...)` to the real microservice. The TODO block marks where the integration POST goes once the microservice is reachable.

`get_notification_client(db)` picks the backend from `settings.NOTIFICATION_CLIENT`. Falls back to mock on unknown values — safer default than crashing on misconfig.

### 2FA login flow

Two-stage:

```
POST /users/login                  body: {login, password}
                                   → 200 {_type: LoginOtpRequired,
                                          requires_otp: true,
                                          ephemeral_token: "...",
                                          channels_available: ["email", "sms"]}
                                     (no JWT minted yet)

POST /users/login/send-otp         body: {ephemeral_token, channel}
                                   → 200 {channel, expires_in_seconds, resend_after_seconds}
                                     dispatches via NotificationClient

POST /users/login/verify-otp       body: {ephemeral_token, code}
                                   → 200 {_type: Login, access_token, refresh_token, ...}
                                     same shape as a non-2FA /login success
```

When the user has 2FA disabled (`two_factor_enabled=False`) the original `/login` returns the access_token directly — single-stage flow preserved for service accounts and other 2FA-exempt users.

The `ephemeral_token` is opaque (32-byte URL-safe random). Stored hashed in `otp_codes.ephemeral_token_hash`. A sentinel row is written by `/login` to persist the token → user mapping; `/login/send-otp` materializes the actual OTP row when called.

**Cooldown**: a resend within `OTP_RESEND_COOLDOWN_SECONDS` returns 429 with `errorIdentifier="cooldown"` and `details.remaining_seconds`. Outside the window, the previous code is consumed and a fresh code is generated.

**Max attempts**: `OTP_MAX_ATTEMPTS` wrong-code submissions invalidate the OTP row (consumed_at set). User must call `/login/send-otp` again.

**Channels**: email always available (every user has an email at signup); SMS available only when `users.phone_number` is non-empty. The `channels_available` list returned at `/login` reflects this.

### Forgot-password flow

```
POST /users/forgot-password        body: {login_or_email, channel}
                                   → 200 always (anti-enumeration)
                                     {_type: PasswordResetRequestAck, message: ...}

POST /users/reset-password         body: {token_or_code, new_password}
                                   → 200 {_type: PasswordResetAck, message: "Password updated."}
                                     OR 401 if token invalid/expired/consumed
```

**Anti-enumeration (Q3b.4)**: `/users/forgot-password` always returns 200 with the generic message regardless of whether the user exists. Inactive users + users without a phone number on file (when SMS channel is requested) get the same response — no information leak about account existence.

**Token forms**:
- `email` channel → 32-byte URL-safe random token sent in a clickable reset link.
- `sms` channel → 6-digit numeric OTP. URLs in SMS are awkward (broken / phishing-flagged), so SMS uses the same code form as 2FA.

Both forms are hashed identically (`HMAC-SHA256(pepper, token)`); `/users/reset-password` accepts either form on the same endpoint and matches by hash.

**Validation**: new password must be ≥8 characters. Token expires after `PASSWORD_RESET_TTL_SECONDS` (default 1 hour). Single-use: a successful reset consumes the row.
