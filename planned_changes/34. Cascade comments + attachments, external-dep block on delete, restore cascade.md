# Doc 34 — Cascade comments + attachments, external-dep block on delete, restore cascade

This doc covers three coordinated changes to the M/A/T/S delete +
restore paths, scoped together because they share a common contract:
a cascade is now a paired (delete, restore) operation that brings
*everything* down with the parent and brings *everything* back
together.

1. **Cascade comments + attachments on M/A/T/S delete** — the
   polymorphic comments + attachments tables now follow the parent
   M/A/T/S into soft-delete instead of being orphaned.
2. **External-dependency block on delete** — refuse the delete if
   anything in the about-to-be-deleted subtree is the target of a live
   dep edge whose source lives outside the subtree. Forces the user to
   clear the dep first instead of silently losing it.
3. **Restore cascade** — restoring an M/A/T/S also restores every
   descendant + comment + attachment soft-deleted as part of the same
   cascade event. Identification is by `deleted_at` timestamp match —
   independently soft-deleted rows stay dead.

Each ships as its own commit. **Status as of this doc snapshot:** all
three are implemented, tested, committed, and pushed:

## Decision log (from the Q&A round)

All scope decisions taken before implementation:

| Q | Decision | Rationale |
|---|---|---|
| 1 | Project delete is unchanged. The whole-project cascade is all-or-nothing within one project; nothing can be external because deps are project-scoped. | Confirmed in conversation — "Project delete cascades and it is all soft deletes". |
| 2 | Vendors not affected by M/A/T/S delete. Milestone-vendor link rows stay as-is. | Vendors are independent catalog rows; the link table just has a dead reference, which is fine. Confirmed — "vendor is not affected". |
| 3 | Comments + attachments on M/A/T/S are cascade-soft-deleted with the parent. Orphan rows aren't acceptable. | Confirmed — "comment and attachments are deleted (soft delete)". |
| 4 | Dep edges INSIDE the subtree continue to be cascade-soft-deleted (existing behaviour, doc 21A). | They have nowhere to go — both endpoints disappear with the subtree. |
| 5 | Dep edges with EXTERNAL source: refuse the delete, list the offenders, ask the user to clear them first. | Per user — "if … any child object is a dependency for any other MATS object then the delete will fail and give error". |
| 6 | Restoring a milestone restores the M/A/T/S subtree it was deleted with. Same for activity → T/S, task → S. | Confirmed — "restore tasks and activities when milestone restored". |
| 7 | Restoring does NOT auto-restore dep edges. | Bringing the entity back doesn't imply the user wants the old dependency contract back — target may have been gone for a while, dates may have shifted. Re-establish via PATCH `dependsOn`. |
| 8 | Identification of "rows soft-deleted with this parent" is by `deleted_at` timestamp match. | The cascade already stamps every row in one shot with `datetime.now(timezone.utc)`; the timestamp is microsecond-precise, so collisions across independent cascades are negligible. Restoring queries `deleted_at == cascade_ts` and unsets it. |
| 9 | Independently-soft-deleted rows (e.g. a comment manually deleted yesterday) stay dead even when the parent is restored today. | Falls out of the timestamp-match rule. Tested explicitly. |
| 10 | Apply the dep-block rule to all four levels (M/A/T/S) for consistency. | Internally consistent: the user shouldn't be able to delete a task whose successor lives elsewhere any more than they should a milestone. |

## Change 1 — Cascade comments + attachments on M/A/T/S delete

Commit: `8b61f1d`.

### Why this exists

Comments + attachments are polymorphic via `(target_kind, target_id)`
— there's no FK from these tables to the M/A/T/S rows. Before this
change, soft-deleting an M/A/T/S left every comment + attachment
under it dangling. The rows still pointed at a now-invisible target
and still showed up in `GET /comments?target_kind=...` queries.

### What ships

New helper `app/shared/comments_attachments_cascade.py`:

```python
def cascade_soft_delete_comments_and_attachments(
    db: Session,
    *,
    targets: List[Tuple[str, TargetIds]],
    deleted_by: Optional[Any],
    now: datetime,
) -> None: ...
```

`targets` is a list of `(kind, id_or_clause)` pairs. Each `id_or_clause`
is one of: a single id string, a list of ids, or a SQLAlchemy `Select`
sub-query. The helper builds an `OR` predicate that matches any
`(target_kind, target_id)` pair in one indexed scan per table.

Three steps:
1. Snapshot the comment IDs about to be soft-deleted.
2. Stamp comments + standalone attachments (`comment_id IS NULL`) with
   the OR predicate.
3. Stamp comment-bound attachments (`comment_id IN doomed_comments`)
   so attachments hanging off a soft-deleted comment follow it.

All three steps share the SAME `now` timestamp passed in by the
caller — that's what lets the matching restore-cascade in Change 3
identify exactly which rows to bring back.

### Wired into

- `MilestoneRepository.soft_delete_with_cascade` — M/A/T/S subtree
- `ActivityRepository.soft_delete_with_cascade` — A/T/S subtree
- `TaskRepository.soft_delete_with_cascade` — T/S subtree
- `SubtaskRepository.soft_delete` — S subtree (nested via `descendant_ids`)
- `app/api/v3/milestones/services/cascade.py:cascade_soft_delete_project` — whole project

The cascade methods derive the subtree IDs from `deleted_at == now`
predicates so the helper sees exactly the same row set the caller
just stamped.

### Tests

10 new under `TestMilestoneDeleteCascadesCommentsAttachments` /
`TestActivityDelete...` / `TestTaskDelete...` / `TestSubtaskDelete...`
/ `TestProjectDeleteCascadesEverything` /
`TestPreExistingSoftDeletesNotReStamped` in
`tests/test_doc34_cascade_and_block.py`.

Coverage:
- Every level (M/A/T/S delete + project delete) cascades comments +
  standalone attachments + comment-bound attachments.
- Sibling subtrees are not touched.
- Cascade timestamps are uniform across the subtree.
- Already-soft-deleted rows from earlier independent deletions keep
  their original timestamps and are not re-stamped.

## Change 2 — External-dep block on delete

Commit: `286dbad`.

### Why this exists

Before: deleting an M/A/T/S silently soft-deleted every incoming dep
edge as a side-effect. The user's expressed plan ("X depends on Y")
was lost without warning.

After: refuse the delete with **422 `dependency_block`** when anything
in the about-to-be-deleted subtree is the TARGET of a live dep edge
whose SOURCE lives outside the subtree. Self-contained edges (source
AND target both in the subtree) don't block — the cascade soft-deletes
them consistently.

### What ships

New module `app/shared/dep_block.py`:

```python
def collect_external_dep_blockers(
    db: Session,
    *,
    root_kind: str,
    root_id: str,
    project_id: str,
) -> List[Blocker]: ...

def raise_if_external_blockers(
    blockers: List[Blocker],
    *,
    root_label: str,
    root_kind: str,
) -> None: ...
```

`collect_external_dep_blockers`:
1. Walks the subtree under `(root_kind, root_id)` collecting per-kind
   IDs (M / A / T / S, recursive subtask BFS).
2. For each kind, queries the matching `*_dependencies` table for live
   edges where `target IN subtree` AND `source NOT IN subtree`.
3. Resolves source/target IDs to display labels via
   `build_label_index_for_project` so error messages render `M2`,
   `A1.3` instead of UUIDs.

`raise_if_external_blockers` translates a non-empty blocker list into
a `ValidationError` with structured details:

```json
{
  "errorIdentifier": "dependency_block",
  "rootKind": "milestone",
  "rootLabel": "M1 — Foundation",
  "blockers": [
    {"source": "M2", "sourceKind": "milestone",
     "target": "M1", "targetKind": "milestone"},
    {"source": "A2.1", "sourceKind": "activity",
     "target": "A1.3", "targetKind": "activity"}
  ]
}
```

The `DomainError` projection in `app/main.py` lifts `details` to
`_embedded.details` in the response envelope, so the FE renders:

```
422 dependency_block
"Cannot delete milestone 'M1 — Foundation' — the following live
 dependencies must be removed first: M2 (depends on M1); A2.1
 (depends on A1.3)."

_embedded.details.blockers: [...]
```

### Wired into

All four delete services, BEFORE any cascade work runs:

- `app/api/v3/milestones/services/delete.py:delete_milestone`
- `app/api/v3/activities/services/delete.py:delete_activity`
- `app/api/v3/tasks/services/delete.py:delete_task`
- `app/api/v3/subtasks/services/delete.py:delete_subtask`

Project delete (`projects/services/delete.py`) is unchanged — deps
are project-scoped, so the all-at-once cascade has nothing external
to block.

### Tests

7 new under `TestExternalDepBlock`:
- Milestone-/activity-/task-/subtask-level external-dep block (4 cases).
- Self-contained dep doesn't block.
- Soft-deleted dep edge doesn't block.
- Blocker labels resolve to display codes (`M2`, `A1.3`, …).

Plus 8 existing dep-cascade tests in `test_dependencies.py` rebuilt
for the new contract — scenarios that used to assert "delete silently
soft-deletes incoming edges" now assert the 422 + `dep_block`. Two
`test_deleted_by_set_on_*_cascade` tests dropped because the only
remaining cascade path that stamps `deleted_by` is the PATCH-clear
path (already covered by `test_deleted_by_set_on_replace_list`).

## Change 3 — Restore cascade

Commit: `efa045d`.

### Why this exists

The matching inverse of Change 1's cascade-soft-delete. When an
M/A/T/S is restored, the user expects the rows that came down WITH it
to come back UP with it.

### What ships

The four `*Repository.restore` methods now do bottom-up cascade
restore. Identification is by `deleted_at` timestamp match —
every row stamped by a single `soft_delete_with_cascade` call shares
one `deleted_at` instant, so a `WHERE deleted_at == cascade_ts`
predicate finds exactly the cascade-deleted rows (and nothing more).

For each level:

- `MilestoneRepository.restore` — M + every A/T/S/resource/comment/
  attachment whose `deleted_at == milestone.deleted_at`.
- `ActivityRepository.restore` — A + T/S/resources/comments/attachments.
- `TaskRepository.restore` — T + S/resources/comments/attachments.
- `SubtaskRepository.restore` — S + nested-descendant subtask subtree
  (BFS over `parent_subtask_id` matching the cascade timestamp).

New helper `cascade_restore_comments_and_attachments` in
`app/shared/comments_attachments_cascade.py` mirrors the soft-delete
helper:

```python
def cascade_restore_comments_and_attachments(
    db: Session,
    *,
    targets: List[Tuple[str, TargetIds]],
    cascade_deleted_at: datetime,
) -> None: ...
```

### What is NOT auto-restored

Dep edges. They were soft-deleted as a side effect of the entity
going away (or, in the doc-34 era, as part of a PATCH-clear that the
user did before the delete to satisfy the dep-block rule). Bringing
the entity back doesn't imply the user wants the old dependency
contract back. Re-establish via PATCH `dependsOn` explicitly.

### Tests

6 new under `TestRestoreCascade`:
- Milestone restore revives the full A/T/S subtree.
- Milestone restore revives all comments + attachments under the subtree.
- Restore does NOT revive rows soft-deleted independently before the
  cascade (timestamp predicate enforces this).
- Activity restore revives T/S only (milestone untouched).
- Task restore revives S only.
- Subtask restore BFSes over nested descendants.

## Operational notes

- **Permissions unchanged.** `milestones:delete` / `activities:delete`
  / `tasks:delete` / `subtasks:delete` continue to gate the action.
  The dep-block rule fires after the permission check.
- **No new endpoints**. All changes are behaviour on existing
  DELETE / restore paths.
- **No env vars introduced**.
- **Wire format** for the 422 error: `_embedded.details.blockers`
  is the field FE clients should read when they see
  `errorIdentifier == "dependency_block"`.
