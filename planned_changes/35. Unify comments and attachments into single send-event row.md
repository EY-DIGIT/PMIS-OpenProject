## Scope

The senior product owner asked for the comments / attachments storage
model to look like an email send-event:

- Each "send event" is one row in the `comments` table.
- The row has either body text, an attachment, or both. Never edited
  after-the-fact (only soft-delete + new row on top of the trail).
- The attachment lives on an external file server; the comments row
  stores the file's URL (with metadata) directly, not an FK to a
  separate `attachments` table.
- Multiple files in one submission collapse into one row whose
  `attachments` JSON column carries the array.

Rationale: simpler data model (one row = one observable event), no
join from comments → attachments to render a thread, attachment-only
"sends" become first-class instead of being modeled as a comment with
a NULL body workaround. Aligns with how most messaging UIs already
think about the timeline — message + optional attachment list, never
attachment-without-message-shell.

## Schema delta

### `comments` table — add column, relax body

- `+ attachments JSON NULL` — list of objects
  `{url, filename, mimeType, sizeBytes, uploadedAt}`.
- `* body` relaxed from NOT NULL to NULL — a row can now be
  file-only (body NULL) or comment-only (body present).
- Service rule (enforced in `CommentService.create`): at least one
  of `body` or `attachments` must be present. Reject with 422 if both
  are empty / NULL.

### `attachments` table — DROPPED

After data migration. The standalone table is gone entirely.

### Data migration (in `upgrade()`)

For each live attachment row:

- If `comment_id` is set: append its file metadata to the parent
  comment's `attachments` JSON array. URL is composed as
  `{FILE_SERVER_PUBLIC_BASE_URL}/{storage_key}`; if the public base
  isn't set (typical for existing deployments), the URL falls back
  to the bare `storage_key` and the local fallback `GET /files/{key}`
  route resolves it.
- If `comment_id` is NULL (standalone attachment): create a new
  `comments` row with `body=NULL`, `target_kind` / `target_id` from
  the attachment, and an `attachments` array of one entry.

Soft-deleted attachment rows are NOT migrated — they're effectively
hidden from the trail under the senior's "deleted is gone" rule.

### Local fallback `GET /files/{storage_key}` route

Kept (and added if missing) so existing deployments without
`FILE_SERVER_PUBLIC_BASE_URL` configured can still serve attachment
bytes. The migration writes URLs as bare storage keys in that case;
the route resolves them by joining with `ATTACHMENTS_STORAGE_BASE_PATH`.

### Downgrade

Best-effort: recreates the `attachments` table and re-explodes the
JSON array into rows. Original attachment ids are NOT preserved (they
get fresh UUIDs). Any callers that rely on the original ids must
restore from backup.

## Cascade interaction with doc 34

Doc 34's three-part cascade (soft-delete with timestamp match, external-dep
block, restore cascade) was implemented against the two-table schema.
After doc 35 the cascade walk only touches the `comments` table —
attachment metadata travels with the comment row in the JSON column,
so soft-deleting / restoring the comment soft-deletes / restores its
attachments by definition. The shared helper
`app/shared/comments_attachments_cascade.py` was simplified to drop
the second-table walk; behavior is otherwise identical.

## API surface impact

- `POST /…/comments` accepts the same payload shape — `body` plus an
  optional `attachments` list of file references. Pre-doc-35 clients
  uploading via separate `/attachments` POST followed by a comment
  reference will need to switch to the unified shape; the
  multipart-on-create endpoints (doc 32) already wrote to the unified
  table internally so they only needed minor renderer updates.
- `GET /…/comments` returns rows with the embedded `attachments`
  array. Pre-doc-35 clients that did `GET /attachments?comment_id=…`
  will get 404 — the route is gone.
- `DELETE /attachments/{id}` is gone. To remove an attachment the
  caller now soft-deletes the comment that holds it.
