# Doc 36 — DB-backed notification templates + required division contact details

Two coordinated changes. Change 1 moves email + SMS template
authoring out of the codebase and into the master-data API so ops can
edit message copy without a release. Change 2 makes division contact
details (`email`, `phone_number`) mandatory on create instead of
optional.

| # | Change |
|---|---|
| 1 | DB-backed notification templates — new `notification_templates` master table + `/api/v3/master/notification_templates/*` CRUD endpoints; the email/SMS renderers in `app/shared/notifications.py` look up template copy from DB instead of from hardcoded strings. |
| 2 | Divisions: `email` + `phone_number` columns made `NOT NULL`. Pydantic create schema rejects requests that omit them. Backfill migration populates the seeded `tmd1` / `tmd2` / `others` rows before flipping the constraint. |

---

## Change 1 — DB-backed notification templates

### Problem

Email subject + HTML body and SMS body for the three notification
templates (`otp_login`, `password_reset_link`, `password_reset_otp`)
are currently hardcoded in **`app/shared/notifications.py`** —
specifically the `_render_email(template_kind, payload)` and
`_render_sms(template_kind, payload)` functions (~lines 126-260).
Editing message copy (e.g. fixing a typo, rebranding "PMIS" to a new
product name, adjusting tone) requires a code release. Ops can't see
the current copy without reading source.

The `notification_log` table already records every dispatch with the
`template_kind` discriminator. Templates themselves are the only
piece still living in code.

> Note on the notification microservice: SMS support is currently a
> **mock** in PMIS-notification-service (`SMS_PROVIDER=mock` is the
> dev default; `twilio` / `msg91` adapters exist but aren't wired in
> any environment). Templates rendered upstream in the monolith and
> POSTed to the service stay valid through the mock-vs-real switch —
> nothing in the templates work depends on which SMS backend is live.

### Decision

Move templates into a new `notification_templates` master-data table.
Renderers in `app/shared/notifications.py` look up by
`(template_kind, channel)` and substitute payload values into stored
content. Add `/api/v3/master/notification_templates/*` endpoints
gated by `master_data:view` / `master_data:manage`.

### Schema

New table: `notification_templates`

| Column | Type | Notes |
|---|---|---|
| `id` | `INTEGER PK` | Autoincrement |
| `template_kind` | `VARCHAR(64) NOT NULL` | Matches `notification_log.template_kind` (`otp_login` / `password_reset_link` / `password_reset_otp` / future kinds added at runtime via the create endpoint). |
| `channel` | `VARCHAR(16) NOT NULL` | `email` or `sms`. |
| `subject` | `VARCHAR(500) NULL` | Email subject. NULL for SMS rows. |
| `body` | `TEXT NOT NULL` | Email HTML body or SMS plaintext. Supports `{placeholder}` substitution using Python `str.format` semantics (see Placeholder spec below). |
| `is_html` | `BOOLEAN NOT NULL DEFAULT TRUE` | TRUE for email rows (HTML body); FALSE for SMS. The current SMTP/SendGrid path always sends `is_html=true` for email — this flag is forwarded to the notification microservice's `is_html` field. |
| `is_builtin` | `BOOLEAN NOT NULL` | TRUE for the three seeded templates; protected from delete. |
| `active` | `BOOLEAN NOT NULL` | Soft-deactivate without delete. Renderer falls back to a generic "you have a notification" body when no active row matches. |
| `description` | `VARCHAR(1024) NULL` | Free-form ops note (e.g. "Sent on every successful 2FA login attempt"). |
| `created_at`, `updated_at` | `UtcDateTime` | |

**Constraint**: `UNIQUE (template_kind, channel) WHERE active = TRUE` — at most one live row per `(kind, channel)` pair. Edit-in-place via PATCH; deactivate via PATCH `active=false` to keep history.

**Indexes**: composite `(template_kind, channel, active)` for the renderer's hot lookup.

### Placeholder spec

Body / subject strings use `{placeholder}` substitution. Each
template kind has a fixed set of available placeholders (validated on
PATCH so a bad reference is rejected at write time, not at render
time):

| Template kind | Available placeholders |
|---|---|
| `otp_login` (email + sms) | `{code}`, `{ttl_minutes}` |
| `password_reset_link` (email) | `{reset_url}`, `{token}`, `{ttl_minutes}` |
| `password_reset_link` (sms) | `{token}` (truncated to 24 chars), `{ttl_minutes}` |
| `password_reset_otp` (email + sms) | `{code}`, `{ttl_minutes}` |

Computed placeholders (e.g. `{ttl_minutes}` from `ttl_seconds`,
`{reset_url}` from `FRONTEND_BASE_URL` + `{token}`) are derived in the
renderer before substitution — the stored template only sees the
already-computed values. Unknown placeholders in a stored body raise
422 on PATCH; missing placeholders at render time are substituted as
empty strings (defensive — never crash the auth flow).

### API — `/api/v3/master/notification_templates/*`

| Method | Path | Permission | Notes |
|---|---|---|---|
| GET | `/api/v3/master/notification_templates` | `master_data:view` | List. Optional `?include_inactive=true` for admins. |
| GET | `/api/v3/master/notification_templates/{id}` | `master_data:view` | Single read. |
| POST | `/api/v3/master/notification_templates/create` | `master_data:manage` | Create custom template (e.g. for a new template_kind that gets registered later). 409 if the `(template_kind, channel)` pair already has an active row. |
| PATCH | `/api/v3/master/notification_templates/{id}` | `master_data:manage` | Edit subject/body/active/description. Validates placeholder set against the kind→channel matrix. Built-in templates ARE editable on subject + body (the whole point of moving them to DB). `template_kind` and `channel` are immutable. |
| DELETE | `/api/v3/master/notification_templates/{id}` | `master_data:manage` | Soft-deactivate (`active=false`). Built-ins protected from hard delete. |
| POST | `/api/v3/master/notification_templates/{id}/restore` | `master_data:manage` | Re-activate. 409 if another active row already covers the `(kind, channel)` pair. |

Pydantic `NotificationTemplateCreateRequest` / `…UpdateRequest` live
in `app/api/v3/master_data/schemas.py` next to the existing master-
data shapes.

### Renderer changes — `app/shared/notifications.py`

Replace the hardcoded if/elif/else blocks in `_render_email` and
`_render_sms` with a single helper:

```python
def _resolve_template(db: Session, *, template_kind: str, channel: str) -> Optional[NotificationTemplateModel]:
    return (
        db.query(NotificationTemplateModel)
        .filter_by(template_kind=template_kind, channel=channel, active=True)
        .one_or_none()
    )
```

Both renderers:

1. Look up the active template row.
2. Compute the placeholder dict (`code`, `ttl_minutes`, `reset_url`, …) from the existing `payload` argument.
3. `subject = row.subject.format(**placeholders)` and `body = row.body.format(**placeholders)`.
4. Fall back to a generic body when no row is found OR `format` raises (defensive — log warning, dispatch a placeholder message).

The renderer signatures change from
`_render_email(template_kind, payload)` → `_render_email(db, template_kind, payload)`
because the `Session` is needed for the lookup. `HttpNotificationClient.send`
already has `self.db`, so the wiring is local.

### Seeding

`init_db()` upserts the three current templates into the table with
`is_builtin=True`. The strings come from the existing renderer code,
verbatim, so the migration is a pure refactor — no behavior change at
boot. Subsequent edits (via PATCH) replace the seed copy; the seed
function is idempotent and only inserts when the row is missing.

### Migration

`alembic/versions/<rev>_doc36_notification_templates.py`:

1. `CREATE TABLE notification_templates`.
2. Insert the six seed rows (`otp_login` × `email`, `otp_login` × `sms`, `password_reset_link` × `email`, `password_reset_link` × `sms`, `password_reset_otp` × `email`, `password_reset_otp` × `sms`) with `is_builtin=true`, `active=true`.
3. Partial unique index on `(template_kind, channel) WHERE active`.

Idempotent — wrapped in inspector + existing-row checks.

### Test coverage

`test_doc36_notification_templates.py`:

- Seed rows present after `init_db`.
- CRUD over the master endpoint.
- Built-in delete returns 422; PATCH on built-in subject/body succeeds.
- Placeholder validation: PATCH with unknown placeholder returns 422 listing the offender.
- Renderer lookup: `_render_email("otp_login", {"code":"123456", "ttl_seconds":300})` substitutes code + ttl_minutes correctly.
- Renderer fallback: when no active row exists for the `(kind, channel)` pair, dispatch records a `notification_log` row but with the generic body (and a warning log).
- Active-row uniqueness: trying to insert a second active row for `(otp_login, email)` returns 409.
- End-to-end: `POST /users/login/send-otp` after editing the email subject via the master endpoint dispatches with the new subject.

## Change 2 — Division `email` + `phone_number` mandatory

### Problem

Today, `divisions.email` and `divisions.phone_number` are nullable in
the model and `Optional[str]` in `DivisionCreateRequest` /
`DivisionUpdateRequest`. The seeded built-ins (`tmd1` / `tmd2` /
`others`) ship with both fields NULL. FE asks: divisions are owners
of projects and need a routable contact channel — admins must supply
both at create time, and the seeded rows need backfilled values.

### Decision

Make both columns `NOT NULL` at the schema layer and at the wire.
Backfill seeded rows with deployment-specific values (env-driven so
each environment can pick its own contact details).

### Schema delta

`divisions` table:

- `* email` → `VARCHAR(255) NOT NULL`.
- `* phone_number` → `VARCHAR(50) NOT NULL`.

No new column. Just NULL → NOT NULL flip after backfill.

Model file `app/infrastructure/db/models/division.py`:

```python
email = Column(String(255), nullable=False, index=True)
phone_number = Column(String(50), nullable=False)
```

### Pydantic

`DivisionCreateRequest`:

- `email: EmailStr` — required (was `Optional[EmailStr]`).
- `phoneNumber: str = Field(..., alias="phone_number", min_length=1)` — required.

`DivisionUpdateRequest`:

- `email: Optional[EmailStr]` — stays optional (PATCH doesn't have to re-send).
- `phoneNumber: Optional[str]` — same.
- Empty-string semantics removed: passing `""` no longer "clears" the
  field. The DB constraint won't allow it either.

### Seed-row backfill

The migration must populate the three seeded rows before flipping the
NOT NULL constraint. Two phases:

1. Backfill: `UPDATE divisions SET email = coalesce(email, :default_email), phone_number = coalesce(phone_number, :default_phone) WHERE is_builtin = true`.
2. Constraint flip: `ALTER COLUMN ... SET NOT NULL`.

Default values come from new env vars (added to `app/core/config.py`):

```
DIVISION_DEFAULT_EMAIL=ops@pmis.example
DIVISION_DEFAULT_PHONE=+910000000000
```

Both have safe placeholder defaults so a fresh dev DB doesn't need
extra config. Production deployments are expected to override.

The bootstrap seed in `init_db()` is updated to insert the seeded
rows with the env-driven values (instead of NULL). Re-running against
a populated DB is a no-op for the email/phone fields (the seed only
fills missing columns).

### Existing user-added rows

User-added divisions (created on-the-fly when a project sets
`owner='others'` with a free-text label) currently leave email + phone
NULL. The migration backfills them with the same env-driven defaults
as the seed rows so the constraint flip doesn't fail. Admins should
edit them via PATCH afterward; the migration just keeps them legal.

### API behavior

- `POST /api/v3/master/divisions/create` without `email` or `phoneNumber` → 422.
- `PATCH /api/v3/master/divisions/{code}` with `email=null` or `phoneNumber=null` → 422 (can't null out a required column).
- Backward compat: legacy `/api/v3/divisions` POST is identical (same Pydantic schema).

### Migration

`alembic/versions/<rev>_doc36_division_contact_required.py`:

1. Backfill nullable rows from env defaults.
2. `ALTER COLUMN email SET NOT NULL`.
3. `ALTER COLUMN phone_number SET NOT NULL`.

Idempotent — re-running the backfill is a no-op (`COALESCE` only fills NULL); the `SET NOT NULL` is naturally idempotent.

### Test coverage

`test_doc36_divisions_required_contact.py`:

- Create without `email` → 422.
- Create without `phoneNumber` → 422.
- Create with both → 201; both echoed in response.
- PATCH with `email=null` → 422.
- Seeded rows have `email` + `phone_number` populated post-init_db.
- Backfill migration smoke test: feed the migration a DB with NULL contact rows, assert post-migration rows have the env-default values.

## Rollout order

1. Ship Change 2 first (smaller, no API surface area added — just a
   tightening). FE coordinates by ensuring the create form requires
   both fields.
2. Ship Change 1 second. FE adds the optional `notification_templates`
   admin UI under master-data once the endpoints land. Renderer
   refactor is server-only — no breaking change.

Both can live in the same release if FE is ready for both UI changes;
they're independent on the BE side.

## Open questions

- Change 1: should the renderer cache template lookups in-process
  (e.g. 60-second TTL) to avoid a DB hit per OTP dispatch? **Decision pending** —
  start without caching, profile under load before adding complexity.
- Change 2: should division-contact backfill use the *project owner's*
  contact details when the division was created from a project's
  `ownerOther` field? **No** — overkill. The env default is fine; admins
  can edit afterward.
