# Doc 37 — Static-data master endpoints + user-service microservice extraction

Two coordinated changes. **Part 1** sweeps the remaining hardcoded enums into master tables so ops can edit them through `/api/v3/master/*`. **Part 2** plans (and ships) the extraction of user-management out of the monolith into the standalone microservice running on port 8001 — same pattern as PMIS-notification-service.

| # | Part |
|---|------|
| 1 | Static-data → master endpoints. New tables: `project_categories`, `activity_types`, `milestone_statuses`, `activity_statuses`. Existing in-code tuples `PROJECT_CATEGORY_CHOICES`, `ACTIVITY_TYPES`, `MILESTONE_STATUS_CHOICES`, `ACTIVITY_STATUS_CHOICES` become DB-first with in-code fallback (matches the doc-20 `project_status_transitions` precedent). |
| 2 | User-service microservice extraction. PMIS-user-management (port 8001) was extracted around doc 21B and is missing every change since: doc 21B follow-up master/roles + master/permissions, doc 33 changes 1/2/3 (vendor role + by-module + 2FA + password-reset + notifications), doc 36 (notification templates). Bring the microservice to parity, add a monolith proxy flag, push, then flip traffic over. |

## Part 1 — Static data → master endpoints

### Why

User asked for an audit of static data residing in code that should be controllable via masters. The accepted scope (Q2):

- ✅ project category enum (MSAP / MSIP / BSP / others)
- ✅ activity type enum (standard / resource / transactional)
- ✅ milestone status enum (not_completed / completed)
- ✅ activity status enum (not_completed / completed)
- ❌ allowed file extensions + max file size (stays in code)
- ❌ OTP digit length / TTL / cooldown (stays as env vars; note for future)
- ❌ permission codes (stays in code — coupled to route decorators)
- ❌ JWT signing algorithm, validation min/max, framework constants (stays in code)

### What lives where today (verified scan)

Hardcoded tuples found in the monolith:

| Constant | File | Values |
|---|---|---|
| `PROJECT_CATEGORY_CHOICES` | [`app/api/v3/projects/services/transitions.py`](../app/api/v3/projects/services/transitions.py) line 172 | `MSAP`, `MSIP`, `BSP`, `others` |
| `ACTIVITY_TYPES` | [`app/domain/activities/activity.py`](../app/domain/activities/activity.py) line 12 | `standard`, `resource`, `transactional` |
| `MILESTONE_STATUS_CHOICES` | [`app/domain/milestones/milestone.py`](../app/domain/milestones/milestone.py) line 12 | `not_completed`, `completed` |

Existing precedent: `project_status_transitions` (doc 20) is the same shape — DB table + master endpoints + in-code constants kept as fallback. We follow that pattern for the four new catalogs.

### Schema

Four new master tables. Same shape — small enum-like catalogs:

```
project_categories
  id              INTEGER PK autoincrement
  code            VARCHAR(50)  UNIQUE NOT NULL    -- 'MSAP', 'MSIP', 'BSP', 'others'
  label           VARCHAR(255) NOT NULL           -- display name
  is_builtin      BOOLEAN NOT NULL                -- TRUE for the 4 seeded
  requires_other  BOOLEAN NOT NULL DEFAULT FALSE  -- TRUE only for 'others' (mirrors divisions)
  active          BOOLEAN NOT NULL DEFAULT TRUE
  description     VARCHAR(500) NULL
  created_at, updated_at  UtcDateTime
```

`activity_types`:

```
  id INTEGER PK
  code VARCHAR(50) UNIQUE NOT NULL    -- 'standard', 'resource', 'transactional'
  label VARCHAR(255) NOT NULL
  is_builtin BOOLEAN NOT NULL
  active BOOLEAN NOT NULL
  description VARCHAR(500) NULL
  created_at, updated_at
```

`milestone_statuses`:

```
  id INTEGER PK
  code VARCHAR(50) UNIQUE NOT NULL    -- 'not_completed', 'completed'
  label VARCHAR(255) NOT NULL
  is_builtin BOOLEAN NOT NULL
  is_terminal BOOLEAN NOT NULL DEFAULT FALSE  -- 'completed' is terminal
  active BOOLEAN NOT NULL
  description VARCHAR(500) NULL
  created_at, updated_at
```

`activity_statuses`: identical shape to `milestone_statuses`.

### Endpoints

Six per catalog (4 catalogs = 24 endpoints), all gated by `master_data:view` / `master_data:manage`. Pattern matches the existing `/api/v3/master/divisions/*`:

```
GET    /api/v3/master/project_categories          (list, ?include_inactive=true)
GET    /api/v3/master/project_categories/{code}   (single read by code)
POST   /api/v3/master/project_categories/create   (admin)
PATCH  /api/v3/master/project_categories/{code}   (admin; built-ins editable on label/description only)
DELETE /api/v3/master/project_categories/{code}   (admin; soft-deactivate; built-ins protected)
POST   /api/v3/master/project_categories/{code}/restore  (admin)
```

Same surface for `activity_types`, `milestone_statuses`, `activity_statuses`.

### Validator wiring

The four in-code tuples become **in-code fallbacks**. Validators (`PROJECT_CATEGORY_CHOICES` membership checks in `projects/schemas.py`, `ACTIVITY_TYPES` checks in `activities/schemas.py`, etc.) call a new helper:

```python
def is_valid_category(db, code: str) -> bool:
    """Catalog-first membership check, falls back to in-code tuple when no rows."""
    if db is not None:
        rows = ProjectCategoryRepository(db).list_active_codes()
        if rows:
            return code in rows
    return code in PROJECT_CATEGORY_CHOICES
```

Same idiom as `assert_transition_allowed` in `transitions.py`. The fallback covers tests on fresh in-memory DBs that haven't run `init_db`.

The `PROJECT_CATEGORY_CHOICES` tuple stays in source — it's the seed list AND the fallback. Adding a new built-in code requires editing the tuple AND adding a `PermissionDef`-style entry to a `BUILTIN_CATEGORIES` list that the seed loop reads on every boot. Adding a runtime category goes through `POST /master/project_categories/create`.

### Pydantic schema impact

Each schema field that uses `validate_in_choices` against the in-code tuple gains a session-aware variant. Where a `field_validator` runs without DB access (Pydantic's default), the schema-side check uses the static tuple; the service layer adds a DB-aware check after construction. Two validators is acceptable — same pattern as `validate_owner_pair` (which also does a DB-first / in-code-fallback membership check).

### Migration

`alembic/versions/<rev>_doc37_static_data_masters.py`:

1. `CREATE TABLE` for each of the four new catalogs.
2. Insert seed rows from the in-code tuples — `is_builtin=true`, `active=true`. For `milestone_statuses` and `activity_statuses`, mark `completed` as `is_terminal=true`.
3. Idempotent (inspector checks).

### `init_db` seed

Add a seed loop per catalog modeled on the divisions seed. Idempotent (only inserts missing rows). Re-runs preserve user edits — same pattern as notification_templates (doc 36).

### Tests

`tests/test_doc37_static_data_masters.py`:

- Seeded built-in rows present after init.
- CRUD flow per catalog (admin-only writes; member 403).
- Built-ins protected from delete.
- Soft-deactivate + restore.
- Validator falls back to in-code when catalog empty (fresh test DB).
- Project create rejects an invalid category code.
- Activity create rejects an invalid type / status code.

### Permissions

No new permission codes needed — these endpoints reuse `master_data:view` / `master_data:manage`.

### Out-of-scope (noted for future work)

- **Status transitions** for milestones / activities are NOT modeled here. Today they're trivial (`not_completed → completed` and back), so a transition table would be overkill. If the lifecycle becomes richer (e.g. `not_completed → in_progress → completed` with admin-gating), extract a `milestone_status_transitions` / `activity_status_transitions` table mirroring `project_status_transitions`.
- **OTP settings runtime-tunability** — user noted to keep this in mind. Today `OTP_TTL_SECONDS`, `OTP_RESEND_COOLDOWN_SECONDS`, `OTP_MAX_ATTEMPTS`, `OTP_CODE_LENGTH` are env vars. Moving them to a master table would let ops tune per-environment without a redeploy. Defer until a clear ops need surfaces — env vars are working.
- **File upload limits** — extension allow-list, MIME whitelist, max size. These are coupled to security policy and typically don't change after launch; left in code intentionally.
- **Validation thresholds** — min/max string lengths in Pydantic schemas. Schema-coupled; no benefit to runtime mutability.

## Part 2 — User-service microservice extraction

### Current state

[`PMIS-user-management`](https://github.com/EY-DIGIT/PMIS-user-management) (port 8001) was extracted from the monolith around doc 21B. It runs but is **missing every change since**:

- Doc 21B follow-up: `/api/v3/master/roles/*` and `/api/v3/master/permissions/*` (catalog routers).
- Doc 33 change 1: vendor role seed + 4-role model.
- Doc 33 change 2: `GET /master/permissions/by-module`.
- Doc 33 change 3: 2FA OTP login (`/login/send-otp`, `/login/verify-otp`), forgot-password (`/forgot-password`, `/reset-password`), per-user `users.two_factor_enabled` flag, `notification_log` / `otp_codes` / `password_reset_tokens` tables, `NotificationClient` interface.
- Doc 33 hotfix: `MIGRATIONS_AUTORUN` / `MIGRATIONS_REQUIRED` / `DATABASE_URL_MIGRATIONS` env vars.
- Doc 36: `notification_templates` table + master endpoints + DB-backed renderer.

### Goals

1. Bring user-management to **parity** with the monolith's user/auth/RBAC/notification surface.
2. **Same SECRET_KEY** + shared Postgres so JWT verification and DB reads work across both services without coordination calls (matches the existing PMIS pattern).
3. Add a **proxy flag in the monolith** so it can either handle user/auth requests itself OR forward them to port 8001. Default off initially; flip on in dev → staging → prod.
4. Keep the monolith's user routes responding throughout the cutover so the FE doesn't change. Once stable, remove monolith handlers.
5. **Push** to the user-management remote on `dev` branch.

### Architectural decisions

| # | Decision | Rationale |
|---|---|---|
| 4a | **Strangler-fig**, gated by env flag. Monolith proxies user/auth requests to port 8001 when `USER_SERVICE_PROXY_ENABLED=true`; otherwise handles them locally. | Reversible. Match the notification-service pattern that already works. |
| 4b | **Shared SECRET_KEY** — every service verifies JWTs locally. No introspection RPC. | Lower latency, no SPOF, matches current pattern. The user-service still issues tokens; everyone else verifies. |
| 4c | **Shared Postgres** — both services hit the same `users` / `roles` / `permissions` / `user_roles` / `user_permissions` / `revoked_tokens` / `otp_codes` / `password_reset_tokens` / `notification_log` / `notification_templates` tables. | No data sync needed. Schema migrations need coordination — handled below. |
| 4d | **Monolith proxies during transition** so FE keeps calling the same URLs. After cutover stabilizes (~1 release), remove monolith handlers; FE optionally switches base URL for auth to port 8001 directly. | FE-zero-impact transition. |

### Data model: who owns the migrations

Shared DB introduces a coordination problem: both services have alembic chains, and both seed the same tables. **Decision**:

- **User-service is the owner** of `users`, `roles`, `role_permissions`, `user_roles`, `user_permissions`, `revoked_tokens`, `otp_codes`, `password_reset_tokens`, `notification_log`, `notification_templates`, plus the bootstrap admin + RBAC seed.
- **Monolith is the owner** of `projects`, `milestones`, M/A/T/S, comments, attachments-related tables, `vendors`, `divisions`, `resource_types`, `project_status_transitions`, plus the 4 new doc-37-part-1 catalogs.
- **`vendor_id` on users** is a cross-boundary FK — user-service's `users` table references `vendors.id` which monolith owns. Both services must agree on vendor schema. We mark `users.vendor_id` as `String(36)` FK, no SQLAlchemy `ForeignKey` constraint *in the user-service model definition* (it's a logical FK; the FK is enforced by the monolith's migration), so user-service's alembic doesn't try to create the vendors table.
- **Migration runner**: in deploys, **only one service** runs `alembic upgrade head` — typically the monolith, with `MIGRATIONS_AUTORUN=false` on the user-service. User-service migration files live in its repo but are run via the monolith deploy job that has both repos checked out, OR the user-service alembic is re-run with `MIGRATIONS_REQUIRED=false` and just pulls the schema as-is.

This is the messiest part of shared-DB. We accept the coupling because the alternative (separate DB + sync) is a much bigger refactor.

### Files to add in monolith

#### `app/shared/user_service_client.py` (NEW)

HTTP proxy — same shape as `HttpNotificationClient`. Forwards user/auth requests to `USER_SERVICE_URL` when `USER_SERVICE_PROXY_ENABLED=true`. On any non-2xx, falls through to a 502 (treats user-service as authoritative).

```python
class UserServiceClient:
    def login(self, login: str, password: str) -> dict: ...
    def refresh(self, refresh_token: str) -> dict: ...
    def introspect(self, access_token: str | None, refresh_token: str | None) -> dict: ...
    def send_otp(self, ephemeral_token: str, channel: str) -> dict: ...
    def verify_otp(self, ephemeral_token: str, code: str) -> dict: ...
    def forgot_password(self, login_or_email: str, channel: str) -> dict: ...
    def reset_password(self, token_or_code: str, new_password: str) -> dict: ...
    # plus user CRUD + RBAC user-side
```

#### `app/api/v3/users/routes.py` proxy hook

Each route handler checks `settings.USER_SERVICE_PROXY_ENABLED` and either:
- forwards to `UserServiceClient.<method>(...)` and returns the response transparently, OR
- runs the existing local handler.

A small decorator (`@maybe_proxy`) keeps the per-route diff minimal.

#### Config

Add `USER_SERVICE_URL: str = ""` and `USER_SERVICE_PROXY_ENABLED: bool = False` to `app/core/config.py`.

### Cutover plan

1. **Land all the porting work** — user-management at parity, monolith proxy disabled by default.
2. **Test in dev** with `USER_SERVICE_PROXY_ENABLED=true`. Run the monolith and user-service against the same Postgres. Hit monolith `/api/v3/users/login` and verify the request lands in user-service's logs.
3. **Smoke-test** every auth flow through the proxy: login (single-stage + 2FA), refresh, logout, introspect, forgot-password, reset, user CRUD, RBAC user-side, master/roles, master/permissions, master/notification_templates.
4. **Deploy to staging** with the flag on. Watch for latency or 5xx anomalies.
5. **Production cutover**: flip the flag on. Monolith continues to respond on the same URLs; FE is unaffected. Watch error rates for one release cycle.
6. **Cleanup**: in a follow-up doc, delete the monolith user/auth handlers + the proxy plumbing. FE optionally switches its auth base URL to `:8001` directly.

### Rollback

Set `USER_SERVICE_PROXY_ENABLED=false`. Monolith handles everything locally again, on its existing route handlers (kept unchanged through the cutover). No DB rollback needed (shared DB).

- `tests/test_users.py` — user CRUD + last-admin lockout.

### Risk + open questions

- **Schema migration coordination** is the highest-risk piece. We're explicit about which service owns what (above), but two CI pipelines hitting the same Postgres requires deploy ordering. Concretely: user-service deploys first (so any schema changes it owns are applied), then monolith. If both ship in the same release, the joint deploy job runs alembic in a single step against the merged migrations.
- **Race during cutover**: if a user logs in via monolith pre-flip and hits a protected route post-flip, the monolith JWT is still valid (same SECRET_KEY) — no race window.
- **Latency**: an extra HTTP hop per user/auth request. Within a single VPC this is single-digit milliseconds; if both services are co-located it's negligible. Worth monitoring.
- **What if user-service is down**? Monolith can fail-closed (5xx for all auth requests) or fail-open-to-local (run the local handler as fallback). Fail-closed is simpler and safer; a degraded user-service is a global outage anyway. **Decision pending** — start fail-closed; revisit if ops want graceful degradation.
- **Notification microservice (8002) integration**: both monolith and user-service can call PMIS-notification-service. We keep the `NotificationClient` interface in both; both write `notification_log` rows. No coordination needed (different rows for different events).
