# Doc 38 — Master endpoint ownership split: user-service vs notification-service

> Cross-repo change. The monolith owns the routing decision (the proxy middleware); the user-service hands off ownership of one master slice; the notification-service gains a database and an admin surface for the first time.

## TL;DR

Three master-data slices currently proxy from monolith → **user-service (8001)**:

```
/api/v3/master/roles
/api/v3/master/permissions
/api/v3/master/notification_templates
```

The third one is mis-located. Notification templates are notification-domain data, not user-domain data. This doc moves `notification_templates` ownership to **notification-service (8002)** so each service owns the catalog it actually uses.

End state:

```
/api/v3/master/roles                     →  user-service        :8001  (unchanged)
/api/v3/master/permissions               →  user-service        :8001  (unchanged)
/api/v3/master/notification_templates    →  notification-service :8002  (NEW)
```

User-service stops carrying the templates table + renderer. When it needs to send a notification (login OTP, password reset), it POSTs `template_kind + payload` to notification-service — notification-service looks up the template, renders, dispatches.

---

## Why now

The proxy middleware was built in doc 37 part 2 with a path-prefix list pointed entirely at user-service. At the time, notification-service was stateless and templates lived next to the renderer in user-service — pragmatic but wrong on bounded-context grounds. Doc 36 (DB-backed templates) and doc 37 (extraction) both took the easy path and kept templates in user-service because user-service already had a DB.

Two specific frictions surfaced after doc 37 cutover:

1. **Templates ARE notification-domain data**. Renaming `password_reset_link` to `password_reset_url` should be one repo's concern, not "edit user-service AND remember to coordinate with notification-service for the dispatch contract."
2. **Future template kinds** (e.g. `project_published_notice`, `milestone_completed`) will be requested by project-management code paths. Routing those through user-service makes no sense.

The end state is "user-service knows about identity, notification-service knows about messages." This doc gets us there.

---

## What's in scope

- ✅ `notification_templates` table + 6 master endpoints move from user-service → notification-service.
- ✅ Monolith's `_PROXIED_PATH_PREFIXES` split: 2 prefixes route to user-service, 1 routes to notification-service.
- ✅ User-service's `_render_email` / `_render_sms` stop reading the local table; they POST `template_kind + payload` to notification-service which renders and dispatches.
- ✅ Notification-service gains: SQLAlchemy + Alembic + JWT auth middleware (shared SECRET_KEY) + `/api/v3/master/notification_templates/*` router.
- ✅ Notification-service's existing `/api/v1/notifications/email/send` and `/sms/send` gain a new optional shape — `{template_kind, payload, recipient}` — that does server-side rendering. The legacy pre-rendered shape (`subject`, `body`) keeps working for back-compat.

## What's out of scope

- ❌ Moving roles or permissions out of user-service. They stay where they are.
- ❌ Moving any project-management master slices (divisions, project_categories, etc.). They stay on the monolith.
- ❌ Dropping the legacy pre-rendered email/sms shape. Back-compat preserved.

## Sequence of changes

The order matters because the monolith proxy can't redirect to notification-service until notification-service has the endpoints. Three phases:

### Phase 1 — Notification-service gains template ownership

1. Add database + Alembic + auth middleware to notification-service.
2. Add `notification_templates` table + 6 seeded rows (same content as user-service had).
3. Add `/api/v3/master/notification_templates/*` master endpoints.
4. Add `template_service` for server-side rendering.
5. Extend `/api/v1/notifications/email/send` + `/sms/send` to accept `template_kind + payload` (legacy shape still works).
6. Smoke-test direct: POST `/api/v3/users/login` against monolith with the proxy CURRENTLY pointed at user-service, confirm nothing broken; then independently POST a templated email request to notification-service:8002 and verify it renders.
7. Push notification-service.

### Phase 2 — User-service stops being authoritative

1. Update user-service's `HttpNotificationClient.send` to POST `template_kind + payload` instead of pre-rendered subject/body. Mock backend unchanged.
2. Delete `app/api/v3/master_data/routes.py`'s notification-template section.
3. Drop the `notification_templates` table + seed from user-service. (DB column survives because monolith owns alembic; but the model file goes.)
4. Smoke-test the auth flows: login OTP, password reset link, password reset OTP. Confirm notification-service renders + dispatches.
5. Push user-service.

### Phase 3 — Monolith middleware split

1. Split `_PROXIED_PATH_PREFIXES`:
   ```python
   _USER_SERVICE_PREFIXES = (
       "/api/v3/users",
       "/api/v3/master/roles",
       "/api/v3/master/permissions",
   )
   _NOTIFICATION_SERVICE_PREFIXES = (
       "/api/v3/master/notification_templates",
   )
   ```
2. Add `NotificationServiceProxyMiddleware` (sibling of `UserServiceProxyMiddleware`) that proxies to `NOTIFICATION_SERVICE_URL`.
3. Add tests.
4. Push monolith.

After all three phases land, flip both proxy flags on in dev → staging → prod.

## Database coordination

`notification_templates` is in the **shared Postgres** today (along with `users`, `roles`, etc.). After this change:

- The TABLE remains in the shared Postgres (data continuity).
- WRITES come from the notification-service.
- READS come from the notification-service when it renders.
- User-service's model file is removed; user-service no longer reads or writes the table.

Notification-service's alembic chain is small (one initial revision + the table create + seed). It runs against the same shared Postgres. To avoid two services racing alembic on the same DB:

- **Recommended**: keep the monolith as the alembic owner. Notification-service ships migrations in its repo as new revisions (sharing the same chain via `down_revision = <monolith head>`); the monolith's alembic config is updated to scan both repos' `versions/` directories. This is fiddly.
- **Simpler alternative for this change**: ship notification-service with `MIGRATIONS_AUTORUN=false` like user-service. The `notification_templates` table is created by a one-shot migration ALREADY shipped in monolith doc 36 — the new ownership doesn't change schema. Notification-service just reads/writes existing columns.

We're going with the simpler alternative. No new monolith migration needed for this change.

---

## Auth strategy in notification-service

JWT decode + verification with the shared SECRET_KEY (HS256) — same pattern as user-service and monolith. Requests must carry `Authorization: Bearer <token>`. The notification-service does its own `master_data:view` / `master_data:manage` permission check against the user's effective permission set, looked up from the shared Postgres via the `permissions` / `role_permissions` / `user_roles` / `user_permissions` tables (read-only — user-service is still the writer).

This means notification-service needs read access to the RBAC tables. With shared Postgres, that's automatic.

## Cutover plan

Three env vars on the monolith:

```bash
USER_SERVICE_PROXY_ENABLED=true              # already documented in doc 37
USER_SERVICE_URL=http://10.1.131.199:8001    # already documented

NOTIFICATION_SERVICE_PROXY_ENABLED=false     # NEW — default off
NOTIFICATION_SERVICE_URL=http://10.1.131.199:8002  # NEW — already exists for other notification flows
```

When `NOTIFICATION_SERVICE_PROXY_ENABLED=false`, monolith's middleware doesn't intercept notification-template paths. Those requests fall through to monolith's local handlers (which still exist as the rollback path). When the flag flips on, monolith proxies to notification-service.

Same fail-closed contract as the user-service proxy: if notification-service is unreachable, return 503 with `errorIdentifier="notification_service_unavailable"`. No silent fallback to local.

## Risks + open questions

- **Notification-service rendering parity**: when user-service was rendering, the renderer had access to `FRONTEND_BASE_URL` for password-reset email links. Notification-service needs the same env var (it's already in their `.env.example` for other reasons). Verify in implementation.
- **Notification-service startup ordering**: now depends on shared Postgres. If Postgres is unhealthy, notification-service won't start. Document this dependency explicitly.
- **Test coverage**: the move-templates work shifts `test_doc36_notification_templates.py` coverage from user-service → notification-service. The monolith's `test_doc37_user_service_proxy.py` still covers the proxy contract for the user-service prefixes; we add `test_doc38_notification_service_proxy.py` for the notification-service prefixes.
- **Mock notification dispatch in user-service tests**: the user-service used to render templates locally for tests via the seeded table. After this change, user-service's tests need to mock `HttpNotificationClient.send` (or use a mock notification-service stub). The conftest's autouse template-seed fixture comes out.
