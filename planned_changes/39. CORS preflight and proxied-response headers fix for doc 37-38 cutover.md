# Doc 39 — CORS preflight and proxied-response headers fix for doc 37-38 cutover

> Cross-repo? **No.** Monolith-only — fix to `app/main.py` middleware order and the proxy clients in `app/shared/`.

After doc 37 (user-service proxy) and doc 38 (notification-service proxy) cutover went live in production with `USER_SERVICE_PROXY_ENABLED=true` and `NOTIFICATION_SERVICE_PROXY_ENABLED=true`, the FE on `http://10.1.131.199:3000` started reporting **"Failed to fetch"** on every login attempt. Server logs showed `OPTIONS /api/v3/users/login → 405` repeatedly, and `POST /api/v3/users/login → 200` immediately after — i.e. login succeeded server-side, but the browser refused to expose the response to JS code.

Two distinct bugs surfaced from the proxy cutover, both architecturally rooted in middleware ordering. This doc fixes both and pins the contracts with regression tests so they can't reoccur unnoticed.

| # | Sub-change |
|---|------------|
| 1 | Skip `OPTIONS` in both proxy middlewares so CORS preflights don't get forwarded to upstream services that don't register them. |
| 2 | Reorder `app/main.py` middleware stack so `CORSMiddleware` is OUTERMOST — the proxy short-circuits the response delivery, and any CORS middleware mounted *inside* the proxy never gets a chance to stamp `Access-Control-Allow-*` headers on the way out. |

---

## Why this exists

The doc-37 / doc-38 proxy is fundamentally a strangler-fig: the FE keeps calling monolith URLs, the monolith decides per-prefix whether to forward to a microservice. The browser sees only the monolith — so the CORS contract is between the browser and the monolith, regardless of which process actually fulfilled the request.

That contract has two surfaces:

1. **Preflight.** Before a non-simple cross-origin request (any `POST` with `Content-Type: application/json` qualifies), the browser sends `OPTIONS /<path>` with `Origin` + `Access-Control-Request-Method` headers and expects 200/204 with `Access-Control-Allow-*` in the response.
2. **Response headers on the actual call.** Even after a successful preflight, the actual `POST`/`GET` response must carry `Access-Control-Allow-Origin`, otherwise the browser fetches the body but blocks JS from reading it (the `"failed to fetch"` symptom).

Pre-cutover both surfaces were trivially handled because every `/api/v3/*` route was served by monolith's local handlers, which sit *inside* `CORSMiddleware`. The middleware caught preflights and stamped headers on responses — invisible plumbing.

After the proxy turned on, `UserServiceProxyMiddleware` and `NotificationServiceProxyMiddleware` started intercepting matching paths and forwarding to user-service / notification-service. Two things broke at once:

- The proxies forwarded `OPTIONS` requests too — but user-service / notification-service routes only register `POST`/`GET`/`PATCH`/etc., so FastAPI returned 405 on every preflight.
- Even when a `POST` succeeded server-side and got proxied through cleanly, the proxy short-circuits the response by calling `await response(scope, receive, send)` directly — `self.app` is never invoked. That bypasses every middleware layered *inside* the proxy. `CORSMiddleware` was added FIRST in `app/main.py`, making it the innermost wrapper, so the proxy's short-circuit `send` skipped it and the response went out without `Access-Control-Allow-Origin`.

## What's in scope / out of scope

- ✅ Both proxy middlewares now early-return for `method == "OPTIONS"` — request falls through to `CORSMiddleware`.
- ✅ `CORSMiddleware` moved to be the LAST `add_middleware(...)` call in `app/main.py` so it's the OUTERMOST wrapper, capturing both proxied and local responses.
- ✅ Regression tests pinning each contract.
- ❌ No change to `CORS_ORIGINS` allowlist — the existing config already includes the FE's deployed origin.
- ❌ No change to user-service / notification-service. They never needed CORS in the first place; they're internal-network services and should never receive a browser request directly.

## Decision log

| Q | Decision | Rationale |
|---|---|---|
| 1 | Should the proxy forward `OPTIONS` to upstream and let user-service handle CORS, or short-circuit `OPTIONS` locally on the monolith? | **Short-circuit locally.** | CORS is a contract between the browser and *the URL the browser typed*. The upstream service doesn't know about the FE origin (and shouldn't — it's an internal-network service) so it has no business answering preflight. Keeping CORS on the gateway is the textbook architecture. |
| 2 | If `CORSMiddleware` outermost handles preflight, is the proxy's `OPTIONS` early-return redundant? | **Keep both.** | Belt-and-suspenders. If anyone later reorders middleware without realising the dependency, the proxy bypass still prevents 405s. The early-return is a 3-line guard with zero hot-path cost. Redundancy is fine when each layer can stand alone. |
| 3 | Should the proxy add CORS headers itself when forwarding (instead of relying on `CORSMiddleware` outermost)? | **No.** | Two sources of CORS truth = inevitable drift. Allowlist lives in `CORSMiddleware`'s config; the proxy must not duplicate that logic. |
| 4 | Why not just configure `CORSMiddleware` per-route? | **N/A — not a Starlette feature.** | Starlette's `CORSMiddleware` is a single global middleware. Per-route CORS would be a custom dependency, vastly more code for no gain. |

## Service-layer rules

The proxies (`UserServiceProxyMiddleware`, `NotificationServiceProxyMiddleware`) now have an early-return at the top of `__call__`:

```python
if (scope.get("method") or "").upper() == "OPTIONS":
    await self.app(scope, receive, send)
    return
```

This runs BEFORE the path-prefix match check, so it applies regardless of whether the path would otherwise be proxied. `OPTIONS` requests on proxied paths fall straight through to `self.app`, which (with `CORSMiddleware` outermost) means CORS handles preflight before any other middleware sees the request.

Middleware order in `app/main.py` after the fix (request order, outermost → innermost):

1. `CORSMiddleware` (added LAST → runs first)
2. `NotificationServiceProxyMiddleware`
3. `UserServiceProxyMiddleware`
4. `AuthenticationMiddleware`
5. `LoggingMiddleware` (added FIRST → runs last)

Response order is reversed: when `UserServiceProxyMiddleware` short-circuits `send`, the message bubbles up through `NotificationServiceProxyMiddleware` (no-op for non-matching paths) and then `CORSMiddleware`, which stamps `Access-Control-Allow-*` headers before the message reaches the network.

### Smoke / integration test

Reproduce against the deployed system (10.1.131.199):

```bash
# 1. CORS preflight on a proxied path — must return 2xx with Allow-Origin echoed
curl -i -X OPTIONS http://10.1.131.199:8000/api/v3/users/login \
    -H 'Origin: http://10.1.131.199:3000' \
    -H 'Access-Control-Request-Method: POST'
# expect: 200 + access-control-allow-origin: http://10.1.131.199:3000

# 2. Actual POST — response must carry Allow-Origin
curl -i -X POST http://10.1.131.199:8000/api/v3/users/login \
    -H 'Origin: http://10.1.131.199:3000' \
    -H 'Content-Type: application/json' \
    --data-raw '{"login":"admin","password":"admin123"}'
# expect: 200 + access-control-allow-origin: http://10.1.131.199:3000
#         in response headers (was MISSING pre-fix)
```

Browser-level: log in from the FE on `http://10.1.131.199:3000` — should now succeed without "Failed to fetch".

## Risks + open questions

- **Risk: future maintainer moves `CORSMiddleware` back to "the top of the file" to match the apparent FastAPI tutorial pattern.** Mitigation: the regression tests fail loudly with a message that points at exactly this. The comment block above the middleware stack explains the ordering dependency.
- **Risk: the proxy's `OPTIONS` early-return becomes redundant when CORSMiddleware is outermost (it never reaches the proxy for OPTIONS preflight).** Decision: keep it (per Decision log Q2). It's defensive and costs nothing.
- **Open question: should we add a similar test against the FE origin specifically (`http://10.1.131.199:3000`) rather than `http://localhost:3000`?** Probably not — `CORS_ORIGINS` allowlist already includes the FE origin, and using the dev origin in tests keeps them runnable on developer laptops without the production env. The smoke recipe above covers the prod-origin case.

### Security implications

`allow_credentials=True` plus the `CORS_ORIGINS` allowlist now form the **FE-trust boundary** for the whole product. With `CORSMiddleware` as the outermost layer, every response (local handler, proxied to user-mgmt, proxied to notification-service) is exposed to any origin in that list. Adding an origin to `CORS_ORIGINS` is therefore a security-sensitive change — anything in there can mount authenticated calls on behalf of a logged-in user. Concretely:

- Never add `"*"` to `CORS_ORIGINS` — Starlette rejects it with `allow_credentials=True` anyway, but the wrong response would be to drop credentials, which would break the FE.
- Never add a third-party domain "for testing." A site embedded under that origin can quietly mount API calls against the user's session.
- The proxy's response-header allowlist (currently `content-type`, `x-request-id` in `_proxy_request_sync`) determines what upstream services can leak through to the browser. Future additions (e.g. `Set-Cookie`) need security review — once a header passes the allowlist, CORS exposes its value to JS on any allowlisted origin.
- If the microservices ever move to a public ingress, they need their own CORS posture. Today they're internal-only and have none — the doc-39 fix relies on monolith being the only browser-facing surface. See [points_to_consider/cors-middleware-must-stay-outermost.md](../points_to_consider/cors-middleware-must-stay-outermost.md) for the full guidance.

The full reasoning, defense-in-depth rationale, and future-maintainer guidance lives in [points_to_consider/cors-middleware-must-stay-outermost.md](../points_to_consider/cors-middleware-must-stay-outermost.md).

### Lessons learned

- **The proxy short-circuit pattern is incompatible with naive middleware-stack reasoning.** When middleware A wraps middleware B, the convention is "A wraps B's responses too." That breaks the moment B is a proxy that doesn't call `self.app` — A's response wrapper is bypassed. Any future middleware that needs to wrap responses (rate limiting, request-ID stamping, custom headers) must be **outermost** of any proxy in the stack.
- **CORS bugs are bimodal** — preflight failure and missing-response-headers look very different in client logs but the diagnostic answer is the same: the wrapping CORSMiddleware isn't seeing the request/response. Always probe both surfaces (`curl -X OPTIONS` and `curl -X POST -H 'Origin: ...' -i`) when CORS misbehaves.
- **"Failed to fetch" is an unhelpful browser error.** It often means CORS, but can also mean network-layer failure (DNS, TLS, connection refused) or a Mixed-Content blocker. The first check should always be: open DevTools → Network tab → look at the actual response. If status is 200 but no body is delivered to JS, it's CORS. If the request never leaves the browser, it's preflight or network.
- **Belt-and-suspenders is OK in middleware.** Two layers each catching `OPTIONS` is fine — they don't conflict, they're cheap, and one makes the other unnecessary in normal operation but not in pathological reorderings. Defense in depth has a budget; this fits inside it.

### Going forward — when to touch which repo

This was monolith-only. The user-service and notification-service repos don't carry CORS at all — they're internal-network services that should never see a browser. If future work pushes them to a public ingress, *that's* the right time to add CORS to them; not now.

For any new middleware in monolith's `app/main.py`:
- If the middleware needs to mutate responses, add it **after** the proxy middlewares (so it ends up outside them in the stack).
- If the middleware only mutates requests, it can go inside or outside the proxy depending on whether it should run for proxied-away paths.
- The comment block above the middleware stack documents the rule. Update it if a new middleware joins.
