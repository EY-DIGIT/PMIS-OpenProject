# Doc 40 — Tree endpoint: `scheduleStatus` + `daysDelayed` on M/A/T/S nodes

> Single endpoint, single change. `GET /api/v3/projects/{project_uuid}/tree` now carries a `scheduleStatus` field on every milestone, activity, task, and subtask in the response — and a `daysDelayed` field on the subset that have slipped past their expected end date.

| # | Sub-change |
|---|------------|
| 1 | Compute schedule status from each node's expected `start_date` / `end_date` against today's IST calendar date — values: `"not_started"`, `"in_progress"`, `"delayed"`. |
| 2 | When status is `"delayed"`, also include `daysDelayed` (integer count of calendar days past the expected end date). Omit the field on non-delayed nodes. |

---

## Why this exists

The FE renders the project tree (milestones → activities → tasks → subtasks) and needs to know which items are running late. Each node already carries `startDate` and `endDate`; computing `today vs window` everywhere on the FE means duplicating the logic across grid rows, gantt charts, status badges, etc., and risks drift if every component computes "today" slightly differently. Doing it once on the BE — at the same instant for the whole tree — gives every consumer a consistent answer with zero client-side arithmetic.

The `daysDelayed` companion is the obvious follow-on: a delay badge ("3 days late") needs the count, and counting back from `endDate` on the FE is the same redundant arithmetic. Returning it inline keeps the FE rendering trivial.

---

## What's in scope / out of scope

- ✅ Read-only enrichment of the tree response. No DB schema change. No new endpoint. No write-side change.
- ✅ Applies to all four levels: milestone, activity, task, subtask.
- ❌ Does **not** consider `actual_start_date` / `actual_end_date`. The field answers "is this on schedule?", not "is this done?". Items completed before/on time read as `in_progress` while inside their window, then transition to whatever the date math says when the window closes. Items completed late read as `delayed` (the delay calc uses `endDate`, not the actual completion date). See "Open question" below.
- ❌ Does **not** affect any other endpoint. `GET /api/v3/milestones`, `GET /api/v3/activities/{id}`, etc., do not get `scheduleStatus` in this doc — the tree is the consumer that asked. Other endpoints can pick this up in a follow-up if needed.
- ❌ No FE work in this repo. The new fields are purely additive on the wire; existing FE clients ignore them. A FE PR can light up new badges/columns in a follow-up — independent of this deploy.

## Decision log

| Q | Decision | Rationale |
|---|---|---|
| 1 | What to call the field? | **`scheduleStatus`**. | Distinct from the existing lifecycle `status` column on activities/tasks/subtasks (which holds values like `not_completed` / `completed`). Naming it `status` would collide and confuse FE consumers. |
| 2 | Snake-case or camel-case values? | **Snake-case strings** (`"not_started"`, `"in_progress"`, `"delayed"`). | Matches the existing `status` column conventions in the codebase. The user's spec wrote `"not started"` / `"in progress"` / `"delayed"` with spaces; underscored form is the canonical API representation, FE can pretty-print as needed. |
| 3 | Always include `daysDelayed`, or only when delayed? | **Only when delayed.** | The user's spec says "If the status is delayed, then the number of days of delay will be returned." Emitting `daysDelayed: null` everywhere would be valid JSON but would invite FE consumers to misread it as "no delay yet" rather than "not applicable." Omitting the key entirely when the status isn't `"delayed"` makes the API contract unambiguous: presence of `daysDelayed` ⇒ status is `"delayed"`. |
| 4 | Should `actual_*_date` factor in? | **No** — expected dates only. | Keeps the field's meaning crisp: it's a schedule view, not a completion view. A future doc can add `completionStatus` if the team wants the orthogonal "is this done?" axis. Mixing both into one field requires four states (not started / in progress / completed / delayed) and the user explicitly asked for three. |
| 5 | How is "today" computed? | **IST calendar date sampled once per request.** | The codebase is single-region (UIDAI/India) and stores M/A/T/S start/end as IST midnight via `to_ist_calendar_midnight`. Comparing against UTC's `.date()` would shift the calendar by 5h30m and flip the verdict for nodes whose end date is "today" between 18:30-23:59 UTC. Sampling once at the top of `build_project_tree` also keeps every node consistent on a slow request that straddles IST midnight. |
| 6 | Inclusive or exclusive boundaries? | **Inclusive at both ends.** | A milestone with `endDate == today` is in its last day of work, not late. `today < startDate` ⇒ not started; `startDate ≤ today ≤ endDate` ⇒ in progress; `today > endDate` ⇒ delayed. Matches the inclusive-range fix shipped for bug #54. |

## API surface

### Changed endpoint

`GET /api/v3/projects/{project_uuid}/tree`

Each node in `data.milestones[].activities[].tasks[].subtasks[]` (recursive) now includes:

| Key | Type | Cardinality | Meaning |
|---|---|---|---|
| `scheduleStatus` | string | always | `"not_started"`, `"in_progress"`, or `"delayed"`. |
| `daysDelayed` | integer | only when `scheduleStatus == "delayed"` | Count of calendar days `today - endDate` (today and endDate compared as IST calendar dates). |

The change is **backwards-compatible**: all pre-existing keys in the response are unchanged in shape and meaning. Older FE clients that don't know about `scheduleStatus` simply don't render anything for it.

### Unchanged endpoints

`/api/v3/milestones`, `/api/v3/activities/...`, `/api/v3/tasks/...`, `/api/v3/subtasks/...`, `/api/v3/projects` — none of these get the new fields under this doc. Followups can mirror the helper if needed.

## Service-layer rules

The two new helpers are pure functions in `app/api/v3/tree/service.py`:

```python
def _ist_calendar_date(dt: Optional[datetime]) -> Optional[date_type]:
    """Convert a stored UTC datetime to its IST-local calendar date."""

def _schedule_status(
    start_date: Optional[datetime],
    end_date: Optional[datetime],
    today: date_type,
) -> Tuple[str, Optional[int]]:
    """Returns (status, days_delayed)."""
```

`_schedule_status` is the only piece a future maintainer needs to read. Logic:
- Both dates `None` (or one of them) → `("not_started", None)`. Defensive default for legacy rows that haven't had dates set.
- `today < start_date_ist` → `("not_started", None)`.
- `start_date_ist ≤ today ≤ end_date_ist` → `("in_progress", None)`.
- `today > end_date_ist` → `("delayed", (today - end_date_ist).days)`.

`build_project_tree` samples `today_ist = datetime.now(IST).date()` once at the top of the function, then each `*_node()` builder calls `_attach_schedule_status(payload, m.start_date, m.end_date, today_ist)` before returning. The helper mutates the payload dict in place and returns it for fluent chaining.

## Risks + open questions

- **Risk: clock skew between the deployment VM and IST wall-clock.** The verdict is sampled from `datetime.now(IST)`, which is `datetime.now(UTC).astimezone(IST)`. If the host's NTP is broken and the system clock drifts, items right at the end-date boundary could flip prematurely. The host has standard `chronyd` / `systemd-timesyncd` running and we don't depend on sub-day precision, so this is essentially zero risk in practice. Worth flagging only because the field is timing-derived.
- **Open question: should `actual_end_date <= end_date` flip the status?** If yes, an item completed early should probably *not* be in `"in_progress"` until its `endDate` arrives — it should reflect "completed on time" somehow. The current spec only allows three states, so we left this out. If the team later wants a four-state model (add `"completed"`), the helper change is small (consult `actual_end_date`) but it's a wire-shape change so it deserves its own doc.
- **Open question: should the project itself get the field?** Currently only M/A/T/S nodes carry `scheduleStatus`; the top-level `data.project` block has `startDate` and `endDate` but no schedule status. Easy to add via the same helper; left out because the user's spec said "M/A/T/S objects" specifically.

### Lessons learned

- **Compute "today" once per request.** Different node builders calling `datetime.now()` independently would drift across a slow request straddling IST midnight, producing inconsistent verdicts on items whose end-date is exactly today. One sample at the top of `build_project_tree` and pass it down.
- **IST conversion is the only subtle bit.** Stored datetimes are tz-aware UTC after the `UtcDateTime` bind. Calling `.date()` on a UTC datetime yields the **UTC** calendar date, off by 5h30m for boundary cases. The helper explicitly converts to IST first (`dt.astimezone(IST).date()`); skipping that step would give the wrong verdict for nodes whose end date is "today" between 18:30 and 23:59 UTC. There's a unit test pinning this.
- **Omit-when-N/A reads better than always-null.** Returning `daysDelayed: null` for non-delayed nodes is technically fine, but downstream consumers tend to interpret `null` as "no delay yet" rather than "not applicable." Omitting the key entirely makes the contract unambiguous and matches the user's spec verbatim.

### Going forward — when to touch which repo

Future work that wants the same `scheduleStatus` field on other endpoints (single-milestone GET, activity GET, project list) should:
1. Import `_schedule_status` from `app/api/v3/tree/service.py` (or move it to `app/shared/schedule_status.py` if more than one endpoint imports it — refactor that out the second time it's needed, not the first).
2. Pass the same `today_ist = datetime.now(IST).date()` so all endpoints agree on the verdict for a given moment.

A FE PR can land independently; nothing in this doc blocks them.
