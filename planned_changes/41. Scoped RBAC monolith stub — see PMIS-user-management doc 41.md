## Outcome (post-deploy)

The full deploy → validation → fixes → rollback sequence is documented
in detail at the canonical doc:
[PMIS-user-management/planned_changes/41 → "Outcome (post-deploy)"](../../PMIS-user-management/planned_changes/).

Monolith-relevant highlights:

- Live deploy succeeded as `pmic-backend:v83` and was promoted to
  `:v84` after a permission seed-list trim (`PROJECT_ADMIN_ROLE_PERMISSIONS`
  no longer carries `MILESTONES_UPDATE` / `ACTIVITIES_UPDATE`; commit
  `361ac98`).
- 65 / 65 cases of the live role-permission matrix matched expected
  behaviour against monolith-hosted routes (project lifecycle +
  M / A / T / S writes + project_members CRUD).
- The work was **rolled back** at the user's request after validation
  completed. The DB was restored from `pmis_db_backup_pre_doc41_20260507_212051.sql`
  (preserved on the deploy host as a recovery artifact) and the
  monolith container reverted from `:v84` to `:v82`. The `:v83` and
  `:v84` images stay in the host's local registry as an audit trail
  / fast re-deploy path.
- Git commits stay on `dev` (`e80d1c8`, `b04fd75`, `d92cb42`,
  `361ac98`) as the source of truth. Re-deploying is a matter of
  rebuilding from those commits and running `alembic upgrade head`
  on the restored-pre-doc-41 schema.
