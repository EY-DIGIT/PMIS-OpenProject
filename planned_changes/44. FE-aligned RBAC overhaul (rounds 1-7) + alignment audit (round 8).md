## Why this exists

Doc 43 closed the security-hardening pass (admin demotion, F1–F4
hierarchy gates, lockout pivot). What followed was a series of
spec-clarification rounds from the FE team — the doc-41 RBAC was
correct in shape but mismatched the FE's actual consumption pattern
in dozens of small ways. Each round was a tight loop: a one-page
FE spec annotation → a tiny backend patch → a short test class →
deploy. The cumulative result is that the wire shapes the FE reads
off `/users`, `/vendors`, `/projects`, `/role-assignments`, and the
new `/role-grants` lookup all match the FE's mental model exactly.

Round 8 is the final close-out: a triage pass against the open bug
list to figure out which remaining items are backend, which are
frontend, and which are already fixed but not yet observed by the FE
team. The result is the table in §"Round 8 — alignment audit"
below.

## Round-by-round summary (rounds 2–7)

### Round 2 — admin tier opened up
- Removed G4 (admin → admin password change) + G5 (admin → admin
  DELETE) per FE spec ("admins are peers for destructive ops").
- `can_caller_grant`: admin now grants admin.
- Updated `RBAC_GUIDE` last-refresh stamp to 2026-05-08.

### Round 3 — project mapping optional on user create
- `POST /users/create` no longer fails when `project_ids` is empty
  or omitted.
- Validation moved to the orgRole-specific paths: `project_admin`
  and `project_member` still require at least one project id, but
  `org_admin` / `division_member` / no-orgRole creates accept empty.

### Round 4 — caller-scoped list filters
- `GET /projects`: when caller is non-admin, filter to projects the
  caller is associated with via union of (project_members,
  project-scoped role-assignments, org-scoped role-assignments
  joined on project_vendors).
- `GET /vendors`: when caller is non-admin, filter to the vendor
  matching `users.vendor_id` (callers without a vendor mapping see
  an empty list).

### Round 5 — per-role perm overhaul + project-scope gate hardening
- `ORG_ADMIN_ROLE_PERMISSIONS` rewritten: drops `users:create` /
  `users:update` / `users:delete`; gains `users:deactivate` (status
  flip only) + `rbac:assign` + `project_members:*`. Same for
  `project_admin`.
- `PROJECT_MEMBER_ROLE_PERMISSIONS` slimmed: no `users:read`, no
  `vendors:read` — User Mgmt + Vendor Mgmt menus invisible to them.
- `PATCH /users/{id}` route gate widened to accept either
  `users:update` (full edit) OR `users:deactivate` (status field
  only). Service rejects non-status fields when caller has only
  `users:deactivate`.
- New permission code `users:deactivate` added to both repos.
- `require_project_permission` (option a) walks project → vendor so
  org-scoped perms apply only to the right projects (no cross-vendor
  leak).
- Round 5 also reverted round 2 admin-grant relaxation: admin can
  no longer grant peer admin. Only super_admin can.

### Round 6 — vendor user_assignments matrix
- `PATCH /vendors/{vendor_id}`: new field `user_assignments` —
  `[{project_id, role, user_ids[]}]`. Desired-state semantics: for
  each `(project_id, role)` tuple, the `user_ids` list REPLACES any
  existing role-assignment rows for that tuple (insert missing,
  delete absent).
- `POST /vendors/create` and `GET /vendors/{id}` echo the same
  shape so the FE can read what it sent.

### Round 7 — alignment audit (the big one)
Items #1–#9 from the round-7 audit:
1. super_admin role is ungrant-able through the API on every path
   (top-tier closure). `can_caller_grant` rejects with a fixed
   "init_db only" message regardless of caller tier.
2. admin → admin mutations blocked on ALL ops (PATCH / password /
   DELETE), not just destructive — `can_caller_modify_user` extended.
3. `GET /users` vendor-scoped for non-admin callers (org_admin /
   project_admin see only users with matching `users.vendor_id`).
   Sentinel `__no_vendor_assigned__` for callers without a vendor
   mapping → empty result.
4. `PATCH /users/{id}` vendor-scope target check (non-admin caller
   can only PATCH own-vendor users; self-PATCH bypasses).
5–8. Spec clarifications already covered earlier (org_admin sees
   only own-org projects, project_admin can't change roles, can't
   self-unassign, etc.).
9. `tasks:delete` + `subtasks:delete` added to `ORG_ADMIN` and
   `PROJECT_MEMBER` seeds. `project_admin` already had them.
- New endpoint `GET /api/v3/role-grants/{role_name}` — static
  matrix lookup. Returns the list of role names the caller-tier
  `role_name` can grant via the role-assignment API. Bound to the
  `can_caller_grant` rules:
    - `super_admin` → `[admin, org_admin, project_admin, project_member, division_member]`
    - `admin` → `[org_admin, project_admin, project_member, division_member]`
    - `org_admin` → `[project_admin, project_member, division_member]`
    - `project_admin` → `[project_member]`
    - `project_member` / `division_member` / unknown → `[]`
- `format_collection_response` now passes `db` to
  `format_user_response` so the `orgRole` projection runs per row
  on the list path (was only present on GET-by-id pre-round-7).
- Project-admin self-unassign blocked on
  `DELETE /projects/{id}/role-assignments/{aid}` when target == caller
  AND target role is `project_admin` (only admin / super_admin can
  unassign a project_admin from their own project).

## Round 8 — backend fix plan (the six BE bugs)

### Fix 1 — `GET /vendors/{id}` vendor-scope check (bug #2)

**Where**: `PMIS-OpenProject/app/api/v3/vendors/routes.py::get_vendor`
(also reachable via `/api/v3/master/vendors/{id}` delegate at
`master_data/routes.py`).

**Current behaviour**: After the `require_permission(VENDORS_READ)`
gate passes, the handler resolves the vendor by id-or-code and
returns it. There is NO check that the caller is allowed to read
THIS vendor — every authenticated user with `VENDORS_READ` can fetch
any vendor by id (live-confirmed cross-vendor leak).

**Fix**: Mirror the pattern in `list_vendors` (lines 227–240):
admin / super_admin pass through; everyone else is rejected with
403 unless `vendor.id == caller.vendor_id`. Implementation:

```python
caller_id = get_current_user_id(request)
if caller_id is not None:
    repo_user = UserRepository(db)
    repo_rbac = RbacRepository(db)
    if not repo_rbac.user_has_admin_role(caller_id):
        caller = repo_user.get_by_id(caller_id)
        caller_vendor = getattr(caller, "vendor_id", None) if caller else None
        if caller_vendor != vendor.id:
            raise ForbiddenError(
                "Insufficient permissions to view this vendor."
            )
```

Apply the same to the master-router delegate.

**Test**: `tests/test_doc44_round8_vendor_scope.py::TestVendorGetScope`
— OA scoped to vendor X requesting vendor Y returns 403; admin
returns 200; OA requesting own vendor returns 200; self-vendor
match works for OA without admin role.

### Fix 2 — `GET /projects` filter unpublished for non-admin (bug #3)

**Where**: `PMIS-OpenProject/app/api/v3/projects/services/list.py::list_projects`.

**Current behaviour**: When caller is non-admin, the visibility
filter narrows by membership (lines 79–103) but does NOT filter by
`ProjectModel.status`. Org-admin / project-admin / project-member
all see projects in any status (`draft`, `new`, `published`, etc.)
as long as they're associated. Live-confirmed: OA sees a `draft`
project.

**Fix**: After the existing visibility-union filter, add:

```python
# Doc 44 round 8 — non-admin tiers see only published projects.
# Spec: "Org Admins, Project Admins, and Project Members should
# not be able to view projects assigned to them before the
# projects are published."
query = query.filter(ProjectModel.status == "published")
```

Place it INSIDE the `not user_has_admin_role` branch so admins keep
the all-statuses view. The single `GET /projects/{id}` endpoint
needs the same gate: a non-admin caller fetching an unpublished
project should get 404 (or 403 — pick one and stay consistent with
the membership filter's silent-hide behaviour; 404 matches the list
filter best).

**Open question**: should `closed` / `suspended` / `archived`
projects also be hidden post-publish? The spec only mentions
"before they are published" — likely the FE wants the full lifecycle
shape (closed projects still appear). Confirm with FE before
shipping.

**Test**: `tests/test_doc44_round8_project_status_filter.py`:
`TestProjectListFiltersUnpublished` — OA / PA / PM mapped to
project P with `status='draft'` get an empty list; admin sees P;
flipping P to `status='published'` makes it visible to all four.

### Fix 3 — strip `MASTER_DATA_VIEW` from `org_admin` (bug #4)

**Where**:
- `PMIS-OpenProject/app/core/permissions.py:295`
- `PMIS-user-management/app/core/permissions.py:311` (mirror)

**Current behaviour**: `ORG_ADMIN_ROLE_PERMISSIONS` includes both
`VENDORS_READ` and `MASTER_DATA_VIEW`. Live-confirmed: OA can
`GET /master/divisions` (HTTP 200, returns 3 rows). Spec says OA
must not have any Master Data access.

**Fix**: Remove `MASTER_DATA_VIEW` from `ORG_ADMIN_ROLE_PERMISSIONS`
in both repos. Keep `VENDORS_READ` (org_admin still needs to view
vendors — their own).

**Self-heal**: The `_align_role_permissions` boot loop in
`RbacRepository` already revokes drift; existing OA roles in the DB
will lose `master_data:view` on next service restart. No alembic
needed.

**Test**: `tests/test_doc44_round8_master_data_perm.py`:
`TestOrgAdminMasterDataPerm::test_seed_excludes_master_data_view`
+ `test_org_admin_403_on_master_endpoints` (route-level; covers
`/master/divisions`, `/master/resource-types`, `/master/vendors`,
`/master/permissions`).

### Fix 4 — `user_assignments`-only PATCH for org_admin (bug #7)

**Where**: `PMIS-OpenProject/app/api/v3/vendors/routes.py::update_vendor`.

**Current behaviour**: The route has a single
`require_permission(VENDORS_MANAGE)` gate covering ALL fields.
org_admin lacks `vendors:manage`, so even a body containing only
`{"user_assignments": [...]}` returns 403 (live-confirmed).

**Fix** (preferred): split the gate into a body-shape-aware check.

```python
# Doc 44 round 8 — user_assignments carve-out for org_admin.
# Spec: "Org Admins should be able to assign Project Admins and
# Project Members to projects from the Project Mapping section."
# Treat user_assignments as a separate gate (rbac:assign) so the
# matrix update doesn't require vendors:manage.
held = getattr(request.state, "user_permissions", set()) or set()
data_dict = data.dict(exclude_unset=True)
non_assignment_fields = {
    k for k in data_dict.keys() if k != "user_assignments"
}
if non_assignment_fields and VENDORS_MANAGE not in held:
    raise ForbiddenError("vendors:manage required to edit vendor fields.")
if "user_assignments" in data_dict and not (
    VENDORS_MANAGE in held or RBAC_ASSIGN in held
):
    raise ForbiddenError("rbac:assign required to update user_assignments.")
```

Replace the current single dependency with this in-body check.
Pre-validate per-(project, role) tuple via the existing
`can_caller_grant` so an org_admin can only set assignments on
projects in their vendor (the `_create_assignment` helper already
handles the gate; reuse it instead of writing rows directly).

**Test**: `tests/test_doc44_round8_vendor_user_assignments_perm.py`:
`TestOrgAdminCanPatchUserAssignmentsOnly`:
- OA PATCH `{user_assignments: [...]}` on own vendor → 200, rows landed.
- OA PATCH `{name: "x", user_assignments: [...]}` on own vendor → 403 (still needs `vendors:manage` for `name`).
- OA PATCH `{user_assignments: [...]}` on OTHER vendor → 403 (gate blocks via `can_caller_grant` since OA isn't org_admin of the target vendor).
- admin PATCH `{name: "x", user_assignments: [...]}` → 200 (full perms).

### Fix 5 — `USERS_READ_ALL` for `project_admin` (bug #18)

**Where**:
- `PMIS-OpenProject/app/core/permissions.py:318` (`PROJECT_ADMIN_ROLE_PERMISSIONS`)
- `PMIS-user-management/app/core/permissions.py` mirror at the same role list

**Current behaviour**: `PROJECT_ADMIN_ROLE_PERMISSIONS` carries
`USERS_READ` (own-profile / single-user reads) but NOT
`USERS_READ_ALL`. The list endpoint `GET /api/v3/users` requires
`USERS_READ_ALL`. Live-confirmed: PA hits 403 on `GET /users`. The
spec wants the Users list visible to PA so they can pick assignees
when mapping project_member roles.

**Fix**: Add `USERS_READ_ALL` to `PROJECT_ADMIN_ROLE_PERMISSIONS` in
both repos. The round-7 vendor-scope filter on `GET /users` (in
`PMIS-user-management/app/api/v3/users/controller.py::list`) already
limits non-admin callers to their own-vendor users, so PA will see
exactly the users they need (their vendor's roster) — no
cross-vendor leak.

**Self-heal**: `_align_role_permissions` boot loop adds the missing
permission to existing PA role rows on next service restart. No
alembic needed.

**Test**: `tests/test_doc44_round8_project_admin_users_list.py`:
`TestProjectAdminCanListUsers`:
- PA `GET /users` → 200 (was 403).
- Returned list contains only users whose `vendor_id` matches PA's
  vendor (vendor-scope filter from round 7 still active).
- Cross-vendor user not present.

### Fix 6 — `GET /projects/{id}/role-assignments` on monolith (bug #10)

**Where**: `PMIS-OpenProject/app/api/v3/projects/routes.py`.

**Current behaviour**: User-mgmt :8001 has the route at
`/api/v3/projects/{project_uuid}/role-assignments` returning role
buckets (live-confirmed). Same path on monolith :8000 returns 404.
The FE consumes monolith routes for project context, so they either
silently drop the call or hit the wrong service.

**Fix**: Mirror the user-mgmt handler on the monolith. Same shape
on the wire:
```json
{
  "data": {
    "projectId": "...",
    "projectName": "...",
    "roles": [
      { "roleId": 18, "roleName": "project_admin", "users": [{...}] },
      { "roleId": 19, "roleName": "project_member", "users": [{...}] }
    ]
  }
}
```
Reads directly from `user_role_assignments` (shared-DB table — both
services see the same rows). Gated with `require_permission(PROJECT_MEMBERS_READ)`.

**Test**: `tests/test_doc44_round8_alignment.py::TestProjectRoleAssignmentsOnMonolith`:
- Returns role-grouped buckets with the expected user fields.
- 404 on unknown project_uuid.

## Round 8 — frontend fix plan (the ten FE bugs)

These items were not investigated end-to-end (the FE on `:3000`
isn't reachable from the BE-side network). Each entry below pairs
the bug with the BE shape it should consume + a one-paragraph FE
work description, so the FE team can pick them up without re-tracing
the audit.

### FE-1 — Rename "Vendors" to "Organizations" in Project Details

Pure label change. Search for the string "Vendor"/"Vendors" in the
Project Details template + tab labels and replace with
"Organization"/"Organizations". The backend keeps the `vendor`
entity name on the wire — no API changes consumed.

### FE-5 — Role-aware, read-only filters for Org/Project Admins

When the logged-in user is `org_admin` or `project_admin`:
- The vendor / organization filter on Search Project should be
  pre-set to the user's own vendor and disabled (read-only).
- The status filter should be pre-set to `published` (after fix
  #3 on the BE, only `published` is returned anyway, but the UI
  should reflect this so the user understands the constraint).
The FE knows the caller's role from the login response (`orgRole`)
and the caller's vendor from the same payload (`vendorId`).

### FE-6 — Hide Org Name + Status edit controls for Org Admins

Backend already returns 403 when `org_admin` tries to PATCH `name`
or `active`/`status` on a vendor. The FE should hide / disable
those input fields when `orgRole === 'org_admin'`. Show only the
read-only display.

### FE-8 — Edit-Organization redirect by role

On the Project Details page, the "Edit Organization" CTA should
branch:
- `super_admin` / `admin` → navigate to **Search Organization**
  page with the vendor IDs from the project's vendor list
  preselected in the multi-select filter (URL-encode the vendor IDs
  in a query param the Search Organization page already supports).
- `org_admin` → navigate directly to **Organization Details** for
  their own vendor (the `vendorId` from the user's profile). Do
  NOT include the multi-select query.
The role check should use `orgRole` from the user object the
session holds.

### FE-9 — Render the `orgRole` column on Search User

The `GET /api/v3/users` response now carries `orgRole` per row
(string: `super_admin`, `admin`, `org_admin`, `project_admin`,
`project_member`, `division_member`, or `null`). Add a "Role"
column to the table that renders this field. Display label
mapping for the FE:

| `orgRole` value | Display |
|---|---|
| `super_admin` | Super Admin |
| `admin` | PMIS Admin |
| `org_admin` | Org Admin |
| `project_admin` | Project Admin |
| `project_member` | Project Member |
| `division_member` | Division Member |
| `null` | — |

### FE-11 — De-duplicate already-assigned users in role-assignment dropdown

When the Project Mapping screen is open and the FE has the current
list of users assigned to project P at role R (from the
`/api/v3/projects/{P}/role-assignments` response — now available on
both monolith and user-mgmt per fix #6), filter those users out of
the "add user to project at role R" dropdown for the same
(project, role) pair. The backend treats the assignment as
idempotent — the dedup is purely UX so users don't see duplicates.

### FE-12 — Show the Role field on user-edit forms; gate edit by caller

On the user-create / user-edit form:
- Always show the Role field (read-only by default).
- Make it editable only when the **caller's** orgRole is
  `super_admin`, `admin`, or `org_admin`.
- The list of grantable role options for the dropdown comes from
  `GET /api/v3/role-grants/{caller_role}` — that endpoint returns
  exactly the roles the caller-tier can grant. Use it instead of
  hard-coding the matrix on the FE side.

### FE-13 — Read-only Milestones + Activities for Org/Project Admins/Members

The actual list endpoint is **project-scoped**:
`GET /api/v3/projects/{project_uuid}/milestones` (NOT a top-level
`/milestones` — that path returns 404). All three scoped roles
hold `milestones:read` and `activities:read` in the seed and the
endpoint returned HTTP 200 in the audit. FE work:
- Make sure the "Milestones" / "Activities" menu items are
  rendered (not hidden) for `org_admin`, `project_admin`,
  `project_member`.
- Use the project-scoped path for the list.
- Render the list in read-only mode for `project_member` (they
  hold `:read` only — no edit perms).

### Lessons learned

- The `apply_vendor_user_assignments` helper validates that each
  `project_id` in the matrix belongs to the path-vendor, but did
  NOT enforce that the caller has authority over the path-vendor
  itself. That gap was hidden as long as the route required
  `vendors:manage` (admin-only); opening the route to org_admin via
  the body-shape carve-out exposed it, so fix 4 had to add a
  caller-vendor scope check too. Lesson: when relaxing a top-level
  permission gate, audit every helper called inside the route for
  its own authorization assumptions.
- `_align_role_permissions` makes perm-seed changes safe to deploy
  without an alembic, but the boot-time revoke runs on service
  start. If both monolith and user-mgmt mutate the same role's
  perm list and the boot order matters, document it. (For round 8
  the two perm changes are non-conflicting — drop `master_data:view`
  from org_admin and add `users:read_all` to project_admin —
  so order doesn't matter.)
- The same path can exist on both monolith and user-mgmt with
  different behaviours (round-8 fix 6 is an example). The FE
  team's confusion about #10 came from this mismatch — they were
  hitting one service expecting the data the other served. When
  introducing a route on user-mgmt that reads a shared-DB table,
  consider mirroring it on the monolith from day one to avoid the
  cross-service-call confusion.

### Going forward — when to touch which repo

- New permission codes still go into the registry on **both**
  repos in lockstep (the perm catalog is shared via the
  ``BUILTIN_PERMISSIONS`` constant + `_align_role_permissions`
  boot loop on each service).
- For shared-DB read endpoints (`user_role_assignments`,
  `users`, `vendors`, `projects`): default to mirroring routes on
  both services so the FE has a single endpoint surface to learn
  per resource.
