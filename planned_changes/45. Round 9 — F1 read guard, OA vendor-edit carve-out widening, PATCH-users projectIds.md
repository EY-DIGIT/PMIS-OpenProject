## Round 9 — backend fix detail

### Fix A — F1 read-side hierarchy guard (bug #5)

**Where**: `PMIS-user-management/app/api/v3/users/controller.py::UserController.get`.

**Before**: `GET /users/{id}` had `require_permission(USERS_READ)` only. PMIS Admin (legacy `admin` tier) successfully fetched super_admin's profile (live: HTTP 200, returned `login: "super_admin"`).

**After**: After ID resolve, if caller != target AND target holds super_admin AND caller doesn't, return 403 "Only super_admin can view a super_admin user." Self-fetch + super_admin → super_admin reads still allowed (parity with G2/G3, which only block destructive peer ops).

**Test**: `tests/test_doc44_round9_sa_read_guard.py` — 4 cases (admin blocked, SA → SA allowed, self-read, regular target unaffected).

### Fix B — `PATCH /vendors/{id}` body-shape gate widened (bug #8)

**Where**: `PMIS-OpenProject/app/api/v3/vendors/routes.py::update_vendor`.

**Before** (round 8): non-`vendors:manage` callers could only PATCH bodies that contained ONLY `user_assignments`. OA had no path to update Contact / Email / Mobile / Project Mapping per spec.

**After**: tier-aware allowlist:

| Tier (perm signature)                                | Allowed body fields                                                          |
| ---------------------------------------------------- | ---------------------------------------------------------------------------- |
| `vendors:manage` (admin / super_admin)               | all fields, no restriction                                                   |
| `rbac:assign` + holds `org_admin` role + same vendor | `email`, `contact_person`, `phone_number`, `project_ids`, `user_assignments` |
| `rbac:assign` (project_admin only) + same vendor     | `user_assignments` only                                                      |
| no `vendors:manage` and no `rbac:assign`             | 403                                                                          |

If the body contains any field outside the caller's allowlist, the request is rejected: `403 "Insufficient permissions to edit <fields>. Required: vendors:manage"`. Caller-vendor scope check (round 8) still fires for non-admin callers.

**Test**: `tests/test_doc44_round9_alignment.py::TestOrgAdminCanEditAllowedVendorFields` (7 cases) + `TestProjectAdminLimitedToUserAssignments` (3 cases) + `TestAdminFullPatchUnchanged` (1 case).

### Fix C — `PATCH /users/{id}` accepts `projectIds`

**Where**:

- Schema: `PMIS-user-management/app/api/v3/users/schemas.py::UserUpdateRequest`.
- Helper: `PMIS-user-management/app/api/v3/users/services/replace_project_membership.py` (new).
- Wire-through: `PMIS-user-management/app/api/v3/users/controller.py::UserController.update`.

**Before**: `UserUpdateRequest` carried only user fields (email, names, vendor, division, status, phoneNumber). Project mapping changes required separate `POST/DELETE /users/{id}/role-assignments` calls. CREATE accepted `projectIds`; GET returned `projects[]`. Asymmetric.

**After**: `projectIds: Optional[List[str]]` accepted on PATCH.

- `None` (omitted) → no-op.
- `[]` → clear all project_members rows + revoke all project-tier role assignments (project_admin / project_member / division_member).
- non-empty → diff: revoke rows for projects no longer in the list; grant rows for new projects using the user's most common existing project-tier role (or `derive_org_role` when none); replace `project_members` rows to match.

Caller-vs-target gate (`can_caller_grant`) fires per grant + revoke, so an org_admin of vendor X can only operate on projects within X. Validation: every project_id must exist + not be soft-deleted (mirrors CREATE).

**Test**: `tests/test_doc44_round9_patch_project_ids.py` — 5 cases (omit / clear / diff / unknown-id-422 / response-shape).

### Lessons learned

- F1 was scoped to **mutations** in round 7 (PATCH / password /
  DELETE) but read-side leaks were not caught until tester surfaced
  it. When adding hierarchy gates, sweep ALL operations on the
  resource, not just writes.
- The body-shape gate from round 8 was too binary (user_assignments-
  only vs `vendors:manage`-everything). Round 9 generalizes it to
  per-tier field allowlists. The pattern (pull caller's role tier,
  intersect requested fields with that tier's allowlist, reject
  excess) is reusable for other tier-aware partial-PATCH routes.
- Audit-as-you-go: when a user files a single misalignment ("PATCH
  doesn't accept projectIds"), it's worth running the full GET vs
  PATCH alignment audit before committing the fix — round 9
  surfaced 5+ similar gaps that would have come back as more bugs.
  Ship the explicit fix, document the others.
