## Why this exists

These are all responses to FE-team flagged issues from a single
alignment-audit pass against the Project Management mockups (the
same audit that produced doc 44 and 45). They didn't fit cleanly
into any single doc number so each round shipped under "round N"
labels with no unifying plan doc. This retrospective closes the gap.

## What landed

### Round 10 (orgRole + check-login + admin-tier exclude)

- **`users.org_role` column** added (idempotent backfill migration).
  Companion to user-mgmt's same change. `orgRole` is now persisted
  instead of derived per-request.
- **`POST /users/create`** requires `orgRole` in the body; rejected
  if missing.
- **`GET /users/check-login?login=...`** — returns
  `{available: bool}`. Admin-only.
- **Listing filters** — `GET /users` (when project-scoped) and
  related pickers exclude `admin` / `super_admin` tier users.

### Round 11 (vendor email + access-token TTL)

- Vendor email uniqueness enforced on `POST /vendors/create` and
  `PATCH /vendors/{id}`. Excludes soft-deleted rows.
- `GET /users?vendorId=...` — filter list by vendor.
- `ACCESS_TOKEN_EXPIRE_MINUTES` raised from 15 → 60.

### Round 11b (`GET /projects/{id}/assignable-users`)

- New endpoint returning the union of (a) every user with a
  project-tier role assignment on this project and (b) every user
  with an org_admin assignment on the project's owning vendor(s).
- De-duplicated by user id. Carries `orgRole` so the FE picker can
  render names without a per-id `/users` round-trip.

### Round 11c / 11d (vendor user_assignments matrix)

- `PATCH /vendors/{id}` accepts a `userAssignments` field — a list
  of `{userId, role}` rows that fully replace the vendor's role
  assignment state.
- `GET /vendors/{id}` emits the same shape (round-trippable).

### Round 12 (PA-scope filter on `GET /vendors/{id}`)

- For project-admin callers, `projects` and `user_assignments` on
  `GET /vendors/{id}` are filtered to projects they administer.
  Other tiers see the unfiltered view.

### Lessons learned

- Multi-round work that lacks a unifying plan doc accumulates
  rapidly. The "round N" naming-by-commit-message worked tactically
  but left no audit trail until this retrospective. Going forward,
  any 4-round-plus batch should get its own doc *before* round 1.
- `user_assignments` round-trippability is what made the vendor PATCH
  form sane — the FE can re-submit the same body it received without
  diffing. Worth applying the same idiom whenever a sub-resource
  list is on the same form.
