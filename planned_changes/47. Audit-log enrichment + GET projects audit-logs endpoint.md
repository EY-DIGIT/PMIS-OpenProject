# Doc 47 — Audit-log enrichment + GET `/projects/{uuid}/audit-logs`

> **Status: SHIPPED** — landed on `dev`. Single-repo change (monolith
> only — `project_audit_logs` lives here).

Adds a paginated, FE-shaped audit-log endpoint for a project, plus
denormalised snapshot columns on `project_audit_logs` so the response
can be built without joining the live `users` / `projects` rows at
read time (which would diverge over time as those rows are edited or
soft-deleted).

| # | Sub-change |
|---|------------|
| 1 | Add NOT NULL snapshot columns to `project_audit_logs`: `actor_login`, `actor_code`, `project_name`, `project_status`, `owner`. Flip `actor_role` from nullable to NOT NULL. |
| 2 | Backfill columns from joined live data on existing rows; for `actor_role`, derive from `user_role_assignments` (priority bucket fallback). |
| 3 | New `GET /api/v3/projects/{uuid}/audit-logs` with a top-level `project` block and flat per-row elements. Paginated with offset + pageSize. |
| 4 | Auto-resolve helpers in `services/audit.py` so every `record_audit` call writes the snapshot columns + `actor_role` without each call-site repeating the lookup. |

---

## Why this exists

The pre-doc-47 `project_audit_logs` table stored only `project_id`,
`actor_id`, `action`, and `created_at`. The FE-required audit view
needs the project name, status, owner, the actor's login, their
human-readable code, and their role at the time of the action — all
of which decay if you join to live tables (user gets soft-deleted,
project gets renamed, role gets revoked). Snapshotting at write time
is the standard fix.

The endpoint is new because there was no public read surface for
this data previously.

## What's in scope / out of scope

- ✅ Snapshot columns: `actor_login`, `actor_code`, `project_name`,
  `project_status`, `owner`, `actor_role` — all NOT NULL post-backfill
- ✅ Auto-resolve helpers — every existing `record_audit` call site
  picks up the snapshot fields for free
- ✅ `GET /projects/{uuid}/audit-logs` with project block + flat rows
- ❌ Multi-project / global audit view (out of scope — project-scoped only)
- ❌ Filtering by date range or action type (follow-up if needed)

## Schema

```
project_audit_logs:
  + actor_login    VARCHAR(50)  NOT NULL INDEX
  + actor_code     VARCHAR(40)  NOT NULL
  + project_name   VARCHAR(255) NOT NULL
  + project_status VARCHAR(50)  NOT NULL
  + owner          VARCHAR(50)  NOT NULL
  ~ actor_role     VARCHAR(50)  NULL → NOT NULL  (NOT NULL flip after backfill)
```

Three alembic migrations:
- `b1d3e7a9c204` — add 4 NOT NULL columns + backfills + NOT NULL flip
- `c3a8d1f7e542` — add `actor_code` NOT NULL with backfill
- `d4f9b2e8a317` — backfill `actor_role` with priority buckets

`_ROLE_PRIORITY` for the actor_role resolver:
`super_admin > admin > org_admin > project_admin > project_member >
division_member`. Falls back to `users.org_role` if no assignment
matches. Else `"user"`. `actor_id IS NULL` → `"system"`.

### Lessons learned

- Snapshot columns are cheaper than joining to live tables at read
  time, especially when the live tables are mutable and soft-deletable.
  The denormalisation cost (5 short columns × N rows) is trivial.
- A single auto-resolve helper at the audit-write point is much
  better than expecting every caller to pass the right snapshot
  fields. The helper has one responsibility (compute the snapshot
  from `actor_id` + the project row) and every call site benefits.
