# Doc 48 — API-split forwarders: surface user-mgmt-only routes on monolith :8000

> **Status: SHIPPED** — landed on `dev`. Companion to user-mgmt's
> doc 7. Cross-repo move with the cross-cutting plan recorded here.

Three thin handlers were added to monolith `:8000` that forward to
PMIS-user-management on the same path. The full implementation
(caller-vs-target grant gates, lockout checks, audit emission,
vendor→users query) stays in user-mgmt. The forwarders exist solely
so the FE can hit `:8000` for these routes without a direct `:8001`
call.

| Method | Path | Status |
|--------|------|--------|
| POST   | `/api/v3/projects/{uuid}/role-assignments` | forwarded to user-mgmt |
| DELETE | `/api/v3/projects/{uuid}/role-assignments/{aid}` | forwarded to user-mgmt |
| GET    | `/api/v3/vendors/{vendor_id}/users` | forwarded to user-mgmt |

The matching `GET /api/v3/projects/{uuid}/role-assignments` listing
already had a native handler on monolith and intentionally stays
local — only the writes (and the vendor-users listing) forward.

---

## Why this exists

Pre-doc-48, hitting `POST /api/v3/projects/{uuid}/role-assignments`
on `:8000` returned 404. The route existed on `:8001` (user-mgmt
owned the logic) but the FE was pointed at `:8000`. Two options:

1. Port the logic into monolith — would duplicate the caller-vs-target
   grant gates, `revoke_with_lockout_check`, `serialize_assignment`,
   etc. (~400 lines of duplicated code with drift risk).
2. Thin forwarding handlers — ~15 lines each, no logic copied,
   user-mgmt remains the single source of truth.

Option 2 was chosen. The reusable `proxy_or_503(request, body_bytes)`
helper added in `app/shared/user_service_client.py` handles the hop;
returns the upstream response when `USER_SERVICE_PROXY_ENABLED` is on
and a clear 503 envelope when it's off.

## What's in scope / out of scope

- ✅ `proxy_or_503` helper in `app/shared/user_service_client.py`
- ✅ Three thin forwarders — body, query, Authorization forwarded;
  upstream response (including 4xx envelopes) bubbled back unchanged
- ✅ Listing endpoint (`GET /role-assignments`) stays local —
  monolith already had a native handler
- ❌ Other partial-proxy patterns (per-method splits on the same path)
  outside these three

---

## API surface

The handler bodies are intentionally minimal:

```python
async def create_project_role_assignment(project_uuid, request):
    body_bytes = await request.body()
    return await proxy_or_503(request, body_bytes=body_bytes)
```

`proxy_or_503` returns:
- The upstream response when proxy is on (status + headers + body
  passed through)
- A `503` with `errorIdentifier="user_service_proxy_disabled"` when
  proxy is off (these handlers have no local fallback — fail loud)

### Lessons learned

- Thin forwarders are the right answer when the URL namespace belongs
  to one service but the logic belongs to another. Ports invite drift;
  forwarders don't.
- Fail-closed (503) on `USER_SERVICE_PROXY_ENABLED=false` is the
  safer default when there's no local fallback. Falling through to
  monolith's router would 404 — less informative than the explicit
  503 envelope.
- This is also the architectural smell that motivated [doc 50](
  ./50.%20Convert%20proxy%20middleware%20to%20httpx.AsyncClient.md):
  these new forwarders made the sync-httpx-in-async-middleware
  bottleneck more visible because they share the same plumbing.
