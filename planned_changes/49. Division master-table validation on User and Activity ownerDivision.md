# Doc 49 — Division master-table validation on User.division and Activity.ownerDivision

> **Status: SHIPPED** — landed on `dev` in this repo, user-mgmt, and
> project-management. Cross-repo change. The user-mgmt slice is at
> [user-mgmt doc 8](../../PMIS-user-management/planned_changes/8.%20User.division%20must%20reference%20the%20shared%20divisions%20master%20table.md);
> project-mgmt slice is at [project-mgmt doc 9](../../PMIS-project-management/planned_changes/9.%20Activity.ownerDivision%20master-table%20validation.md).

Replaces the previously-strict-against-hardcoded-`tmd1`/`tmd2`/
`others` enum check on `Activity.ownerDivision` and the pre-existing
loose check on `User.division` with a uniform lookup against the
shared `divisions` master table. Admins can add new division codes
via `POST /api/v3/master/divisions/create` and they become
assignable immediately, with no code release.

| Surface | Before | After |
|---|---|---|
| Activity.ownerDivision (POST/PATCH) | strict `tmd1/tmd2/others` Pydantic enum | normalised in Pydantic; service layer queries `DivisionRepository.is_known_code` |
| User.division (POST/PATCH, monolith mirror) | no validation | service layer queries the same repository |
| Project.owner (POST/PATCH/upsert) | DB-extended catalog check (was already correct) | unchanged |

---

## Why this exists

Two motivations collided:

1. **FE feedback**: admins added new divisions to the catalog and
   expected them to be assignable everywhere. The Activity
   ownerDivision validator was hardcoded — admins couldn't use their
   own division values without a code release.
2. **Drift cleanup**: an earlier interim loosening removed the
   user-mgmt enum check entirely, leaving `users.division` accepting
   arbitrary strings (which were leaking into the DB).

Master-table-driven validation fixes both: catalog is the source of
truth, soft-disabled rows are rejected (active-only), and any
catalog row works.

## What's in scope / out of scope

- ✅ Service-layer catalog check via `DivisionRepository(db).is_known_code(...)`
  on Activity create/update + User create/update (monolith mirror)
- ✅ Pydantic `_validate_division_code` now only normalises (strip +
  lowercase + non-empty)
- ✅ Test fixture seeds `tmd1`/`tmd2`/`others` so existing tests that
  use built-ins continue to pass; `test_master_data.py`'s manual
  seed fixture made idempotent
- ✅ Mirrored to user-mgmt (read-only `DivisionModel` mirror,
  shared-DB lookup) and project-management (activity mirror)
- ❌ `divisionOther` / `ownerOther` coupling — untouched. When
  `division == 'others'` a free-text label is still required;
  unchanged from pre-doc-49.
- ❌ The dead `assert_owner_is_division` helper at
  `app/api/v3/projects/services/transitions.py:57` — never called,
  left in place.

---

## Schema

No schema change. The `divisions` table is already in production
(seeded by `init_db`, written by `POST /api/v3/master/divisions/create`).

---

## Service-layer rules

`DivisionRepository.is_known_code(code) -> bool` filters
`active = true`. Active-only matches the FE picker (which hides
soft-disabled rows). Soft-disabled rows are no longer assignable to
new activities / users — historical rows that reference them stay
valid (only writes hit the check).

### Lessons learned

- "Validate against a master table" is more flexible than enum-as-
  code, but both have failure modes — the enum is rigid (release-
  gated); the master-table check fails open if the catalog is empty.
  Mitigated here by `init_db` seeding the built-ins.
- The cross-service ORM mirror in user-mgmt (a minimal
  `DivisionModel` declaring only the columns we query) keeps the
  cross-service coupling explicit + small. Anyone touching the
  monolith's `divisions` schema knows to check the mirrors too.
- Test fixture seeding had to be made idempotent in `test_master_data.py`
  because the conftest-level seed and the per-test fixture both
  inserted built-ins (unique-constraint collision). Idempotency at
  seed time is cheap and avoids exactly this kind of conflict.
