# Doc 50 — Convert user-service and notification proxy middleware to `httpx.AsyncClient`

> **Status: SHIPPED** — landed on `dev` in this repo. Monolith-only
> change. Removes the only known concurrency-time bottleneck in the
> proxy plumbing.

The proxy middleware was calling `httpx.Client(...).request(...)`
synchronously from inside an `async def __call__` ASGI method. That
blocks the Uvicorn event loop for the full upstream RTT, so
concurrent proxied requests serialise on a single worker — a slow
upstream cascades into queueing for every other in-flight request,
including ones on unrelated local paths. This doc swaps the sync
client for `httpx.AsyncClient` and awaits the upstream call.

| Surface | Before | After |
|---|---|---|
| `UserServiceProxyMiddleware.__call__` | `with httpx.Client(...) as c: c.request(...)` (sync, blocks event loop) | `async with httpx.AsyncClient(...) as c: await c.request(...)` |
| `NotificationServiceProxyMiddleware.__call__` | same sync pattern | same async pattern |
| `proxy_or_503` (and the 3 forwarders that use it) | sync — returns a Response | `async def`, callers `await` it |

---

## Why this exists

A static-review probe across the codebase flagged the sync-httpx-in-
async-middleware pattern as the only real concurrency-time risk.
Under single-user load it's invisible — measured live timings showed
~83ms p50 for proxied user-list, ~75ms direct — proxy hop is ~8ms.
Under concurrent load it's the dominant bottleneck.

The probe was triggered by user reports that some APIs "feel slow",
which I couldn't reproduce at single-user. The async fix removes
the failure mode regardless of whether it was *the* cause.

## What's in scope / out of scope

- ✅ Convert `_proxy_request_sync` → `_proxy_request_async` in both
  proxy clients
- ✅ Make `maybe_proxy_user_service` and `proxy_or_503` async; their
  callers now `await` them
- ✅ Update the proxy-test fixtures to also patch `httpx.AsyncClient`
  (test stub had only patched `httpx.Client`, broke after the swap)
- ❌ Connection pooling — each request still creates a fresh
  AsyncClient instance. Same lifecycle as the pre-doc-50 sync
  Client. Not a regression; future doc could share a client across
  requests if it becomes the next bottleneck.
- ❌ Other sync-in-async patterns elsewhere in the codebase — out of
  scope for this doc

## Benchmark — 20 concurrent requests, 200ms upstream sleep, single Uvicorn worker

| | wall-clock | p50 | p95 | p99 |
|---|---:|---:|---:|---:|
| SYNC (before) | **4.431s** | 2443ms | 4427ms | 4427ms |
| ASYNC (after) | **0.539s** | 477ms | 534ms | 534ms |
| Speedup | **8.2×** | 5.1× | 8.3× | 8.3× |

Outbound httpx log timestamps under SYNC show requests firing
200–220ms apart (serialised on the event loop). Under ASYNC, all 20
requests fire within milliseconds of each other and complete around
the same time. The gap widens linearly with concurrency — at N=50
it'd be ~10s vs ~0.5s (20×); at N=100 ~20s vs ~0.5s (40×).

Single-user warm timings are unchanged — there's nothing to
parallelise with N=1.

## What doesn't change

- Forwarded request semantics — headers, body, query string,
  Authorization, OPTIONS bypass, `_is_proxy_active()` gating, 503 on
  unreachable, 4xx error-envelope passthrough — all preserved.
- The rerouting simulation (`c:/tmp/sim_api_rerouting.py`)
  asserts 25 invariants pre and post; all still green.
- The proxy flag (`USER_SERVICE_PROXY_ENABLED`) behaviour is
  identical. Off = no-op pass-through. On = forward.

### Lessons learned

- Sync HTTP inside `async def` is a silent footgun in FastAPI. The
  middleware compiled, the tests passed (because the test stubs
  were also sync), and single-user benchmarks looked fine. Only
  concurrent load exposed it.
- Hand-rolled httpx test stubs are a maintenance burden — they
  shadow the real `httpx.Client` / `httpx.AsyncClient` and have to
  be updated lock-step with the production code. Could revisit by
  using `respx` everywhere (the cross-repo rerouting simulation
  already uses respx and didn't need any test-side change for this
  refactor).
- The fix doesn't require an edge gateway. The "architecture
  critique" earlier in the planning round suggested an nginx-in-front
  pattern; this fix is independent and doesn't compete with that
  future refactor.
