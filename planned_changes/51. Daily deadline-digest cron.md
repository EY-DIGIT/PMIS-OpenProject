# Doc 51 — Daily deadline-digest cron (cross-cutting plan)

> **Status: SHIPPED-PENDING-DEPLOY** — implementation lives in
> notification-service. Monolith is not touched.

A new endpoint on notification-service that DevOps's host cron calls
once a day to send per-user digest emails about milestones /
activities ending soon (or past due) on projects the user is
responsible for.

This doc is the **cross-cutting plan**. The implementation slice
lives in
[`PMIS-notification-service/planned_changes/3. Daily deadline-digest cron endpoint.md`](../../PMIS-notification-service/planned_changes/).

---

## Why this lives in notification-service, not the monolith

- Per user direction: "I don't want the cron job to be on the monolith".
- notification-service already has the dispatch + SMTP/SendGrid +
  `notification_log` audit + template renderer. Putting the cron
  there means no new email plumbing.
- notification-service connects to the shared `pmis_db` (since
  doc 38), so it can query projects / milestones / activities / users
  / role-assignments directly via read-only ORM mirrors. No HTTP hop
  back to monolith or project-mgmt is needed.
- Monolith stays out of this entirely. The plan-doc is here only so
  the cross-cutting design is findable from this folder.

## What changes in each repo

### `PMIS-notification-service`
- New endpoint: `POST /api/v1/notifications/cron/daily-digest`
  gated by `X-Cron-Secret` env var.
- New service: `app/services/digest_service.py` (scan + recipient
  resolution + per-user aggregation + rendering + send).
- New built-in template `project_deadline_digest` (email, HTML).
- 7 new read-only ORM mirrors for the shared-DB tables this service
  reads (projects, milestones, activities, users, roles,
  user_role_assignments, project_vendors).
- Full test coverage (~28 new tests).

### `PMIS-OpenProject` (this repo)
- **No code change.** This doc only.

### `PMIS-user-management`
- **No code change.**

### `PMIS-project-management`
- **No code change.**

## Deployment

The DevOps person wires the host cron to call the endpoint daily,
suggested 09:00 IST. Env vars they need to set on the
notification-service container:

```
CRON_SHARED_SECRET=<long random>
FRONTEND_BASE_URL=<portal URL — reused from password-reset config>
DEADLINE_WINDOW_DAYS=5     # optional, default 5
```

Suggested crontab line:

```
0 9 * * * curl -fsS -X POST -H "X-Cron-Secret: $SECRET" \
  http://localhost:8002/api/v1/notifications/cron/daily-digest \
  > /var/log/pmis/daily-digest.json
```

`CRON_SHARED_SECRET=""` (the default) keeps the endpoint **disabled**
(returns 503) until ops sets it. Safe boot.

---

## Outcome

Once deployed, the only ongoing maintenance is:
- Edit the `project_deadline_digest` template via
  `/api/v3/master/notification_templates/...` if the email copy needs
  to change (no code release required).
- Tune `DEADLINE_WINDOW_DAYS` if 5 days is too noisy / too quiet.
- Watch `notification_log` for `status='failed'` rows if SMTP /
  SendGrid is flaky.

If we want to add SMS or task/subtask-level deadline alerts later,
those are follow-up docs.
