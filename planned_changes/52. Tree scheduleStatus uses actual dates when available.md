# Doc 52 — Tree `scheduleStatus` / `daysDelayed` use actual dates when available

> **Status: SHIPPED-PENDING-DEPLOY** — code landed on `dev` in both
> monolith and project-mgmt. No DB / FE / wire changes; just the
> calculation now prefers actuals when present.

The existing `_schedule_status` helper on the tree endpoint computed
its verdict from **planned** `start_date` / `end_date` only — actual
dates were intentionally ignored (the original framing answered "is
this on schedule?" not "is this done?"). Per the new product rule,
the calculation should treat actual dates as the primary signal and
fall back to planned dates only when actuals are NULL.

| # | Sub-change |
|---|------------|
| 1 | `_schedule_status` and `_attach_schedule_status` accept two new optional kwargs: `actual_start_date`, `actual_end_date`. |
| 2 | The helper picks `effective_start = actual_start_date or start_date` and `effective_end = actual_end_date or end_date`, then runs the same not-started / in-progress / delayed math against those. |
| 3 | All four `_attach_schedule_status` call sites in `build_project_tree` (milestone, activity, task, subtask) now pass the row's actual dates through. |

---

## Why this exists

Real life: a milestone with `planned_end = 2099-01-10` shouldn't
read `in_progress` forever just because nobody bothered to push the
planned end date back. If `actual_end_date` was recorded as
`2025-01-20`, the schedule status should reflect that the work
actually ended back then, and (relative to today) it's delayed
relative to its actual completion.

Symmetrically: a milestone that started early (`actual_start_date`
before its planned start) shouldn't read `not_started` just because
today is still before the planned start.

The previous "planned only" rule was deliberate — but the FE team
flagged that the current product UX requires actuals-first.

## What's in scope / out of scope

- ✅ Helper signature extended (backwards-compatible — both new
  kwargs default to `None`, falling back to planned dates if not
  passed).
- ✅ All call sites in `build_project_tree` updated to pass the
  row's actual dates.
- ✅ Test coverage: 7 new unit cases covering each actual / planned
  combination, plus one end-to-end test that proves the actual_end
  override surfaces correctly through `/api/v3/projects/{id}/tree`.
- ❌ No new endpoint. The user originally asked for a per-node
  "track" API; that was descoped during planning — the existing
  tree response already carries the field for every node, and
  pulling one node is a cheap pluck from the tree response.
- ❌ No wire shape change. `scheduleStatus` / `daysDelayed` keep
  their existing keys + value enum.
- ❌ No DB / migration change.

## Decision log

| Q | Decision | Rationale |
|---|---|---|
| Effective-date pairing | `actual_X or planned_X` independently for start and end | Matches the user's intent: each side falls back individually. A node with only `actual_start` set + no `actual_end` is "in progress relative to its planned deadline" — the most useful interpretation. |
| Wire-enum naming | Keep `not_started` / `in_progress` / `delayed` | FE already consumes these. No FE work needed for this change. |
| Today-before-actual_start corner case | Honestly returns `not_started` | If the actual_start is in the future (e.g., a data correction or scheduled-but-not-yet-started item), the verdict is "not started" — which is correct. |
| Backwards compatibility | The new kwargs default to `None` | Any existing caller not aware of doc 52 keeps the old behaviour. Only the four call sites in `build_project_tree` were updated to pass them. |

---

## API surface

No change. The tree response still emits, per node:

```json
{
  ...
  "scheduleStatus": "delayed",
  "daysDelayed": 5
}
```

`daysDelayed` is computed against the **effective** end date, so a
node finished early (`actual_end_date` in the past) will report a
positive `daysDelayed` if today is past that actual end.

---

## Service-layer rules

The single `_schedule_status` helper at
[`app/api/v3/tree/service.py`](../app/api/v3/tree/service.py) is the
sole place this rule lives. Anything else that needs a schedule
status (a future "track" endpoint, a digest field, a dashboard
column) should call this same helper rather than re-implementing
the math.

## Risks + open questions

- **Existing rows with stale actuals.** If a row has
  `actual_end_date` set to some incorrect value from an earlier
  data-import bug, its `scheduleStatus` will now reflect that bad
  value where previously it was driven by the cleaner planned
  dates. Low risk — the actual-end column is FE-controlled and
  visible on the edit form; bad values would already have been
  noticed.
- **No flag.** The change is unconditional. If the new rule turns
  out to be wrong for a subset of projects, the revert is one
  commit.
