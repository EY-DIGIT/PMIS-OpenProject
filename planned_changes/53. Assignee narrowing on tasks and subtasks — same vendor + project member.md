# Doc 53 — Assignee narrowing on tasks and subtasks (same vendor + project-tier member)

> **Status: SHIPPED-PENDING-DEPLOY** — code landed on `dev`. No DB
> migration, no FE coordination, no wire-shape change. Monolith-only.

Tightens the value-level gate on `assignedTo` for tasks and subtasks.
For non-admin callers, the assignee must now both:

1. Be in the **same vendor** as the caller (`users.vendor_id` match).
2. Hold a **project-tier role assignment** on the same project
   (`user_role_assignments` with role in `{project_admin,
   project_member, division_member}` and `scope_id = project_id`).

`admin` and `super_admin` callers bypass both — they have global
reach by design. `org_admin` callers fall under the narrowing along
with `project_admin` / `project_member`.

---

## Why this exists

Before doc 53, the validator only checked that the assignee existed,
was active, and not soft-deleted. The FE's `/projects/{id}/assignable-
users` picker correctly narrowed the list shown to the user, but the
BE accepted any active UUID — meaning a `project_member` on Project A
could (with a hand-crafted PATCH body or a misbehaving picker) assign
a task to someone in a completely different vendor with no
relationship to the project.

Closing that gap puts the FE picker and the BE gate in agreement: the
server now rejects what the picker wouldn't have offered in the first
place.

## What's in scope / out of scope

- ✅ Same-vendor check (caller's `users.vendor_id` == assignee's)
- ✅ Project-tier role membership check on the same project
- ✅ admin / super_admin bypass
- ✅ org_admin and division_member fall under the narrowing
- ✅ Tasks (POST create + PATCH update) and subtasks (POST create +
  PATCH update + nested create)
- ❌ Activity / milestone assignee — no `assignedTo` field at those
  levels; out of scope
- ❌ `project_members` table membership as an alternative
  qualification — only `user_role_assignments` project-tier rows
  count (per your explicit choice in the planning question)
- ❌ org_admin reach via vendor mapping as a qualification path for
  the assignee — they have to hold a project-tier role specifically

## Decision log

| Q | Decision | Rationale |
|---|---|---|
| Which roles trigger narrowing? | project_admin, project_member, org_admin | Direct user instruction. All three are vendor-scoped tiers. |
| What about admin / super_admin? | Bypass | Global tier, no vendor binding; would otherwise be locked out of every assignment by the same-vendor rule. |
| What counts as "assigned to the project"? | Project-tier role assignment row (`project_admin`, `project_member`, `division_member` with `scope_id = project_id`) | Matches the canonical doc-41 scoped-role surface. project_members table not consulted (legacy path). |
| What counts as "same vendor"? | `users.vendor_id` on both rows must match exactly. Both must be non-null | Single source of truth for "user's organization" per the doc-41 "vendor = organization" decision. |
| Caller with NULL vendor_id under a non-admin role? | Reject with a clear "no vendor binding" error | Data anomaly; better to fail loudly than silently allow cross-vendor. |
| Backwards compatibility on the validator signature? | New kwargs default to `None`; legacy callers see Layer-1-only behaviour | Existing callers (audit-log, etc) that don't have project context aren't broken. |

## API surface

**No wire-shape change.** Same request bodies, same success
responses, same error envelope.

What changes: **two new error messages** under the existing
`ValidationError` envelope when the new rules reject a request:

```json
{
  "data": null,
  "error": {
    "_type": "Error",
    "errorIdentifier": "ValidationError",
    "message": "assignedTo user '<uuid>' is not in your organization. You can only assign tasks / subtasks to users in your own vendor."
  },
  "status": 422
}
```

```json
{
  "data": null,
  "error": {
    "_type": "Error",
    "errorIdentifier": "ValidationError",
    "message": "assignedTo user '<uuid>' is not assigned to this project. They must first be added as a project_admin, project_member, or division_member of the project."
  },
  "status": 422
}
```

The FE should already be unaffected since the `/assignable-users`
endpoint correctly narrows the picker. Any request that survives
this gate would have been one the picker wouldn't have offered.

## Service-layer rules

`app/shared/assignee.py::validate_assignable_user_id` is now a
two-layer check:

**Layer 1 (unchanged, always enforced)** — user exists, is `active`,
is not soft-deleted.

**Layer 2 (new, enforced when both `project_id` and `caller_user_id`
are supplied AND caller is NOT admin/super_admin)**:

```
caller_role admin or super_admin  → return user_id (bypass)
                                  └→ caller_vendor_id is NULL?  → 422 "no vendor binding"
                                  └→ assignee_vendor_id != caller_vendor_id → 422 "not in your organization"
                                  └→ assignee has no project-tier role row on this project → 422 "not assigned to this project"
                                  └→ otherwise: return user_id
```

`admin_or_super` is resolved via the existing
`RbacRepository.user_has_admin_role(user_id)` (checks both legacy
`user_roles` and `user_role_assignments` global-scope rows).

`_PROJECT_TIER_ROLES = ("project_admin", "project_member",
"division_member")` is the canonical set the project-tier check uses.

## Risks + open questions

- **Existing rows with cross-vendor assignees** — anything that was
  successfully assigned before doc 53 stays assigned; the new rule
  only applies to *new* writes. If you want to audit / clean up
  existing cross-vendor assignments, that'd be a separate report
  (`SELECT ... FROM tasks JOIN users ON tasks.assigned_to = users.id
  WHERE users.vendor_id != <caller's vendor>`).
- **org_admin reach** — an org_admin of Vendor A who is also the
  vendor mapped to Project X can assign tasks on Project X, but
  only to users whose `users.vendor_id` is also A and who hold a
  project-tier role on X. If your `org_admin` users sometimes have
  `users.vendor_id IS NULL` (a data anomaly), they'll see the
  "no vendor binding" rejection. Easy data cleanup.
- **Future FE rendering** — the new error messages are
  human-readable. If you want a richer error envelope (e.g.
  `errorIdentifier="assignee_not_in_vendor"` for FE-side dispatch),
  flag it and I'll add it as a follow-up.
