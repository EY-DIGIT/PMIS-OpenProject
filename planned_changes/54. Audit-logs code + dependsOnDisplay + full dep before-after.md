# Doc 54 — Audit-logs enrichment: `code`, `dependsOnDisplay`, `dependsOnDisplayBefore`, plus full task/subtask audit coverage

> **Status: SHIPPED-PENDING-DEPLOY** — code landed on `dev`. No DB
> migration. FE consumers may surface the three new keys directly;
> nothing they currently rely on changes shape. Monolith-only.

Enriches the per-row payload of `GET /api/v3/projects/{id}/audit-logs`
with three new fields, and closes two gaps in the underlying audit-row
writers so the change history at task/subtask level is no longer silent.

| Field on each row | Meaning |
|---|---|
| `code` | Project rows → `projectCode`. M/A/T/S rows → the entity's current `displayCode` (`M1` / `A1.2` / `T1.2.3` / `S1.2.3.4`). `null` when the entity has been hard-deleted. |
| `dependsOnDisplay` | Resolved labels from the audit-snapshot's `after.depends_on`. Populated on `*.create` and `*.dep_change` rows. `null` everywhere else. |
| `dependsOnDisplayBefore` | Resolved labels from the audit-snapshot's `before.depends_on`. Populated **only** on `*.dep_change` rows. `null` everywhere else. |

The original `before` / `after` JSON in each row is preserved
byte-for-byte — these three fields are additive. Bare UUIDs in the raw
JSON are still there; the new keys sit alongside as a human-readable
projection.

---

## Why this exists

Two distinct problems showed up while reading the audit log:

1. **UUID soup.** Every row carries entity UUIDs and dependency UUIDs.
   Reading the log meant cross-referencing UUIDs against the tree
   endpoint to figure out *which* milestone/activity got changed and
   *what* it now depends on. `code` + `dependsOnDisplay` fix that.

2. **dep_change rows only recorded the new state.** A row that said
   "this is the dependency now" lost the prior state. Reading a chain
   like `[A1.1] → [A1.3] → [A1.5]` required scrolling back to the
   previous dep_change for the same entity to know what was replaced —
   and if that prior row had been deleted (entity hard-delete cascade),
   the history was just gone. `dependsOnDisplayBefore` (backed by a new
   `before.depends_on` capture at write time) makes each row
   self-contained.

A third problem fell out of the audit while we were in there:

3. **Tasks and subtasks were not audited on update at all.** Constants
   `ACTION_TASK_UPDATE` / `ACTION_TASK_DEP_CHANGE` /
   `ACTION_SUBTASK_UPDATE` / `ACTION_SUBTASK_DEP_CHANGE` had been
   declared but never called — `tasks/services/update.py` and
   `subtasks/services/update.py` wrote no audit rows. So any
   field-edit or dep-edit at the T/ST level was silent in the history.
   Closed by adding the corresponding `record_audit` calls.

---

## What's in scope / out of scope

- ✅ `code` + `dependsOnDisplay` + `dependsOnDisplayBefore` on every
  row of the audit-logs response
- ✅ `before.depends_on` captured on `milestone.dep_change` and
  `activity.dep_change` (previously only `after.depends_on`)
- ✅ Full audit coverage at T/ST level: `task.update`,
  `task.dep_change`, `subtask.update`, `subtask.dep_change` now fire
  through `record_audit` like their M/A counterparts
- ✅ Raw `before` / `after` JSON preserved verbatim — no audit detail
  is lost; the new fields are additive
- ✅ Hard-deleted entity → `code = null`, dep labels likewise
  collapse to bare UUIDs the label index can't resolve (consistent
  with tree-API behaviour)
- ❌ Backfilling pre-fix dep_change rows — historical rows that
  recorded only `after.depends_on` will surface as
  `dependsOnDisplayBefore: null` (honest "we don't know what was
  there before")
- ❌ Doc-33-era project-association rows (`project.vendor.assoc_*`,
  `project.member.*`) — these carry no entity dep concept; `code` is
  the `projectCode`, `dependsOnDisplay` and `Before` are both `null`
- ❌ Wire-shape change — same envelope, same pagination, same row
  ordering; the three new keys are added, nothing removed

## Decision log

| Q | Decision | Rationale |
|---|---|---|
| Field name for the new "current/new deps" projection | `dependsOnDisplay` (same as tree) | Mirrors the tree API key so FE consumers can share resolution code. |
| Field name for the prior-state projection | `dependsOnDisplayBefore` (sibling, not nested) | Keeps the field's type stable — always a list or null — instead of becoming `{before, after}` only on dep_change rows. Easier to consume. |
| Shape on non-dep_change rows | `dependsOnDisplay = audit snapshot's after.depends_on`; `Before = null` | The display matches what the row's payload actually asserts (e.g. an `activity.create` with `depends_on=[]` displays `[]`, not the entity's current deps). Using live tree state instead would be misleading on historical rows. |
| Capturing old deps at write time | New `list_*_dependencies` call before each `set_*_dependencies` swap, value put on `before.depends_on` | Cheapest place to read the truth. Adds one indexed query per dep_change write. |
| Task / subtask audit gaps | Add full `*.update` + `*.dep_change` coverage now | They were declared-but-unused. Leaving them uncalled meant any FE rendering the audit log at T/ST level would show a hole. |
| Project-level rows on `code` | Use the project's `projectCode` | The "what was changed" for a project.* row is the project itself; that's already a readable string elsewhere in the API. |
| Hard-deleted entity rows | `code` and dep labels go null, raw UUIDs in `before/after` stay | Honest signal that the entity is gone; FE can fall back to showing the UUID if needed. |
| Pre-fix historical dep_change rows (only `after.depends_on` recorded) | `dependsOnDisplayBefore = null` | We can't invent a prior state. Null is the truthful representation. |

## API surface

**No wire-shape change** — same endpoint, same envelope, same
pagination. Three new keys appear on each row:

```jsonc
{
  "id": 11,
  "actorId": "...",
  "actorCode": "US-ADMI-260512000001",
  "actorLogin": "admin",
  "actorRole": "user",
  "action": "task.dep_change",
  "code": "T1.1.2",                       // NEW — entity's current displayCode
  "dependsOnDisplay": ["T1.1.1"],         // NEW — resolved after.depends_on
  "dependsOnDisplayBefore": [],           // NEW — resolved before.depends_on
  "before": {                             // unchanged: raw JSON with UUIDs
    "task_id": "7c17c951-...",
    "depends_on": []
  },
  "after": {                              // unchanged: raw JSON with UUIDs
    "task_id": "7c17c951-...",
    "depends_on": ["8ba8613f-..."]
  },
  "createdAt": "2026-05-13T08:30:12.131878+05:30"
}
```

### Field-by-action matrix

| Action prefix.event | `code` | `dependsOnDisplay` | `dependsOnDisplayBefore` |
|---|---|---|---|
| `project.create` / `project.update` / `project.publish` / `project.archive` | `projectCode` | `null` | `null` |
| `project.vendor.assoc_*` / `project.member.*` | `projectCode` | `null` | `null` |
| `milestone.create` / `activity.create` / `task.create` / `subtask.create` | `M1` / `A1.2` / `T1.2.3` / `S1.2.3.4` | resolved `after.depends_on` (often `[]`) | `null` |
| `*.update` / `*.soft_delete` / `*.restore` | entity's current displayCode | `null` | `null` |
| `*.dep_change` (all four levels) | entity's current displayCode | resolved `after.depends_on` | resolved `before.depends_on` (`null` on pre-fix historical rows) |

## Service-layer rules

### Capturing `before.depends_on` on dep_change writes

`milestone/activity/task/subtask` update services now snapshot the
current deps **before** swapping them in, and pass the snapshot on
`before.depends_on`:

```python
deps_before: Optional[List[str]] = None
if desired_deps is not None:
    deps_before = DependencyRepository(db).list_<kind>_dependencies(entity_id)
    DependencyRepository(db).set_<kind>_dependencies(
        entity_id, model.project_id, desired_deps,
        actor_id=current_user_id,
    )
...
if desired_deps is not None:
    record_audit(
        db,
        project_id=model.project_id,
        actor_id=current_user_id,
        action=ACTION_<KIND>_DEP_CHANGE,
        before={"<kind>_id": entity_id, "depends_on": list(deps_before or [])},
        after={"<kind>_id": entity_id, "depends_on": list(desired_deps)},
    )
```

### New T/ST update + dep_change audit calls

`tasks/services/update.py` and `subtasks/services/update.py` now fire
`record_audit` on both field updates and dep changes, mirroring the
M/A pattern:

| File | Audit rows added |
|---|---|
| `app/api/v3/tasks/services/update.py` | `task.update`, `task.dep_change` |
| `app/api/v3/subtasks/services/update.py` | `subtask.update`, `subtask.dep_change` |

Each takes a `before_snapshot` of pre-update fields and writes
`before = {"task_id": id, **before_snapshot}` / `after = {<changed
fields>}` for the update row, plus the dep_change row described above
when `dependsOn` was supplied.

### Display-layer resolution

`app/api/v3/projects/routes.py::list_project_audit_logs` now builds:

- a `LabelIndex` for the project (4 small queries — same one the tree
  endpoint uses)
- 4 dep maps (one per kind) — only used to surface bare UUIDs when
  needed; the primary source for dep labels is now the audit snapshot,
  not the live tree

Each row goes through `_resolve_target(action, before, after)` →
`(code, deps_after, deps_before)`. The three new fields are placed
between `action` and `before` on the response.

## Cutover / rollout

Pure code change. Restart `pmis-backend` to pick it up. No DB, no FE
coordination required (FE can adopt the new keys at its own pace).

### Rollback

`git revert` the commit:
- `dependsOnDisplay` / `dependsOnDisplayBefore` keys disappear from
  the response
- T/ST update + dep_change rows stop being written (back to silent)
- Existing audit rows are unaffected — `before.depends_on` already
  captured in rows written under doc 54 will simply not surface on
  the post-rollback response

## Risks + open questions

- **Pre-fix dep_change rows.** Historical rows recorded only
  `after.depends_on`. Post-fix, `dependsOnDisplayBefore` will be
  `null` for those — accurate but slightly asymmetric across the
  history boundary. Backfill is not possible without inventing data.
- **New T/ST audit volume.** Adding `task.update` / `subtask.update`
  rows increases write volume on the audit table proportional to
  how often T/ST fields are edited. The denormalised snapshot columns
  on `project_audit_logs` (doc 47) keep the table tidy and the
  audit-logs endpoint's pagination handles growth, but worth a
  glance at table size after a few weeks of production traffic.
- **Field naming.** `dependsOnDisplayBefore` was chosen over nested
  `{before, after}` to keep the field's type stable. If FE feedback
  is that the nested shape would be cleaner, we can swap — it's a
  display-layer-only change.
