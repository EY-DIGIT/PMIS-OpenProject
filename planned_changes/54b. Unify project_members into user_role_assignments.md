# Doc 54-b — Unify `project_members` into `user_role_assignments`

> **Status: SHIPPED-PENDING-DEPLOY** — code landed on `dev` across
> monolith + user-mgmt + project-management. One alembic migration in
> monolith (the canonical schema owner) backfills URA and drops the
> legacy table. No FE coordination; no wire-shape change.

Retires the legacy `project_members` table in favour of `user_role_
assignments` (URA), the doc-41 unified scoped-RBAC table. After this
change, project membership is recorded in exactly one place.

---

## Why this exists

`project_members` predated doc-41. URA was introduced as a "scoped
roles" table that could subsume both `project_members` (project tier)
and `user_roles` (global tier), but only the assignable-users, role-
assignments, and assignee-narrowing readers were migrated. Other
readers still consulted `project_members`.

User-visible symptom: a user attached to a project via the modern
`POST /projects/{id}/role-assignments` flow showed up correctly in
`/assignable-users` but their `GET /users/{id}` response had
`projects: []`. The detail endpoint queried the legacy table only.

The fix could have been a UNION patch on the detail-endpoint query.
Instead we did the full migration — one source of truth.

`user_roles` has the same half-migration shape at the global tier
(admin / super_admin). That's the next doc — see
[55. Unify user_roles into user_role_assignments.md](./55.%20Unify%20user_roles%20into%20user_role_assignments.md).

## Decision log

| Q | Decision | Rationale |
|---|---|---|
| What role does each legacy row map to? | `project_member` | `project_members.roles` was always `[]` in every callsite (verified by audit). The legacy row meant "user is on project, no specific tier"; `project_member` is the default project-tier role. |
| Same PR or split-deploy? | Same PR: backfill + drop in one migration | Smaller blast radius than a two-PR dance, and the alembic migration is idempotent so a failed deploy can re-run safely. project_members is project-scoped only; the user_roles migration (which gates auth on every request) will go split-deploy in doc 55. |
| Keep `/api/v3/project_members/*` URL surface? | Yes | Per user instruction. The repository class kept its API contract; only internals point at URA now. |
| Schema gap (`roles` JSON list of strings → URA `role_id` integer FK)? | No translation needed | The legacy column was a placeholder that was never populated. |
| What does "delete a membership" mean post-migration? | Delete the matching project-scoped URA row (any role tier) | Preserves the pre-migration semantic: the URL deletes the row referenced by the id. The role filter on `get_by_id` / `delete` was over-restrictive — the role is captured by the row itself, not a separate filter. |
| Cascade on project soft-delete? | Wipe every project-scoped URA row with that project_id | URA's `ck_ura_single_scope` CHECK ensures `project_id IS NOT NULL` implies `organization_id IS NULL`, so this delete only touches project-scoped rows; org-scoped assignments are untouched. |

## API surface

**No change.** Every URL keeps its existing path, response shape, and
behaviour:

| URL | Before | After |
|---|---|---|
| `GET /api/v3/users/{id}` | `projects: [...]` joined from `project_members` (often empty for modern users) | `projects: [...]` joined from URA project-scoped rows (now correct for all users) |
| `GET /api/v3/projects/{id}/members` | List from `project_members` | List from URA filtered to `role = project_member` |
| `DELETE /api/v3/memberships/{id}` | Delete from `project_members` | Delete from URA (any project-scoped role tier) |
| `POST /api/v3/users/create` with `projectIds` | Writes `project_members` rows | Writes URA rows with `role = project_member` |
| `PATCH /api/v3/users/{id}` with `projectIds` | Wipes + inserts `project_members` rows + URA rows | Wipes + inserts URA rows only |
| `DELETE /api/v3/projects/{id}` cascade | Wipes `project_members` rows for project | Wipes URA rows for project (project-scoped only) |

## Service-layer rules

### `ProjectMemberRepository` is now URA-backed

`_to_domain` hydrates the `Membership` domain object from a URA row
(URA's primary key surfaces as the legacy `id`). The `roles` field on
the domain is preserved as `[]` for back-compat — it carries no data
either way.

`get_by_id` / `delete` accept ANY project-scoped URA row (no role
filter) — the row's role tier is the row's tier, not a filter.
`list_by_project` / `list_by_user` filter to `role = project_member`
to preserve the legacy "list members at the member tier" semantic.

### `_load_projects_for_user` reads URA

Both monolith and user-mgmt user-repos use the same URA join now,
with `DISTINCT` so a user holding multiple project-tier roles on the
same project surfaces that project once.

### Cascade on project soft-delete

Both monolith and project-management's `projects/services/delete.py`
wipe URA rows where `project_id = <deleted>`. The CHECK constraint
on URA guarantees this only touches project-scoped rows.

## Migration (alembic `baddc1146b85`)

```sql
-- Backfill: every project_members row becomes a URA row with
-- role=project_member, project_id set, organization_id NULL.
-- Idempotent — skips rows that already exist.
INSERT INTO user_role_assignments
    (user_id, role_id, organization_id, project_id, created_at)
SELECT
    pm.user_id, r.id, NULL, pm.project_id, pm.created_at
FROM project_members pm
CROSS JOIN roles r
WHERE r.name = 'project_member'
AND NOT EXISTS (
    SELECT 1 FROM user_role_assignments ura
    WHERE ura.user_id = pm.user_id
      AND ura.role_id = r.id
      AND ura.organization_id IS NULL
      AND ura.project_id = pm.project_id
);

DROP TABLE project_members;
```

`downgrade()` is best-effort: it recreates `project_members` and
restores only the `project_member`-role URA rows (the legacy table
never held `project_admin` / `division_member` rows pre-migration
either).

## Cutover / rollback

### Deploy order

1. Deploy all three services on the new code together. Old containers
   were writing `project_members`; new containers write URA only. A
   small window where both containers are alive is fine — the old
   containers' writes go to the soon-to-be-dropped table, the
   migration captures them on the next run.
2. Run alembic `upgrade head` on monolith. The migration backfills
   any rows the old containers wrote and drops the legacy table.
3. Done.

### Rollback

`git revert` the change set, then `alembic downgrade -1`. The
downgrade recreates the table and best-effort-restores the
`project_member`-role URA rows. Rows added with other roles via the
modern flow (project_admin / division_member) won't appear in the
restored legacy table — they were never there pre-migration either.

## Risks + open questions

- **Mixed-version window during deploy.** If old containers keep
  writing `project_members` after new containers go live, those rows
  get captured on the next backfill run. Acceptable because the
  legacy writes were always paired with URA writes anyway (the
  replace-project-membership flow already wrote both); the
  unification just removes the redundancy.
- **`user_roles` still bifurcated.** Same anti-pattern exists at the
  global tier. Tracked in [doc 55](./55.%20Unify%20user_roles%20into%20user_role_assignments.md);
  not addressed here because the auth-middleware hot-path needs a
  more cautious dual-write transition (a stale read on admin-tier
  membership is a security bug, not just a 403).
