# Doc 55 — Unify the legacy `user_roles` table into `user_role_assignments`

> **Status: PLANNED — not yet implemented.** Companion follow-up to
> doc 54-b (project_members → URA unification). Same migration pattern;
> different scope (global tier roles rather than project tier).

---

## Why this exists

The codebase audit done during the `project_members` unification turned
up a **second, identical half-migration**: the `user_roles` table.

Same shape of problem:

- `user_roles` (compound PK `(user_id, role_id)`) predates doc-41's
  scoped-RBAC `user_role_assignments` (URA). It exists to record
  "user U holds global role R" — there's no scope concept; the row
  itself implies global tier.
- `user_role_assignments` is the modern, unified table. Global tier
  is represented as a URA row with **both** `organization_id` and
  `project_id` NULL.
- Doc 41 introduced URA but did NOT retire `user_roles`. Global role
  writes still go to `user_roles`; some readers consult `user_roles`,
  some consult URA, some consult both via a UNION.

This is the same anti-pattern that the doc-54-b migration fixed for
the project-tier table: bifurcated writes, bifurcated reads, an
incomplete migration that lives indefinitely as a maintenance trap.

## Concrete evidence

| File | Action |
|---|---|
| `app/infrastructure/db/models/user_role.py` | Legacy model — class still defined; table still created |
| `app/infrastructure/db/repositories/rbac_repository.py` (multiple sites) | Writes `UserRoleModel` rows for global admin assignments |
| `app/infrastructure/db/repositories/user_repository.py` (line ~370–380) | Filters non-admin callers via UNION over `user_roles` + `user_role_assignments` |
| `app/shared/assignee.py` | Admin-tier check reads BOTH tables via `RbacRepository.user_has_admin_role` |
| `app/api/v3/users/services/create.py` (admin flag handling) | Writes `user_roles` when `admin=True` is passed on create |
| `app/api/v3/projects/routes.py::/assignable-users` (round-11b hotfix) | Excludes admin-tier candidates via UNION over both tables |

Every read of "does this user have admin / super_admin?" goes through
a helper (`RbacRepository.user_has_admin_role`) that consults both
tables. The helper masks the bifurcation — it's a workaround, not a
fix.

## What's in scope

- ✅ Backfill: every `user_roles` row → URA row with
  `organization_id = NULL`, `project_id = NULL`, `role_id` = the
  matching role's id.
- ✅ Switch every writer that currently inserts/updates/deletes
  `user_roles` to write to URA with both scope columns NULL.
- ✅ Switch every reader to consult URA only (drop the UNION dance).
- ✅ Drop the `user_roles` table.
- ✅ Delete the `UserRoleModel` class + the `user_role.py` file in
  monolith + user-mgmt + project-management.
- ✅ Update `RbacRepository.user_has_admin_role` (and any peer helpers)
  to query URA only.

## What's out of scope

- ❌ Changing the surface-level concept of admin / super_admin. The
  global tier roles stay exactly the same — only the storage table
  changes.
- ❌ Renaming the `roles` table or touching `permissions` /
  `role_permissions`. Untouched.
- ❌ Any FE coordination. Wire shape is unchanged.

## Migration shape (same as doc 54-b)

```sql
-- Backfill: every legacy user_roles row gets a global-scope URA row.
INSERT INTO user_role_assignments
    (user_id, role_id, organization_id, project_id, created_at)
SELECT
    ur.user_id, ur.role_id, NULL, NULL, ur.created_at
FROM user_roles ur
WHERE NOT EXISTS (
    SELECT 1 FROM user_role_assignments ura
    WHERE ura.user_id = ur.user_id
      AND ura.role_id = ur.role_id
      AND ura.organization_id IS NULL
      AND ura.project_id IS NULL
);

-- Drop legacy table.
DROP TABLE user_roles;
```

URA's CHECK constraint `ck_ura_single_scope` already allows the
all-NULL combination (global scope), so no schema change is required
on URA — only the data migration + writer/reader switch.

## Risks

- **`RbacRepository.user_has_admin_role` is hot.** Auth middleware
  calls it on every request to decide whether to bypass scope filters.
  Switching it from "union both tables" to "URA only" must keep the
  legacy paths working until backfill has run. Order of operations on
  deploy:
  1. Deploy all services with code that **reads** from URA only but
     **writes** to BOTH tables (dual-write transition).
  2. Run backfill migration. Confirm URA contains every legacy row.
  3. Deploy code that **writes** URA only.
  4. Run drop-table migration.

  This is more cautious than doc 54-b (which did a single atomic
  switch + drop). Justified here because admin-role checks gate
  literally every authenticated request — a stale read is a security
  bug, not just a 403.

- **Bootstrap admin user.** `session.py` seeds an admin user at boot
  if none exists. The seed writes `user_roles` today. Needs to switch
  to URA along with the rest.

- **Tests assert specific table shape.** Search for tests that insert
  `UserRoleModel` directly — they'll need to switch to URA inserts
  with all-NULL scope.
