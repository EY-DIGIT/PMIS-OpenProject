# Feature: Project Hierarchy — Milestone → Activity → Task (unlimited nesting)

## What changed

Extended the existing `work_packages` system to enforce a structured project hierarchy:

```
Project
 └── Milestone          (depth 0, requires start_date + end_date)
      └── Activity      (depth 1, requires start_date + end_date)
           └── Task     (depth 2+, dates optional, unlimited nesting)
                └── Task
                     └── Task ...
```

### Hierarchy enforcement rules
- **No parent** → type is auto-resolved to `milestone`, dates required
- **Parent is milestone** → type is auto-resolved to `activity`, dates required
- **Parent is activity or task** → type is auto-resolved to `task`, dates optional
- Child dates must fall within parent's date range (containment validation)
- Explicit `typeId` is validated against the depth rule; omitting it auto-resolves
- Circular parent references are guarded against

### New endpoint
- `GET /api/v3/work_packages/{id}/children` — returns the full nested subtree as a recursive HAL+JSON tree

### New query filter
- `GET /api/v3/projects/{id}/work_packages?type=milestone` — filter by type internal_name
